# 07 · Prompt 工程基础（Prompt Engineering Basics）

> Prompt 工程是**不改动模型权重、仅通过组织输入来引导输出**的技术；因为 LLM 本质是"条件概率续写"，好的上下文能把它引向正确的答案分布。重要度 ⭐⭐⭐。

## 🎯 一句话核心

模型永远在做同一件事——**在给定上文的条件下预测下一个 Token**（详见 [01-llm-overview](01-llm-overview.md)）。Prompt 工程不改变这个机制，而是**精心构造那段"上文"**，让模型的条件概率分布落在你想要的答案上。同样的模型，烂 Prompt 得烂答案，好 Prompt 得好答案，差别全在**你喂了什么条件**。

## 📖 核心原理

**为什么"只改输入"就能大幅改变输出？** 因为 LLM 是 `P(下一个Token | 前面所有Token)` 的条件概率机器。你给的每一句话都是"条件"的一部分，会实时改写这个概率分布。当你写"请扮演资深法律顾问，仅依据以下合同条款回答"，模型续写时命中"专业、严谨、基于材料"那片语料分布的概率就被拉高了；当你只写"这个咋办"，条件模糊，模型只能在最泛化的分布里瞎猜。**Prompt 工程就是概率分布的"方向盘"**——不换车（模型），只打方向（上下文）。

**它和另外两种驾驭手段的分工（关键认知）：** Prompt 改的是**调用法**（最轻、零成本、即时生效），RAG 补的是**外部知识**（把私域/最新资料检索进上下文），微调改的是**模型能力本身**（最重、要训练）。三者不是替代而是叠加：**能用 Prompt 解决就别上 RAG，能 RAG 就别微调**（成本从低到高，怎么选见 [28-fine-tuning](28-fine-tuning.md)）。本篇讲的是这三者里门槛最低、性价比最高、且做任何 LLM 应用都绕不开的第一层。

**消息角色（message roles）是现代对话模型的结构化 Prompt 载体。** 你调用的 chat 模型不是喂一整段纯文本，而是喂一个"带角色标签的消息列表"，模型在训练时就学会了区别对待不同角色：

| 角色 | 作用 | 优先级 | 类比 |
|---|---|---|---|
| **System** | 设定人设、规则、约束、输出规范，全局生效 | **最高**（模型最"听"它） | 员工手册 / 岗位职责 |
| **User** | 用户当前的具体问题或指令 | 中 | 当下的具体工单 |
| **Assistant** | 模型自己的历史回复（多轮对话时回传） | 作为上下文 | 之前的对话记录 |

**为什么要区分角色？** System 消息在对齐训练（RLHF）阶段被特意教成"最高优先级的稳定指令"，适合放**不该被用户轻易覆盖**的东西（人设、安全红线、输出格式）。把"你是客服、只答产品问题、用 JSON 回复"放 System，把用户每次的具体问题放 User，模型就能在整段对话里稳定守住规则——这也是 Prompt 安全的第一道防线（把可信指令和不可信用户输入分层，详见 [10-prompt-security](10-prompt-security.md)）。多轮对话时，历史的 User/Assistant 消息一并回传，模型才有"记忆"（LLM 本身无状态，记忆靠应用层每轮重传）。

## 🔧 关键方法 / 流程 / 架构

**Prompt 设计八大原则（把模糊条件变精确条件）：**

1. **明确具体**：别说"总结一下"，说"用 3 个 bullet 总结要点，每条不超过 20 字"。
2. **给角色（role）**：一句"你是资深 X"能把分布拉进对应专业语料。
3. **给约束 + 输出格式**：字数、语气、语言、结构（JSON/表格/Markdown），把格式说死（结构化输出详见 [09-structured-output](09-structured-output.md)）。
4. **分步骤**：把复杂任务拆成"第一步…第二步…"，引导模型按序处理。
5. **提供上下文**：把回答所需的材料/背景直接放进 Prompt，别让它猜。
6. **给示例（few-shot）**：几个"输入→输出"样例胜过千言万语的描述。
7. **避免歧义**：一词多义、代词指代不清都会让分布发散。
8. **复杂任务拆解**：一个 Prompt 只干一件事，链式拆成多步比塞一个巨型 Prompt 更稳。

**Zero-shot vs Few-shot（要不要给示例）：**

```
Zero-shot（零样本）：直接下指令，不给例子
  「把下面这句话的情感分类为 正面/负面/中性：'物流太慢了'」
        └─ 靠模型自身能力，简单任务够用，Prompt 短

Few-shot（少样本）：先给几个 输入→输出 示例，再问真正的问题
  「'质量很好' → 正面
    '再也不买了' → 负面
    '还行吧' → 中性
    '物流太慢了' → ?」
        └─ 用示例"锚定"输出的格式、粒度、风格，模型照葫芦画瓢
```

**Few-shot 的权衡：** 示例能显著稳住**格式和风格**（尤其分类、抽取、固定格式生成），但①占 Token、②示例选得不好会误导（要选有代表性、覆盖边界情况的）、③数量非越多越好——通常 2~5 个即可，边际收益递减且过多可能让模型过拟合到示例的表面特征。**先试 zero-shot，不稳再加 few-shot**。

**Prompt 模板化（工程化复用）：** 生产中 Prompt 不是每次手写，而是**带变量占位的模板**，运行时把变量填进去——完全类比**参数化 SQL**（`SELECT ... WHERE id = ?`），既复用又隔离数据：

```
模板：
  你是{role}。请仅依据以下材料回答用户问题，材料之外的内容回答"未提及"。
  【材料】{context}
  【问题】{question}
  用不超过 {max_words} 字、以 {format} 格式作答。

运行时填充：role=客服助手, context=检索到的文档, question=用户输入, ...
```

模板化的好处：统一质量、便于 A/B 测试与版本管理、把"不可信的用户输入"限定在 `{question}` 变量里（安全边界，见 [10-prompt-security](10-prompt-security.md)）。RAG 就是把检索到的资料填进 `{context}` 这个占位。

**常见实用技巧：**
- **指定输出格式**：明确要 JSON/表格/列表，并给出字段 schema（[09-structured-output](09-structured-output.md)）。
- **角色扮演**：`你是…`，快速设定专业语气与知识范围。
- **限定"仅依据材料"**：`只根据上面的资料回答，资料没有就说不知道，不要编造`——**抑制幻觉的关键一句**（[05-hallucination](05-hallucination.md)）。
- **引入思维链**：复杂推理时加一句 `让我们一步步思考`，引导模型显式展开推理过程再给结论（原理与进阶见 [08-cot-reasoning](08-cot-reasoning.md)）。

## 🔑 要点速记

- Prompt 工程 = **不改模型、只组织输入**；本质是构造"条件"来引导 LLM 的条件概率分布。
- 三大驾驭手段分工：**Prompt（改调用法，最轻）/ RAG（补知识）/ 微调（改能力，最重）**，成本从低到高，能低就别高。
- 消息角色：**System（人设/规则/约束，优先级最高）> User（当前问题）> Assistant（历史回复，供上下文）**。
- 设计原则：**明确具体、给角色、给约束和输出格式、分步骤、给上下文、给示例、避歧义、拆任务**。
- **Zero-shot** 先试；不稳再上 **Few-shot**（给 2~5 个代表性"输入→输出"示例锚定格式，示例过多边际递减）。
- Prompt **模板化**（变量占位 + 复用）类比**参数化 SQL**；RAG 就是往 `{context}` 里填检索结果。
- 招牌技巧：指定输出格式、角色扮演、**"仅依据材料"抑幻觉**、"一步步思考"引 CoT。

## ❓ 高频面试 / 理解题

**Q：Prompt 工程为什么"只改输入就能改变输出"？它改的到底是什么？**
A：因为 LLM 是 `P(下一个Token | 上文)` 的条件概率模型，Prompt 就是那段"上文"，即概率分布的**条件**。改 Prompt 不动任何权重，但会实时改写模型续写时的概率分布——给角色、给约束、给示例，都是把分布往目标答案那片语料"拉"。它是模型的方向盘而非引擎，这也是为什么它零成本、即时生效、却门槛最低性价比最高。

**Q：System / User / Assistant 三种角色分别放什么？为什么要分？**
A：System 放**全局稳定的人设、规则、约束、输出格式**（优先级最高，模型最"听"）；User 放用户**当前的具体问题**；Assistant 是模型**自己的历史回复**，多轮时回传作为上下文。分层的原因：System 在对齐训练时被教成高优先级不易被覆盖，适合放安全红线和格式规范；把可信指令（System）和不可信用户输入（User）分开，也是 Prompt 注入防御的基础（[10-prompt-security](10-prompt-security.md)）。

**Q：什么时候用 Few-shot 而不是 Zero-shot？给越多示例越好吗？**
A：当任务对**输出格式/粒度/风格**有明确要求、或 zero-shot 结果不稳时用 few-shot——几个"输入→输出"示例能有效锚定输出。但不是越多越好：示例占 Token、选得不好会误导、数量上边际收益递减（通常 2~5 个够），过多还可能让模型过拟合示例的表面模式。实践是**先 zero-shot，不满意再逐步加代表性示例**。

**Q：Prompt、RAG、微调三者怎么分工选择？**
A：Prompt 改**调用法**（改输入引导，最轻、零训练成本）；RAG 补**外部/私域/最新知识**（检索资料塞进上下文，可溯源、抑幻觉）；微调改**模型能力/风格本身**（要训练，最重）。成本从低到高，原则是**能 Prompt 解决就别 RAG，能 RAG 就别微调**；它们可叠加（详见 [28-fine-tuning](28-fine-tuning.md)）。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别把安全约束只放 User 里**：该守死的规则（人设、格式、红线）放 System，放 User 容易被后续输入冲淡或被用户指令覆盖。
- ⚠️ **别写模糊 Prompt 却怪模型笨**："帮我弄一下"这种模糊条件下，输出发散是必然——多数"模型不行"其实是 Prompt 不行。
- ⚠️ **Few-shot 示例本身要严格正确且格式统一**：模型会照抄示例的一切，包括你不小心带进去的错误格式和偏见。
- ✅ **要稳定就把格式说死 + 举例 + 降温度**：口头描述格式不如直接给一个样例；需要机器解析的输出用结构化约束（[09-structured-output](09-structured-output.md)）。
- ✅ **抑制幻觉先加一句"仅依据材料、没有就说不知道"**：这是最便宜的兜底，配合 RAG 效果更好（[05-hallucination](05-hallucination.md)）。
- ✅ **加分认知**：能说清"Prompt 工程改的是条件概率分布的条件、不动权重"，比只会背"给角色给示例"这些技巧更显理解本质——所有技巧都是这一原理的推论。

### 附：烂 Prompt vs 好 Prompt 对比

同一个需求"帮我从一段用户评论里提取信息"：

**❌ 烂 Prompt（模糊、无角色、无格式、无约束）：**
```
帮我看看这条评论说了啥
"这手机拍照还行就是电池太不耐用了，客服态度倒是不错"
```
> 问题：没说提取什么、要什么格式、给谁看——模型只能自由发挥，输出一段散文，无法程序化使用，多跑几次结果还不一样。

**✅ 好 Prompt（角色 + 明确任务 + 约束 + 格式 + 示例 + 限定材料）：**
```
System: 你是电商评论分析助手，只根据用户给出的评论内容作答，不臆测评论里没有的信息。

User:
请从下面这条评论中抽取信息，严格按 JSON 输出，字段固定为：
  - aspects: 数组，每项含 name(方面) 和 sentiment(positive/negative/neutral)
  - overall: 整体情感(positive/negative/neutral)
评论中未提及的方面不要编造。

示例：
输入："续航很棒但屏幕偏暗"
输出：{"aspects":[{"name":"续航","sentiment":"positive"},{"name":"屏幕","sentiment":"negative"}],"overall":"neutral"}

现在处理这条：
"这手机拍照还行就是电池太不耐用了，客服态度倒是不错"
```
> 好在哪：System 设定角色 + "仅依据材料"抑幻觉；User 里明确任务、给死 JSON schema、给一个 few-shot 示例锚定格式、限定不编造。输出稳定可解析，换谁跑结果一致——这就是把"模糊条件"改造成"精确条件"。
