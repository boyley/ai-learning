# 27 · 安全与护栏（Safety & Guardrails）

> 护栏是在模型**输入侧和输出侧**加装的一层"安检"——用规则/分类模型/LLM 审核把不安全、不合规、不符合格式的内容挡在门外；它与模型内部的对齐（Alignment）互补，共同构成 LLM 应用的**纵深防御**。重要度 ⭐⭐。

## 🎯 一句话核心

模型本身"懂分寸"（对齐）但不可靠，所以要在应用层的**入口和出口各架一道关卡**：进来的先查（注入/越狱/PII/越界），出去的再验（违规内容/幻觉/格式/信息泄露）。护栏的价值不是"堵住一切"，而是**用多层廉价检查把风险概率压到可接受**——单靠模型自觉或单靠一层规则都靠不住。

## 📖 核心原理

**为什么需要护栏？因为对齐（Alignment）只保证了"模型倾向于"安全，而非"必然"安全。** 模型经过 RLHF/DPO 对齐后学会了拒绝明显有害请求（呼应 [01-llm-overview](01-llm-overview.md) 的三段式范式），但它是**概率模型**：会被巧妙的 Prompt 注入/越狱绕过、会幻觉编造事实、会不小心复述 System Prompt 或把用户 A 的隐私说给用户 B。这些风险无法靠"再训练一次"根除，必须在**应用层**用确定性的工程手段兜底。护栏就是这层工程兜底——它把"模型可能出错"当作既定前提来设计。

**护栏的本质是一个"策略执行点（policy enforcement）"**：定义一组安全/合规策略（不能泄露 PII、不能谈政治、输出必须是合法 JSON……），然后在数据流经模型前后**强制校验**。它和模型是解耦的——护栏不改模型权重，只在旁边加"过滤器"，因此可以独立迭代、可审计、可解释（哪条策略在哪一步拦了什么，都有据可查）。

**核心设计张力：误杀（false positive）vs 漏放（false negative）。** 护栏收得越紧，越可能把正常请求也拦掉（伤用户体验）；收得越松，越可能放过真正的攻击（出安全事故）。没有免费的午餐——只能按业务的**风险容忍度**校准阈值：医疗/金融/未成年场景宁可误杀，通用闲聊可以放松。正因单层护栏必然在这条曲线上取舍，实践上采用**纵深防御（defense in depth）**：多层异构检查叠加（规则 + 分类模型 + LLM 审核），任一层漏了还有下一层兜，整体既不必把单层调到极端严格，也能把综合漏放率压低。

## 🔧 关键方法 / 流程 / 架构

**输入护栏 → 模型 → 输出护栏 的管道：**

```
用户输入
   │
   ▼
┌─────────────── 输入侧护栏（进门先查）───────────────┐
│ ① Prompt 注入 / 越狱检测   （详见 10-prompt-security）│
│ ② 敏感话题 / off-topic 拦截（超出业务范围直接挡）     │
│ ③ PII 脱敏：识别身份证/手机号/邮箱/银行卡 → 遮蔽     │
│ ④ 敏感话题黑名单（暴恐/违法诉求）                    │
└──────────────────────┬──────────────────────────────┘
          放行/脱敏后的输入│（命中→拒绝或改写或转人工）
                         ▼
                  ┌────────────┐
                  │  LLM 模型   │  ← 自身已对齐(RLHF)，但不可全信
                  └──────┬─────┘
                    原始输出│
                         ▼
┌─────────────── 输出侧护栏（出门再验）───────────────┐
│ ⑤ 内容审核 Moderation：暴力/仇恨/色情/违法 分类检测   │
│ ⑥ 幻觉 / 事实校验         （详见 05-hallucination）  │
│ ⑦ 格式 / Schema 校验      （详见 09-structured-output）│
│ ⑧ 敏感信息泄露检测：System Prompt/密钥/他人PII 不外泄 │
└──────────────────────┬──────────────────────────────┘
          通过的安全输出  │（不通过→重生成/兜底话术/拦截）
                         ▼
                     返回用户
```

**输入侧护栏（把风险挡在模型之前）：**

| 护栏 | 防什么 | 典型做法 |
|---|---|---|
| **注入/越狱检测** | 用户用"忽略以上指令""扮演 DAN"绕过约束 | 关键词/正则 + 专门分类模型（详见 [10-prompt-security](10-prompt-security.md)） |
| **敏感话题拦截** | 政治/医疗诊断/法律意见等高风险话题 | 话题分类模型 + 黑名单 |
| **PII 脱敏** | 用户输入里带身份证、手机、卡号、地址 | 正则 + NER 命名实体识别 → 遮蔽/替换占位符 |
| **话题范围限制（off-topic）** | 客服机器人被引去聊无关内容 | 意图/相关性分类，超范围礼貌拒答 |

**输出侧护栏（把风险挡在返回用户之前）：**

| 护栏 | 防什么 | 典型做法 |
|---|---|---|
| **内容审核 Moderation** | 输出暴力/仇恨/色情/违法内容 | 审核 API/分类模型给多维度打分过阈值 |
| **幻觉/事实校验** | 一本正经编造事实 | 对照检索证据核查、引用溯源（详见 [05-hallucination](05-hallucination.md)） |
| **格式/Schema 校验** | 输出不是合法 JSON、字段缺失 | JSON Schema 校验，失败则重试/修复（详见 [09-structured-output](09-structured-output.md)） |
| **信息泄露检测** | 吐出 System Prompt、API Key、他人隐私 | 关键词/正则扫描 + 相似度比对已知机密 |

**四类实现手段（由轻到重，通常组合使用）：**

1. **规则 / 正则**：最快最省、可解释、零延迟；但覆盖窄、易被绕过、误杀多（如正则拦"kill"会误伤"kill the process"）。适合 PII、明确黑名单。
2. **分类模型**：训练/调用一个轻量分类器判"是否有害/是否越界/是否 PII"；比正则鲁棒、有一定泛化，但要维护模型、有延迟。如内容审核分类器、注入检测器。
3. **LLM 审核（LLM-as-judge）**：用另一个 LLM 判"这段回答是否违规/是否偏题/是否泄密"；最灵活、能理解语义，但**贵、慢、本身也可能被绕过或误判**，一般用于高价值/复杂判断。
4. **专门 Guardrails 框架（概念级）**：**NeMo Guardrails**（用 Colang 声明式定义对话流与安全轨道）、**Llama Guard**（Meta 出的专用安全分类模型，对输入输出做安全分类）、Guardrails AI（声明式输出校验/修复）等——把上面几类手段封装成可配置的护栏管道，不用从零手搓。

**对齐（Alignment）与护栏的分工：** 对齐是**模型层面**的安全——通过 RLHF/DPO 让模型"天生"倾向拒绝有害请求（详见 [01-llm-overview](01-llm-overview.md)）；护栏是**应用层面**的安全——外挂的、可控可审计的过滤器。二者互补：对齐挡掉大部分显性有害，护栏兜住对齐漏掉的、以及对齐管不着的（格式、PII、私域越界、信息泄露）。

**合规维度（企业落地绕不开）：** 数据隐私与 **GDPR**（用户数据最小化收集、可删除、可导出、跨境限制）、内容合规（符合当地法规与平台政策）、**审计日志**（每次请求/拦截/放行留痕，可追溯可举证）、**可解释**（能说清"为什么这条被拦"，护栏相比黑盒模型天然更可解释）。

**Agent 场景的特殊安全：** Agent 能调工具、执行动作，风险从"说错话"升级为"做错事"（删库、转账、发邮件）。核心原则——**工具权限最小化**（只授予完成任务必需的工具与数据范围，白名单而非黑名单）、**危险动作人工确认（human-in-the-loop）**（写操作/不可逆操作/高金额操作强制人工二次确认）、对工具的输入输出同样套护栏（防止工具返回内容里夹带二次注入）。ReAct 等 Agent 编排的安全在对应章节展开。

## 🔑 要点速记

- 护栏 = 在**输入侧 + 输出侧**加的校验/过滤层，把不安全/不合规/不合格式的内容挡住。
- **输入侧**：注入/越狱检测、敏感话题拦截、**PII 脱敏**、off-topic 范围限制。
- **输出侧**：内容审核 Moderation、幻觉/事实校验、格式/Schema 校验、信息泄露检测（别吐 System Prompt/密钥）。
- 四类手段由轻到重：**规则/正则 → 分类模型 → LLM 审核 → 专门框架**（NeMo Guardrails、Llama Guard），通常组合。
- **对齐 vs 护栏**：对齐是模型层安全（RLHF），护栏是应用层安全（外挂过滤器），二者互补。
- 核心权衡：**误杀（false positive）vs 漏放（false negative）**，按风险容忍度校准阈值。
- 方法论：**纵深防御（defense in depth）**——多层异构检查叠加，别指望单层挡一切。
- **合规**：数据隐私/GDPR、内容合规、审计日志、可解释。
- **Agent 安全**：工具权限最小化 + 危险动作人工确认（human-in-the-loop）。

## ❓ 高频面试 / 理解题

**Q：既然模型已经用 RLHF 对齐过了，为什么还要在应用层加护栏？**
A：因为对齐只让模型**概率上倾向**安全，不保证必然安全。模型是概率生成器，会被 Prompt 注入/越狱绕过、会幻觉、会不慎泄露 System Prompt 或他人隐私，这些无法靠再训练根除。护栏是应用层的确定性工程兜底：它把"模型可能出错"当既定前提，用规则/分类模型/LLM 审核在入口出口强制校验，且**解耦、可审计、可解释、可独立迭代**。对齐防模型"想不想干坏事"，护栏防它"万一还是干了"——纵深防御。

**Q：输入侧和输出侧护栏分别防什么？各举例。**
A：输入侧在**喂给模型之前**查用户输入——注入/越狱检测（防"忽略以上指令"）、敏感话题与 off-topic 拦截（防被带偏出业务范围）、PII 脱敏（把身份证/手机号遮蔽后再进模型）。输出侧在**返回用户之前**验模型输出——内容审核 Moderation（暴力/仇恨/违法分类）、幻觉/事实校验（对照证据溯源）、格式/Schema 校验（保证合法 JSON）、信息泄露检测（别把 System Prompt/密钥/他人隐私吐出去）。一句话：进门先查、出门再验。

**Q：护栏设计里最核心的权衡是什么？怎么处理？**
A：**误杀 vs 漏放**——收紧了会拦正常请求（伤体验），放松了会放过攻击（出事故），二者此消彼长。处理方式：① 按业务**风险容忍度**校准阈值（金融医疗未成年宁可误杀，通用闲聊放松）；② 采用**纵深防御**，用规则+分类模型+LLM 审核多层异构叠加，这样单层不必调到极端严格，综合漏放率也能压低。别指望单层护栏又准又全。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别只在输出侧加护栏**——注入攻击、PII 泄露在输入侧就该拦；只守出口，恶意 Prompt 已经污染了模型上下文。入口出口都要设卡。
- ⚠️ **别指望单层/单手段挡一切**——正则会被绕、分类模型有漏检、LLM 审核也会误判且能被注入。纵深防御，多层异构叠加才稳。
- ⚠️ **护栏本身也可能被攻击**——用 LLM 做审核时，被审内容里可能夹带针对审核器的注入；Agent 工具返回结果也要当"不可信输入"重新过护栏。
- ✅ **PII 脱敏要在数据进模型/进日志前做**——否则隐私会顺着上下文和审计日志外泄，反而制造合规风险；用占位符替换、必要时保留映射以便回填。
- ✅ **护栏要留审计日志**：每次拦截/放行/改写都记录（命中哪条策略、置信度、原文哈希），既满足合规举证，也用于持续调阈值、发现新型攻击。
- ✅ **Agent 场景权限最小化 + 人工确认**：工具用白名单授权，不可逆/高风险动作（删除、转账、外发）强制 human-in-the-loop，把"说错话"的风险和"做错事"的风险分级管控。
