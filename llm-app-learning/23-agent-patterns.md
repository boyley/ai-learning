# 23 · Agent 编排模式（Agentic Patterns）

> 构建 LLM 应用的**方法论骨架**：把"用 LLM 完成一个复杂任务"拆成几种可复用的编排模式，核心原则是**用最简单能 work 的方案**——能用固定 Workflow 组合解决，就别上完全自主 Agent。重要度 ⭐⭐⭐。

## 🎯 一句话核心

Agentic 系统分两大类：**Workflow（人预先编排好固定路径，LLM 只填空）** 和 **Agent（LLM 自己决定下一步走哪、走几步）**。绝大多数生产需求用五种固定 Workflow 模式（提示链 / 路由 / 并行 / 编排者-执行者 / 评估-优化）组合就能搞定；**真正需要模型自主决策路径的开放式任务才上 Agent**——因为越自主越强，但也越难控、越贵、越不稳。

## 📖 核心原理

**Anthropic《Building Effective Agents》的核心区分：Workflow ≠ Agent。**

- **Workflow（工作流）**：LLM 和工具通过**预先写死的代码路径**编排。开发者提前决定了"先干什么、再干什么、在哪分叉"，LLM 只在每个节点上做具体的语言任务（分类、生成、抽取）。路径是**确定的、可预测的**。
- **Agent（智能体）**：LLM **自己动态决定**流程、自己选用哪个工具、自己判断何时结束。系统给它目标和工具，它在一个循环里"思考→行动→观察"直到完成（即 ReAct 循环，详见 [22-agent-react](22-agent-react.md)）。路径是**运行时才生成的、不可预测的**。

**为什么要先做这个区分？** 因为它决定了系统的**可靠性—灵活性权衡**。Workflow 路径固定，所以**可测试、可预测、便宜、好调试**，但只能解决"你能提前想清楚步骤"的任务。Agent 灵活到能处理开放式问题，但每一步都靠模型自主决策，错误会**累积放大**、成本随步数线性甚至指数增长、行为难复现——这正是 [22-agent-react](22-agent-react.md) 里讲的自主性代价。

**贯穿全篇的黄金原则（Anthropic 反复强调）：**

1. **用最简单能 work 的方案。** 很多号称"需要 Agent"的需求，其实一次精心的 LLM 调用 + 检索/工具就够了——先别急着上编排框架。
2. **只在确实提升效果时才加复杂度。** 每加一层（多一次调用、多一个分支、多一轮循环）都在增加延迟和成本，要问"这一层换来的准确率/能力值不值"。
3. **能用固定 Workflow 组合，就别上完全自主 Agent。** Workflow 的确定性是生产系统的朋友。
4. **框架是加速器不是必需品。** 理解底层模式（本质就是"LLM 调用 + 代码控制流"）比套框架更重要；框架的抽象层反而可能掩盖出错点。

**一句话记住定位：** Workflow 是"你画好流程图，LLM 填空"；Agent 是"你给目标，LLM 自己画流程图并执行"。

## 🔧 关键方法 / 流程 / 架构

### 五大 Workflow 编排模式对照表

| 模式 | 做什么 | 适用场景 | 代价/注意 |
|---|---|---|---|
| **Prompt Chaining 提示链** | 把任务拆成**串行**的固定步骤，前一步输出喂给下一步；步间可插程序化校验（gate） | 任务能**清晰分解为固定顺序**的子步（如"先写大纲→再按大纲扩写→再翻译"） | 串行 = 延迟叠加；每步都可能引入误差 |
| **Routing 路由** | 先用一次 LLM/分类器判断输入类型，再**分发**到不同的专用处理分支 | 输入**类型多样**、不同类型该用不同 Prompt/模型（如客服工单分退款/技术/咨询；简单问题走小模型、难的走大模型） | 分类错 = 全错；类别要互斥清晰 |
| **Parallelization 并行化** | 把工作**并发**跑：① Sectioning 分片——拆成独立子任务同时做再合并；② Voting 投票——同一任务跑多次取多数/择优 | 子任务互相独立可并行（分片提速）；或需要多视角/多次采样提升可靠性（投票做校验、护栏、打分） | 多次调用 = 成本翻倍；投票需设计聚合规则 |
| **Orchestrator-Workers 编排者-执行者** | 一个主 LLM **动态拆解**任务、把子任务派给多个 worker LLM 执行，再**汇总**结果 | 子任务**数量/内容事先不定**、要靠模型临场拆（如"改这个需求涉及哪几个文件"由主 LLM 现场决定） | 类比主从/MapReduce，但拆分是动态的；比 Parallelization 更灵活也更贵 |
| **Evaluator-Optimizer 评估-优化** | **生成→评估→按反馈改进**的循环：一个 LLM 产出，另一个 LLM 当评审给具体意见，反复迭代直到达标 | 有**明确评价标准**、且反馈能实质提升质量、可迭代（如翻译润色、代码改到测试通过、长文按 rubric 打磨） | 循环 = 步数不定、成本上限要设；评价标准要可操作 |

> ⚠️ **Parallelization vs Orchestrator-Workers 的关键差别**：并行化的子任务**在编码时就固定拆好了**（几片、拆哪些是写死的）；编排者-执行者的子任务是**运行时由主 LLM 临场决定的**（几个、拆什么都不定）。前者是固定 Workflow，后者已带一点 Agent 味道。

### 关键模式简图

```
① Prompt Chaining（串行链，可带校验门）
   In →[LLM 步1]→ out1 →(Gate 校验?)→[LLM 步2]→ out2 →[LLM 步3]→ Out
                         └─不合格→回退/终止

② Routing（先分类再分发）
                ┌─类型A→[LLM/流程 A]─┐
   In →[路由LLM]┼─类型B→[LLM/流程 B]─┼→ Out
                └─类型C→[LLM/流程 C]─┘

③ Parallelization
   (a) Sectioning 分片           (b) Voting 投票
        ┌→[LLM 子任务1]┐              ┌→[LLM 第1次]┐
   In →─┼→[LLM 子任务2]┼→[聚合]→Out  In┼→[LLM 第2次]┼→[多数/择优]→Out
        └→[LLM 子任务3]┘              └→[LLM 第3次]┘

④ Orchestrator-Workers（主从，动态拆分）
                 ┌ 派→[Worker 1]┐
   In →[编排LLM]─┼ 派→[Worker 2]┼→[编排LLM 汇总]→ Out
     (动态决定拆几个/拆什么) └ 派→[Worker N]┘

⑤ Evaluator-Optimizer（生成-评估循环）
   In →[生成 LLM]→ 草稿 →[评估 LLM 打分+反馈]
            ▲                     │
            └── 不达标：带反馈重写 ┘
                     │达标
                     ▼
                    Out
```

### 何时才用真正的自主 Agent

当满足以下特征时，固定 Workflow 会捉襟见肘，才值得上 Agent：

- **开放式（open-ended）**：无法提前枚举需要多少步、走哪条路径；
- **步数不定**：解决问题的动作序列因输入而异，写不出固定流程图；
- **需要模型自主决策**：每一步该用哪个工具、下一步做什么，得靠模型看当前观察结果临场判断；
- **可容忍不确定性并有兜底**：环境能提供反馈（工具执行结果、报错），且有护栏/人工检查点/成本上限来约束跑飞。

典型如：编码 Agent（自主读文件、改代码、跑测试、看报错再改）、复杂研究/调研 Agent。其内核就是 [22-agent-react](22-agent-react.md) 的"思考-行动-观察"循环。

### 组合使用：模式可嵌套

这些模式不是互斥选项，而是**积木**，真实系统常嵌套组合，例如：

```
路由(Routing) 到"复杂任务"分支
   └→ 编排者(Orchestrator) 动态拆成 3 个子任务
        ├→ 每个子任务内部用 提示链(Chaining) 分步做
        └→ 汇总后用 评估-优化(Evaluator) 循环打磨到达标
```

**方法论：从最简单一层起步，只在效果不够时才叠加下一层模式。**

## 🔑 要点速记

- **Workflow vs Agent**：Workflow = 预先编排的固定代码路径（LLM 填空）；Agent = 模型运行时自主决定路径（LLM 画流程图）。
- **黄金原则**：用最简单能 work 的方案；能组合固定模式就别上完全自主 Agent；只在确有提升时才加复杂度。
- **五大编排模式**：Prompt Chaining（串行拆步）、Routing（分类分发）、Parallelization（分片/投票并行）、Orchestrator-Workers（动态拆分主从）、Evaluator-Optimizer（生成-评估循环）。
- **Parallelization 两变体**：Sectioning 分片提速；Voting 多次投票提可靠性（做护栏/打分）。
- **并行化 vs 编排者**关键差：子任务是**编码时固定拆** vs **运行时动态拆**。
- **Evaluator-Optimizer 前提**：有可操作的评价标准 + 反馈能实质改进 + 可迭代。
- **上 Agent 的门槛**：开放式、步数不定、需模型自主决策路径，且有护栏与成本上限兜底。
- **复杂度守恒**：越自主越强也越难控——多一次调用/一层循环就多一份延迟、成本与不确定性（呼应 [22-agent-react](22-agent-react.md)）。

## ❓ 高频面试 / 理解题

**Q：Workflow 和 Agent 到底有什么本质区别？为什么要先分清？**
A：本质区别在**谁决定控制流**。Workflow 的路径由开发者用代码**提前写死**，LLM 只在每个节点做语言任务，路径确定、可测、可预测、便宜；Agent 的路径由 LLM **运行时自主生成**（在思考-行动-观察循环里自己选工具、定步数），灵活但不可预测、贵且易跑飞。先分清是因为它决定了可靠性—灵活性权衡：能用 Workflow 解决就别上 Agent，这是生产系统降低成本和风险的第一原则。

**Q：五种编排模式分别解决什么问题？各举一例。**
A：① Prompt Chaining——任务能清晰按顺序拆解时串行分步（写大纲→扩写→翻译）；② Routing——输入类型多样、要分流到不同处理（客服工单分类后走不同流程，或难易分流到大小模型）；③ Parallelization——独立子任务并发提速（分片），或同题多次采样投票提可靠性（内容审核多重护栏）；④ Orchestrator-Workers——子任务数量内容事先不定、需模型临场拆解（改一个需求现场判断涉及哪些文件）；⑤ Evaluator-Optimizer——有明确评价标准且能迭代改进（代码改到测试通过、译文按 rubric 反复润色）。

**Q：Parallelization 的 Sectioning 和 Orchestrator-Workers 都在"拆任务并行"，区别是什么？**
A：区别在**拆分发生的时机与主体**。Sectioning 的子任务是**开发者在编码时就固定拆好的**（拆几片、拆哪些写死在代码里），属于确定的 Workflow；Orchestrator-Workers 的子任务是**主 LLM 在运行时动态决定的**（几个、拆什么都因输入而变），已带自主性、更灵活也更贵、更难预测。一个是固定分片，一个是动态编排。

**Q：什么时候不该用固定 Workflow，而必须上自主 Agent？**
A：当任务是**开放式、步数无法提前枚举、且每一步该做什么必须靠模型看实时反馈临场决策**时。比如编码 Agent 要自己读代码、改、跑测试、看报错再决定下一步，你写不出固定流程图。但上 Agent 的前提是环境能给反馈、且配好护栏（工具白名单、人工检查点、最大步数/成本上限），否则自主性会带来错误累积和成本失控。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别一上来就上 Agent 框架**。多数需求一次好的 LLM 调用 + 检索/工具就够，或几个固定 Workflow 模式组合即可；过早引入自主 Agent 徒增延迟、成本和不可控性。先问"这个任务我能画出固定流程图吗？"能画就用 Workflow。
- ⚠️ **Routing 的分类错误会污染整条链**。路由节点分错类，后面分支再对也没用；要保证类别互斥清晰，对模糊输入设"默认/兜底"分支，并监控分类准确率。
- ⚠️ **Evaluator-Optimizer 容易死循环或空转**。必须设**最大迭代轮数 + 成本上限**，且评价标准要可操作（能让生成方据此实质改进），否则评审只会反复挑无关紧要的毛病。
- ✅ **给自主 Agent 装护栏和"刹车"**。工具白名单、参数校验、最大步数/预算上限、关键动作前人工确认——自主性越高，兜底机制越不能省（详见 [22-agent-react](22-agent-react.md)）。
- ✅ **加分认知**：这些模式的底层其实只有两个原语——**"LLM 调用" + "代码控制流"**。所谓编排框架不过是把这两者的组合方式做了封装；理解了"Workflow 是代码编排路径、Agent 是模型编排路径"，就能不依赖任何框架自己搭系统，也能一眼看穿框架抽象背后的出错点。
