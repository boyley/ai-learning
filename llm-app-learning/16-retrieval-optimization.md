# 16 · 检索与召回优化（Retrieval Optimization）

> 检索是 RAG 的"进料口"——**喂进 LLM 的上下文质量，上限就由这一步决定**；纯向量检索远不够，要靠混合检索 + Query 改写 + 多路融合把"该找的都找回来"。重要度 ⭐⭐⭐。

## 🎯 一句话核心

RAG 效果差，**八成不是模型不行，而是没检索到对的内容**——LLM 只能基于"检索给它的那几段"作答，检索没召回的知识它永远看不到。所以检索优化的目标只有一个：**让真正相关的内容尽可能进入候选集（提高召回 recall）**，再交给 Rerank 精排去粗取精（[17-rerank](17-rerank.md)）。

## 📖 核心原理

**纯向量检索的能力与盲区。** 向量检索（[11-embedding](11-embedding.md)）把 query 和文档都编码成向量，按语义相似度找最近邻。它的强项是**语义近似**——"如何重置密码"能召回"账号找回流程"，哪怕一个词不重合。但它有几处硬伤：

- **专有名词 / 编号 / 代码 / 精确关键词召回差**：Embedding 把文本压成稠密向量，会"抹平"字面细节。`订单号 A1B2-9987`、`ERR_CONN_4021`、函数名 `getUserById`、法条编号"第 47 条"这类**靠精确字面匹配才对**的东西，语义向量反而容易漏——因为它们的"语义"很弱，靠的是**字符级精确命中**。
- **口语化 / 含糊 query 检索不准**：用户问"这玩意儿咋不好使了"，与文档里规范书面的表述语义鸿沟大；query 太短、指代不清、一句话塞多个意图时，单个向量无法表达清楚检索意图。
- **单路召回视野有限**：一个 query 一个向量，只能从一个角度找。

**为什么"混合"而非"二选一"。** 向量检索强在语义、弱在字面；关键词检索（BM25 等稀疏检索）恰好相反——强在**字面精确匹配**（编号、专名、代码一命中就高分），弱在同义/语义泛化。两者的**错误是互补的**：向量漏掉的精确词，BM25 能捞回；BM25 漏掉的同义改写，向量能补上。合起来召回率显著高于任何单路，这就是 **Hybrid Search（混合检索）** 的根本动机。

**召回（recall）与精确（precision）的权衡贯穿全局。** 检索阶段的首要目标是**别漏**（高 recall）——因为漏掉的内容后面任何环节都救不回来；而"太多噪音块混进来"的问题（precision 低）可以交给后续的 **Rerank 精排**和 **Top-K 截断**去解决。所以工程上的典型分工是：**检索阶段广撒网求召回 → Rerank 阶段精挑选求精确**（详见 [17-rerank](17-rerank.md)）。理解这条"先召回后精排"的两阶段哲学，是做好 RAG 检索的关键。

## 🔧 关键方法 / 流程 / 架构

### 1. 混合检索 Hybrid Search + 融合

同时跑**向量检索（语义）**和 **BM25 关键词检索（字面）**，各自出一个排名列表，再用融合算法合并。最常用的是 **RRF（Reciprocal Rank Fusion，倒数排名融合）**：只看每个文档在各列表里的**名次**（不依赖不同检索器不可比的原始分数），名次越靠前贡献越大。

```
RRF_score(d) = Σ  1 / (k + rank_i(d))      k 常取 60
              各路
```

> 为什么用"排名"而非"原始分数"融合？因为向量的余弦相似度（0~1）和 BM25 分数（可到几十）**量纲完全不同**，直接加权相加没有可比性、还得费劲调权重；RRF 只用名次，天然归一、鲁棒、无需调参，所以成为工业默认融合法。

```
                         用户 Query
                             │
              ┌──────────────┴──────────────┐
              ▼                              ▼
      ┌───────────────┐             ┌────────────────┐
      │ 向量检索(语义) │             │ BM25 检索(字面) │
      │  Embedding+ANN│             │  倒排索引/关键词 │
      └───────┬───────┘             └────────┬───────┘
        排名列表 A                       排名列表 B
        d3 d7 d1 …                       d7 d9 d3 …
              └──────────────┬──────────────┘
                             ▼
                  ┌─────────────────────┐
                  │  RRF 融合 + 去重      │  按 Σ1/(k+rank) 重排
                  └──────────┬──────────┘
                             ▼
                    候选集 Top-N（高召回）
                             │
                             ▼
                  ┌─────────────────────┐
                  │  Rerank 精排(可选)    │  见 17-rerank
                  └──────────┬──────────┘
                             ▼
                   Top-K 交给 LLM 生成
```

### 2. Query 改写 / 扩展（在检索前做文章）

query 本身写得差，检索再强也白搭。常见手段：

| 手段 | 做法 | 解决什么 |
|---|---|---|
| **Query 改写** | 让 LLM 把口语化/含指代的问题改写成清晰规范的检索式 | 口语化、指代不清、多轮省略 |
| **多子问题拆分** | 复合问题拆成多个子问题，各自检索再合并 | 一句话塞多个意图，单向量表达不清 |
| **同义词/术语扩展** | 补充同义词、缩写全称、行业术语 | 用户用词与文档用词不一致 |
| **HyDE** | 先让 LLM 生成一个"假设答案"，用**答案**去检索而非用问题 | query 与 doc 的语义鸿沟 |

**HyDE（Hypothetical Document Embeddings）的巧思**：问题和答案在向量空间里往往**离得远**（一个是疑问句、一个是陈述性文档），直接拿问题检索容易偏。HyDE 先让 LLM"脑补"一段假设答案（可能有错，但**结构和用词更像真正的目标文档**），再用这段假设答案的向量去检索——相当于把 query 挪到了"文档那一侧"，**缩小 query-doc 语义鸿沟**，召回更准。代价是多一次 LLM 调用（延迟↑），且假设答案跑偏时可能引入噪音。

### 3. 多路召回 + 融合

把上面的思路推广：**多个 query（原始 + 改写 + 子问题 + HyDE 假设答案）× 多个检索器（向量 + BM25 + ...）并行召回**，全部结果合并、去重、用 RRF 融合成一个候选集。多路互补，能明显把"边角相关"的内容也捞进来。代价是调用次数和延迟增加，需要权衡。

### 4. 元数据过滤（先缩范围再检索）

在向量检索前，先用**结构化条件**（时间、部门、文档类型、租户 ID、权限标签等）过滤掉不可能相关的块，再在剩下的子集里做向量检索。好处：①**缩小搜索空间**，召回更准、更快；②**保证正确性/隔离**（如多租户只能查自己的数据、只查近一年的文档）。这依赖向量库支持带过滤条件的检索（filtered ANN），详见 [13-vector-database](13-vector-database.md)。

### 5. Top-K 与相似度阈值

- **Top-K 不是越大越好**：K 太小可能漏关键块；K 太大则**噪音块稀释信号**、且**撑爆上下文窗口**（成本↑、"迷失在中间 lost-in-the-middle"效应导致中段内容被忽视）。典型做法是**检索阶段召回较大 N（如 50）→ Rerank → 只保留 Top-K（如 3~5）给 LLM**。
- **相似度阈值过滤**：设一个最低相似度门槛，把明显不相关的块直接丢掉——**宁可"没找到"也别塞垃圾**。尤其当知识库里根本没有答案时，阈值能避免硬凑一堆无关块导致 LLM 幻觉编造。

## 🔑 要点速记

- 检索质量决定 RAG 上限：**LLM 只能看见检索给它的内容**，漏了就永远答不出。
- 纯向量检索强在**语义近似**、弱在**精确字面**（编号/专名/代码/关键词）与口语化 query。
- **Hybrid Search = 向量(语义) + BM25(字面)**，二者错误互补，召回更全。
- **RRF** 只用名次融合多路排名，天然归一、鲁棒、无需调权重（k 常取 60）。
- **Query 改写/拆分/扩展 + HyDE**：在检索前把 query 修好；HyDE 用"假设答案"检索，缩小 query-doc 鸿沟。
- **多路召回 → 合并去重 → RRF 融合**：多 query × 多检索器，广撒网提召回。
- **元数据过滤**先按结构化条件缩范围再向量检索（提准 + 隔离/权限）。
- **Top-K 非越大越好**（噪音 + 超长 + lost-in-middle）；**阈值**过滤无关块防幻觉。
- 分工哲学：**检索求召回（别漏）→ Rerank 求精确（去粗）**。

## ❓ 高频面试 / 理解题

**Q：既然向量检索能理解语义，为什么还要保留关键词 BM25？混合检索到底强在哪？**
A：因为向量检索会"抹平"字面细节——把文本压成稠密向量时，**订单号、错误码、函数名、法条编号**这类靠精确字符匹配才对的东西容易被漏掉，它们语义信号弱、全靠字面命中。BM25 恰好强在字面精确匹配、弱在语义泛化，两者的**错误是互补的**：向量漏的精确词 BM25 能捞、BM25 漏的同义改写向量能补。合起来召回率明显高于任一单路，这就是 Hybrid Search 的价值。融合通常用 RRF——只看各路名次、不管量纲不同的原始分数，天然归一无需调参。

**Q：HyDE 是什么？为什么用"假设答案"去检索反而更准？**
A：HyDE（Hypothetical Document Embeddings）先让 LLM 针对问题生成一段**假设答案**，再用这段答案的向量去检索，而不是直接用问题检索。原理是：问题（疑问句）和目标文档（陈述性内容）在向量空间里往往离得远，存在 query-doc 语义鸿沟；假设答案哪怕内容有错，其**结构和用词更接近真正的目标文档**，相当于把检索起点挪到了"文档那一侧"，从而缩小鸿沟、提升召回准确度。代价是多一次 LLM 调用（延迟↑），且假设答案跑偏时可能引噪。

**Q：Top-K 是不是设得越大，RAG 越不容易漏答案？**
A：不是。K 太大有三个坏处：①**噪音块稀释信号**，相关内容被无关内容淹没；②**撑爆上下文**，成本上升；③**lost-in-the-middle**——LLM 对长上下文中段内容容易忽视。正确做法是解耦"召回"和"喂给 LLM"：**检索阶段召回较大的 N（求 recall），经 Rerank 精排后只把 Top-K（如 3~5）交给 LLM**，再配相似度阈值把明显无关的块丢掉，宁缺毋滥。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别只上纯向量检索就以为万事大吉**——线上一大类 badcase（查编号、查专有名词、查代码）都是向量漏召回导致的，加一路 BM25 混合检索往往立竿见影。
- ⚠️ **别用原始分数硬加权融合**：向量相似度和 BM25 分数量纲不可比，加权相加需要反复调参且脆弱；优先用 **RRF**（基于名次）更省心稳健。
- ✅ **先修 query 再怪检索器**：口语化、指代不清、复合意图的 query，先做改写/拆分/HyDE，常比换更强的 Embedding 模型收益大。
- ✅ **能过滤就先过滤**：时间、类型、租户、权限等结构化条件先缩范围，既提准提速又保证数据隔离——尤其多租户系统这是安全底线，不是可选项。
- ✅ **设相似度阈值兜底**：当知识库压根没有答案时，阈值让检索"敢于返回空"，避免硬凑无关块诱发幻觉——"没检索到"再走兜底话术，好过喂垃圾让模型编。
- ✅ **加分认知**：能说清"检索求召回、Rerank 求精确"的两阶段分工，以及"混合检索靠错误互补、RRF 靠名次归一"，比只会背名词更显理解本质。
