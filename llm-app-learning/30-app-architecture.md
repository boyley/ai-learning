# 30 · LLM 应用架构与落地（App Architecture）

> LLM 应用的本质是**把一个"慢、贵、不确定、会瞎编、不安全"的概率生成器，用一整套工程手段驯服成可靠的生产功能**；前面 29 篇讲的每个原理，最终都落在这一张分层生产架构图上。重要度 ⭐⭐⭐。

## 🎯 一句话核心

生产级 LLM 应用 = **编排层（怎么调）+ 能力层（调什么：LLM/RAG/工具）+ 数据层（喂什么：向量/知识/记忆）+ 治理层（怎么保证靠谱：护栏/评估/可观测/缓存/限流）**；Demo 只需要"能力层跑通一次"，生产难在**把治理层做扎实**——评估、护栏、可观测、成本、迭代，这五件事才是 Demo 到生产的真正鸿沟。

## 📖 核心原理

**LLM 应用不是"套个大模型 API"，而是一个以 LLM 为核心不确定组件的分布式系统。** 传统后端的每个依赖（数据库、下游服务）行为是确定的：同样输入同样输出、要么成功要么明确失败。LLM 恰恰相反——它**慢（秒级延迟）、贵（按 Token 计费且不便宜）、不确定（同输入不同输出）、会瞎编（幻觉，详见 [05-hallucination](05-hallucination.md)）、不安全（可被注入/越狱，详见 [10-prompt-security](10-prompt-security.md)）**。整个应用架构存在的理由，就是围绕这五个"毛病"叠加工程手段把它变可靠。这也是为什么本库前面所有篇章——RAG、评估、护栏、结构化输出、推理优化——本质上都是"某一种驯服手段"。

**分层的意义在于"关注点分离 + 可替换"。** 把系统切成接入层→编排层→能力层→数据层→治理层，好处是每一层都能独立演进：换个更便宜的模型只动能力层的路由；加一个知识库只动数据层；上线一道内容审核只动治理层。尤其要把**编排（怎么组织调用）和能力（具体调用什么）分开**——编排层沉淀 Prompt 模板、Agent 流程、工作流逻辑（详见 [22-agent-react](22-agent-react.md)、[23-agent-patterns](23-agent-patterns.md)），能力层是可插拔的 LLM 调用 / RAG 检索（[14-rag-overview](14-rag-overview.md)）/ 工具与 MCP（[20-function-calling](20-function-calling.md)、[21-mcp](21-mcp.md)）。这样"业务怎么编排"和"底层用什么模型/检索"解耦，模型日新月异时才不至于牵一发动全身。

**最关键的心智转变：把 LLM 当成一个"不可靠的外部依赖"来治理，而不是当成一个函数来调用。** 一旦这么看，后端高可用那一整套成熟手段（超时、重试、熔断、降级、限流、多活故障转移）就能直接复用——LLM 会超时（设超时 + 流式）、会限流报错（重试 + 退避）、会整体挂掉（熔断 + 兜底/缓存降级）、会烧钱（配额限流 + 分级路由）。**治理层就是把这套"依赖治理"叠加上 LLM 特有的"内容治理"（护栏 + 评估）。** 前者保证"系统不崩"，后者保证"输出可信"，两者缺一不可。

## 🔧 关键方法 / 流程 / 架构

**一、典型 LLM 应用分层架构（把全库定位到一张图上）：**

```
┌──────────────────────────────────────────────────────────────┐
│  ① 接入层  Web / App / API / IM机器人   （流式返回、鉴权、会话）│
└───────────────────────────────┬──────────────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────┐
│  ② 编排层  Orchestration                                       │
│   Prompt 管理(模板/版本) · Agent 编排(ReAct/多智能体) · 工作流   │
│   → 07 Prompt · 08 CoT · 22 Agent · 23 编排 · 24 多智能体       │
└───────────────────────────────┬──────────────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────┐
│  ③ 能力层  Capabilities（可插拔）                               │
│   LLM 调用(分级路由) · RAG 检索(召回+Rerank) · 工具/MCP          │
│   → 04 采样 · 09 结构化输出 · 14~19 RAG · 20 工具 · 21 MCP       │
└───────────────────────────────┬──────────────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────┐
│  ④ 数据层  Data                                                │
│   向量库 · 知识库/文档 · 记忆(短期会话/长期) · 语义缓存          │
│   → 11 Embedding · 12 相似度 · 13 向量库 · 15 分块 · 25 记忆     │
└───────────────────────────────┬──────────────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────┐
│  ⑤ 治理层  Governance（横切所有层，生产的胜负手）               │
│   护栏/审核 · 评估闭环 · 可观测(Token/成本/延迟/trace)           │
│   缓存 · 限流/配额 · 熔断降级 · 故障转移                         │
│   → 10 注入防护 · 26 评估 · 27 护栏 · 29 推理优化               │
└──────────────────────────────────────────────────────────────┘
```

> 一句话读图：**上面三层是"业务链路"（怎么把用户请求变成一次可靠的模型调用），第④层是"喂料"，第⑤层横切一切、决定这套东西能不能上生产。**

**二、五大工程挑战 × 治理手段（本库贯穿始终的主线，核心表格）：**

| 挑战 | 根因 | 治理手段 | 对应篇 |
|---|---|---|---|
| **慢**（秒级延迟） | 自回归逐 Token 生成 | **流式**返回(先出字)、**异步**任务化、**缓存**命中直接返、精简上下文 | [29-inference-optimization](29-inference-optimization.md)、[06-context-engineering](06-context-engineering.md) |
| **贵**（按 Token 计费） | 长上下文 + 大模型 | **缓存** + **分级路由**(简单问题走小模型) + **精简**上下文 + **限**输出长度 + 监控告警 | [29-inference-optimization](29-inference-optimization.md) |
| **不确定**（同输入异输出） | 采样随机性 | **降温度** + **结构化输出**(JSON schema) + **解析校验** + **失败重试** | [09-structured-output](09-structured-output.md)、[04-sampling-decoding](04-sampling-decoding.md) |
| **会瞎编**（幻觉） | 概率续写本质 | **RAG**(给依据+溯源) + **评估**(faithfulness 兜底) + 提示"不知道就说不知道" | [14-rag-overview](14-rag-overview.md)、[05-hallucination](05-hallucination.md)、[26-llm-evaluation](26-llm-evaluation.md) |
| **不安全**（注入/越狱/越权） | 指令与数据不分、输出不可控 | **护栏**(输入输出双向审核) + **注入防护**(指令数据隔离) + 权限最小化 + PII 脱敏 | [27-safety-guardrails](27-safety-guardrails.md)、[10-prompt-security](10-prompt-security.md) |

> 这张表就是本库的"主线索引"——每一篇原理，本质都在解决这五个问题中的某一个。

**三、把 LLM 当外部依赖治理（复用后端高可用那套）：**

```
一次 LLM 调用要包裹的可靠性护甲：
  超时(timeout)      → 设合理超时 + 流式，别让一个卡死请求拖垮线程池
  重试(retry)        → 429/5xx 指数退避重试；注意幂等与重复计费
  熔断(circuit break)→ 错误率飙升即熔断，避免雪崩、避免烧钱
  降级(fallback)     → 模型挂了返回:缓存结果 / 规则兜底 / "服务繁忙"友好提示
  限流(rate limit)   → 按 RPM/TPM 配额限流，保护下游模型额度、防单用户刷爆
  故障转移(failover) → 主模型不可用→自动切备用模型/备用厂商(多模型冗余)
```

**四、可观测性闭环（AI 应用的"三大件 + 评估"）：**

```
指标(Metrics)  : Token用量 · 成本($) · 延迟(P50/P95/TTFT) · 成功率 · 缓存命中率
链路(Trace)    : 一次请求全链路——Prompt→检索命中了哪些块→模型输出→工具调用→护栏
                 (Agent/RAG 是多步链路，没有 trace 出了问题根本无法定位)
日志(Logs)     : 完整 Prompt/响应留存(可回放、可复盘 badcase)
评估闭环(Eval) : 线上采样 badcase → 进金标准集 → 回归评估 → 优化 → 再上线
                 → 26-llm-evaluation
```

**五、成本控制成体系（五招组合拳，不是单点优化）：**

```
① 缓存    : 精确缓存 + 语义缓存(相似问题命中历史答案)——省钱最快见效
② 分级路由: 意图/难度分级，简单走小模型/便宜模型，难的才上旗舰模型
③ 精简    : 压缩上下文、只喂 Top-K 相关块、去掉冗余历史(Lost in the Middle 也更好)
④ 限输出  : max_tokens 上限、要点式回答，输出 Token 往往比输入更贵
⑤ 监控告警: 按用户/接口维度统计成本，设预算阈值告警，抓异常烧钱
```

## 🔑 要点速记

- LLM 应用五层：**接入 → 编排 → 能力 → 数据 → 治理**；前三层是业务链路，第④层喂料，第⑤层横切定生死。
- **编排与能力解耦**：业务流程沉淀在编排层，模型/检索可插拔在能力层——换模型不动业务。
- 生产化五大挑战 = **慢 / 贵 / 不确定 / 会瞎编 / 不安全**，分别对应 流式缓存 / 分级路由 / 结构化+重试 / RAG+评估 / 护栏+注入防护。
- **把 LLM 当不可靠外部依赖**：超时、重试、熔断、降级、限流、多模型故障转移——后端高可用那套直接复用。
- 治理 = **依赖治理（系统不崩）+ 内容治理（输出可信）**，缺一不可。
- 可观测三大件 + 评估闭环：**Token/成本/延迟/成功率 + 全链路 trace + badcase 回归**；Agent/RAG 多步链路没 trace 无法排障。
- 成本是体系工程：**缓存 + 分级路由 + 精简上下文 + 限输出 + 监控告警**五招组合。
- **Demo 到生产的鸿沟 = 评估 + 护栏 + 可观测 + 成本 + 迭代**——能力层跑通只是起点。

## ❓ 高频面试 / 理解题

**Q：一个生产级 LLM 应用和一个 Demo 差在哪？为什么"Demo 好做、生产难"？**
A：Demo 只需要能力层跑通一次——调个模型、接个 RAG，效果看着惊艳就行。生产难在**治理层**：①**评估**——没有量化评估的 AI 应用是玄学，改 Prompt 是好是坏说不清；②**护栏**——要防注入越狱、内容合规、PII 泄露；③**可观测**——多步链路出了问题要能定位（trace）、成本延迟要能监控；④**成本**——Token 烧钱，要缓存+分级路由+限流控住；⑤**迭代**——线上 badcase 要能回流成评估集持续优化。这五件事都是"隐形工程量"，恰恰是 Demo 阶段看不到、生产阶段绕不过的鸿沟。

**Q：LLM 又慢又贵又会挂，怎么保证线上服务的可用性和响应体验？**
A：把它当**不可靠的外部依赖**来治理，复用后端高可用那套：**超时+流式**（先出字，避免卡死体验和线程占用）、**重试+退避**（应对 429/5xx）、**熔断+降级**（模型挂了返回缓存或规则兜底，而不是整个功能崩）、**限流**（按 RPM/TPM 配额保护额度、防刷）、**多模型故障转移**（主模型不可用切备用厂商）。响应体验主要靠**流式 + 语义缓存 + 分级路由**：先流式让用户马上看到内容，能命中缓存的直接返，简单请求走小模型降延迟。

**Q：LLM 应用的成本怎么系统性地控制？**
A：单点优化不够，要成体系五招组合：①**缓存**（精确+语义缓存，相似问题命中历史答案，最快见效）；②**分级路由**（按难度把简单请求分流到小模型/便宜模型，只有难任务上旗舰模型）；③**精简上下文**（只喂 Top-K 相关块、压缩历史，顺带缓解 Lost in the Middle）；④**限输出**（max_tokens 上限，输出 Token 通常比输入贵）；⑤**监控告警**（按用户/接口维度统计成本、设预算阈值抓异常烧钱）。核心思想：**别用大炮打蚊子，也别把整个知识库都塞进上下文。**

**Q：为什么强调"编排层和能力层要分开"？**
A：因为模型和检索方案变化极快，而业务编排逻辑相对稳定。把"怎么编排"（Prompt 模板、Agent 流程、工作流）和"用什么"（哪个模型、哪种 RAG）解耦后，换更便宜的模型只动路由配置、加个知识库只动数据层、上线内容审核只动治理层，互不牵连。反面教材是把 Prompt、模型选择、业务逻辑全揉在一坨代码里，换模型时全线重写。这就是分层架构"关注点分离 + 可替换"的价值。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别把 LLM 当确定性函数直接裸调**——不包超时/重试/降级，一次模型抖动就能拖垮整个接口；把它当外部依赖套上可靠性护甲是底线。
- ⚠️ **没有评估就别谈优化**——改了 Prompt / 换了模型是变好还是变坏，靠"感觉"永远说不清；先建金标准集和回归评估（[26-llm-evaluation](26-llm-evaluation.md)），再迭代。
- ⚠️ **Agent/RAG 多步链路一定要上全链路 trace**——出了问题要能看到"检索命中了哪些块、模型每步输出了啥、哪步跑偏"，否则线上排障两眼一抹黑。
- ✅ **护栏要输入输出双向做**：入口挡注入/越权，出口挡有害内容/PII 泄露/幻觉（[27-safety-guardrails](27-safety-guardrails.md)、[10-prompt-security](10-prompt-security.md)）；只做一头等于没做。
- ✅ **缓存优先级最高**：语义缓存对成本和延迟都是立竿见影的收益，很多重复/相似问题根本不用真调模型。
- ✅ **加分认知**：能把"慢/贵/不确定/会瞎编/不安全"五个挑战和治理手段一一对应说清，就等于把全库串成了一张生产架构图——这才是从"会用大模型"到"会做大模型系统"的分水岭。
