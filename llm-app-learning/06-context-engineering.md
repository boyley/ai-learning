# 06 · 上下文工程（Context Engineering）

> LLM 是"无状态的续写器"，它对世界的全部认知只来自**当次调用塞进上下文窗口的那些 Token**；系统性地决定"放什么、怎么排、放多少"，就是上下文工程——它比 Prompt 措辞更宏观，是决定 LLM 应用质量上限的关键工程。重要度 ⭐⭐⭐。

## 🎯 一句话核心

模型不"记得"任何东西，它每次只看到你这一次喂进去的上下文——所以**决定 LLM 表现的不只是"话怎么说"（Prompt），而是"给它看的全部信息（指令+示例+检索资料+历史+工具结果）怎么组织"**。上下文工程就是把有限、昂贵、还会"看中间走神"的上下文窗口，用成一块**信噪比最高**的工作内存。

## 📖 核心原理

**先理解硬约束：上下文窗口（Context Window）。** LLM 一次调用能处理的 Token 数有上限，这个上限叫上下文窗口，且它是**输入 + 输出合计**——你塞进去的 system 指令、对话历史、检索资料、用户问题，加上模型要生成的回答，全部挤在同一个额度里（Token 是什么、为什么按 Token 计费详见 [03-token-tokenization](03-token-tokenization.md)）。超出窗口的部分会被**截断**（通常砍掉最早的内容），一旦被截断，模型就"看不见"那段信息，表现得像从没提供过。窗口是**每次调用独立**的：LLM 本身无记忆（[01-llm-overview](01-llm-overview.md)），多轮对话之所以"记得"，纯粹是应用层每轮把历史重新拼进上下文——记忆是工程造出来的假象。

**为什么"上下文工程"这个说法在 2024–2025 兴起？** 早期大家谈"Prompt 工程"，聚焦**一句指令怎么措辞**（角色、口吻、few-shot）。但真实应用里，喂给模型的远不止那句指令：还有 RAG 检索回来的资料、几十轮对话历史、工具/函数返回的 JSON、系统级约束……这些内容的**选择、裁剪、排序、压缩**，对结果的影响往往**大于**指令本身怎么写。于是业界把视角放大，提出"上下文工程"——**系统性地组织喂给模型的全部上下文**，把它当成给模型现场配置的一块"工作内存"来设计。一句话对比：**Prompt 工程管"怎么说"，上下文工程管"给它看什么、看到的怎么组织"**，后者是前者的超集。

**关键认知：窗口不是越大越好，注意力也不是均匀的。** 两个反直觉但必须内化的事实：

1. **Lost in the Middle（中间迷失）**：实验反复证明，把关键信息放在长上下文的**中间**，模型很容易忽略它；放在**开头或结尾**才最被"注意到"。这是注意力机制在长序列上的固有偏置，不是 bug。
2. **越大越贵、越慢、越吵**：窗口翻倍，费用和延迟大致跟着涨（按 Token 计费）；更要命的是，塞进无关内容会**稀释注意力**、引入**噪音与干扰**，甚至让相互矛盾的信息**互相污染**，反而拉低正确率。

所以上下文工程的核心信条是：**不是把能塞的都塞进去，而是精选出最相关的、按最优顺序排布**——这正是 RAG（只检索相关片段而非灌全库，[14-rag-overview](14-rag-overview.md)）和"历史压缩"这类技术存在的根本理由。

## 🔧 关键方法 / 流程 / 架构

**一次 LLM 调用的上下文由多个"块"拼成，各块有不同优先级与排布策略：**

```
┌──────────────────── 上下文窗口（输入+输出共享一个额度）────────────────────┐
│                                                                          │
│  ① System 指令 / 角色 / 规则        ← 放最前：全局约束，最需被"看到"          │
│  ─────────────────────────────                                           │
│  ② Few-shot 示例（可选）            ← 教格式/风格，示例精而少                 │
│  ─────────────────────────────                                           │
│  ③ RAG 检索片段 / 工具输出          ← 动态知识；重排后"最相关的放两端"          │
│  ─────────────────────────────         （对抗 Lost in the Middle）        │
│  ④ 对话历史 / 记忆                   ← 会膨胀：需滑动窗口 / 摘要压缩            │
│  ─────────────────────────────                                           │
│  ⑤ 当前用户问题 + 输出指令           ← 放最后（最靠近生成，注意力最强）         │
│  ─────────────────────────────                                           │
│  ⑥ ↓↓ 模型生成的回答（也占额度）↓↓                                          │
└──────────────────────────────────────────────────────────────────────────┘
   排布铁律：最关键的信息放【开头】或【结尾】，别埋在中间。
```

**四类核心问题与对策（上下文工程的日常）：**

| 问题 | 现象 | 对策 |
|---|---|---|
| **Lost in the Middle** | 长上下文中间的信息被忽略 | 关键内容放开头/结尾；检索结果先 Rerank 再把最相关的排两端 |
| **窗口不是越大越好** | 越大越贵越慢；噪音稀释注意力 | 只放相关的——用 RAG 检索精选片段（[14-rag-overview](14-rag-overview.md)），不灌全文 |
| **多轮历史膨胀** | 对话越长越接近窗口上限、越贵 | ①滑动窗口只留最近 N 轮 ②摘要压缩早期历史 ③关键信息外置到记忆库按需取回 |
| **上下文冲突/污染** | 矛盾/无关内容互相干扰、误导生成 | 剔无关、去重、标注来源；指令与外部数据显式隔离，注明"以下资料仅供参考" |

**多轮对话历史的三种压缩策略（最常见的膨胀治理）：**

```
原始历史：[轮1][轮2][轮3]...[轮N]  ← 越拼越长，终将撞上窗口 + 每轮重算全部历史 → 贵

① 滑动窗口：      丢弃 ── 只保留 ─► [轮N-2][轮N-1][轮N]   最简单，但会"忘"早期关键事实
② 摘要压缩：  [前 N-3 轮的摘要] + [轮N-2][轮N-1][轮N]     省 Token 又保信息，需额外一次 LLM 调用
③ 关键信息外置：[记忆库检索到的相关片段] + [最近几轮]      长期记忆的做法（详见 25）
```

> 这三条正是 Agent"记忆"的工程基础——短期记忆=窗口内历史管理，长期记忆=外置检索，详见 [25-agent-memory-planning](25-agent-memory-planning.md)。

## 🔑 要点速记

- **上下文窗口** = 一次调用能处理的最大 Token，**输入+输出合计**共享；超出被**截断**（多砍最早内容）。
- LLM **无状态无记忆**，多轮"记得"是应用层每轮重传历史造出来的——记忆是工程假象。
- **上下文工程 ⊃ Prompt 工程**：前者管"给模型看的全部信息怎么组织"，后者只管"指令怎么措辞"。
- **Lost in the Middle**：长上下文中间信息易被忽略 → 关键内容放**开头/结尾**。
- **窗口不是越大越好**：越大越贵越慢，噪音稀释注意力、矛盾内容互相污染 → **只放相关的**。
- 上下文六块排布：system 指令(前) → few-shot → RAG/工具输出(重排后两端) → 历史/记忆 → 用户问题(后)。
- 历史膨胀三招：**滑动窗口 / 摘要压缩 / 关键信息外置**。
- 上下文冲突/污染：剔无关、去重、标来源、**指令与数据隔离**。

## ❓ 高频面试 / 理解题

**Q：上下文工程和 Prompt 工程有什么区别？**
A：Prompt 工程聚焦**单条指令怎么措辞**（角色、口吻、few-shot 示例、输出格式，详见 [07-prompt-basics](07-prompt-basics.md)）；上下文工程是它的**超集**，管的是喂给模型的**全部上下文**——system 指令 + 示例 + RAG 检索资料 + 对话历史 + 工具返回结果——怎么**选择、裁剪、排序、压缩**。真实应用里后者对结果的影响常大于指令措辞：同一个 Prompt，检索到对的资料就答对、检索到噪音就答错。一句话：Prompt 管"怎么说"，上下文工程管"给它看什么、看到的怎么组织"。

**Q：既然模型上下文窗口越来越大，是不是把所有资料一股脑塞进去就行，不用 RAG 了？**
A：不行，三个原因：①**Lost in the Middle**——塞进长上下文中间的信息模型容易忽略，召回≠被用到；②**贵且慢**——窗口按 Token 计费，塞满全库每次调用成本和延迟都爆炸；③**噪音污染**——无关和矛盾内容会稀释注意力、误导生成，反而降低正确率。所以正解仍是 RAG：**只检索最相关的片段**喂进去，把宝贵的窗口用在信噪比最高的内容上（[14-rag-overview](14-rag-overview.md)）。

**Q：多轮对话越聊越长，怎么防止撞上上下文窗口上限？**
A：因为 LLM 无记忆，每轮都要把历史重新拼进上下文，历史线性增长早晚撞顶、且每轮都为全部历史重复付费。三种压缩：①**滑动窗口**只留最近 N 轮（简单但会忘早期关键事实）；②**摘要压缩**把早期历史用 LLM 概括成摘要 + 保留最近几轮（省 Token 又留信息）；③**关键信息外置**到记忆库，按需检索取回相关片段（长期记忆做法，[25-agent-memory-planning](25-agent-memory-planning.md)）。生产中常组合使用。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别忘了输出也占窗口额度**：输入几乎塞满窗口会导致回答被压缩甚至截断——预留足够的输出空间。
- ⚠️ **别把关键信息埋在长上下文中间**：受 Lost in the Middle 影响易被忽略；检索结果先 Rerank，把最相关的放**开头或结尾**。
- ⚠️ **别迷信"大窗口=可以偷懒"**：无关内容会稀释注意力、引入矛盾污染，多塞常常越塞越差——**相关性 > 数量**。
- ✅ **指令与外部数据显式隔离**：把 RAG 片段、工具输出等"数据"和"你要做什么"的"指令"分区标注（如"以下为参考资料，仅供引用"），既降污染又是抵御 Prompt 注入的基础。
- ✅ **上下文可观测**：把每次实际拼出的完整上下文打日志。应用出错时，十有八九是"喂进去的东西不对"（检索到噪音、历史被截断、格式错乱），而不是模型笨。
- ✅ **加分认知**：能说清"LLM 无记忆、上下文是唯一工作内存，所以 RAG、历史压缩、Agent 记忆本质都是上下文工程的子问题"，比只会背 Prompt 技巧更显系统理解。
