# 03 · Token 与分词（Token & Tokenization）

> Token 是模型处理文本的**最小单位**——不是字也不是词，而是"子词（subword）片段"；模型眼里根本没有文字，只有一串 **Token ID（整数）**。理解 Token 直接关系到**计费、上下文窗口、延迟**三件工程大事。重要度 ⭐⭐⭐。

## 🎯 一句话核心

大模型不"读字"，它把文本先切成一片片 **Token**（子词碎片），再把每个 Token 映射成一个整数 **ID** 送进网络——所以你关心的**花多少钱、塞不塞得下、跑多快**，本质上全是在数 **Token 数量**，而不是数字数或词数。

## 📖 核心原理

**Token 是"文本 → 模型输入"的原子单位，但它既不是字符也不是完整单词，而是介于两者之间的"子词片段"。** 模型内部维护一张固定大小的**词表（vocabulary）**（常见 3 万～20 万条），表里每一项是一个子词（如 `token`、`##ization`、`的`、` def`）。文本进来时，分词器（tokenizer）按这张表把它切成若干已知片段，再查表把每个片段换成对应的整数 **ID**。**模型从头到尾只在跟这串整数打交道**——它先把每个 ID 变成向量（embedding），再做自回归预测下一个 Token 的 ID，最后解码回文本。所以"字"和"词"是人类的概念，Token 才是模型的计量单位。

**为什么用"子词"，而不是直接按字符或按单词切？** 这是在**词表大小**和**覆盖能力**之间做权衡：
- **按整词切**：词表会爆炸（英文几十万词还不够，加上时态、拼写变体、多语言），而且遇到没见过的词（未登录词 OOV, out-of-vocabulary）就彻底歇菜，只能吐一个 `[UNK]`。
- **按单字符切**：词表极小，永不 OOV，但一个词被拆成十几个 Token，序列变长、语义被打碎，模型学得费劲、算得也慢。
- **子词是折中**：高频的完整词（`the`、`hello`）保留成一个 Token；低频/没见过的词拆成更小的已知片段（`tokenization` → `token` + `ization`，`ChatGPT` → `Chat` + `G` + `PT`）。这样**任何输入都能被表示**（哪怕生僻词、拼错的词、新造词、任意语言），词表又不至于失控。

**子词是怎么"学"出来的——以 BPE（Byte Pair Encoding，字节对编码）为例。** BPE 的直觉极简：**从最细的粒度开始，不断把"最高频相邻组合"合并成一个新 Token**。初始时每个字符（或字节）各自为一个 Token；统计语料中相邻 Token 对出现的频率，把出现最多的那一对（如 `t`+`h` → `th`）合并成一个新单元，加进词表；反复合并到词表达到预设大小为止。结果就是：**高频组合自然长成一个 Token，低频组合仍是碎片**——这正好匹配"常见词省 Token、生僻词多切几刀"的需求。现代分词器（GPT 用的 BPE、以及 WordPiece、Unigram、SentencePiece 等变体）思路一致，且多在**字节层面**做（byte-level BPE），因此能无损覆盖任意 Unicode 字符（中日韩、emoji、代码符号都不会 OOV）。

**同一段文本，Token 数取决于分词器，不同模型可能不同。** 词表和合并规则是训练时定死的，属于模型的一部分。因此**换模型就换分词器**，同一句话在 GPT、Claude、Qwen 上切出的 Token 数可以不一样——估算成本和上下文占用时，务必用**目标模型自己的分词器**去数。

## 🔧 关键方法 / 流程 / 架构

**从文本到 Token ID 再回到文本（模型眼中的全过程）：**

```
"分词很重要"  ← 人看到的是字
   │  ① 分词 Tokenize：按词表切成子词片段
   ▼
["分", "词", "很", "重要"]        （示意，实际切法由分词器词表决定）
   │  ② 查表映射成整数 ID
   ▼
[15234, 8901, 771, 20356]        ← 模型真正的输入
   │  ③ 每个 ID → embedding 向量 → Transformer 自回归生成下一个 ID …
   ▼
[…新的 Token ID…]  ── ④ 解码 detokenize ──▶  "……"（人看到的输出）
```

**一句英文的直观切分**（子词边界示意，`·` 表示一个 Token 分界）：

```
文本:  "Tokenization isn't hard!"
切分:   Token · ization ·  isn · 't ·  hard · !
说明:  高频词 "isn" 完整保留；生僻长词 "Tokenization" 拆成 "Token"+"ization"；
       标点 "!"、缩写 "'t" 各占一个 Token；单词前的空格常并入下一个 Token。
→ 6 个 Token，而人眼只看到 3 个"单词"。
```

**Token 数的换算经验（估算用，非精确）：**

| 文本类型 | 经验换算 | 说明 |
|---|---|---|
| 英文 | 1 词 ≈ 1~1.5 Token | 常见短词 1 个，长词/生僻词拆多个 |
| 中文 | 1 字 ≈ 1~2 Token | 常用字多为 1 个，生僻字按字节拆成多个 |
| 代码 | 偏多 | 缩进、括号、符号、驼峰命名都各占 Token |
| 标点 / 空格 / emoji | 都算 Token | 不是"免费"的，同样计入计费和窗口 |

> 一个好记的粗估：英文约 **1 Token ≈ 4 个字符 ≈ 0.75 词**；中文更"贵"，一段中文的 Token 数常和字数同量级甚至更多。

**Token 决定的三件工程大事（这是本篇的核心落点）：**

```
                       ┌─────────────────────────────────────────┐
   输入文本 ──分词──▶  │  Token 数 = N_in                          │
                       └───────────────┬─────────────────────────┘
                                       │
        ┌──────────────────────────────┼──────────────────────────────┐
        ▼                              ▼                               ▼
 ① 计费 Cost                    ② 上下文窗口 Context Window      ③ 延迟 Latency
 按 (N_in + N_out) 收费          N_in + N_out ≤ 窗口上限          输出逐 Token 生成
 输出通常比输入更贵              超了就截断/报错                  N_out 越大越慢
 → 省 Token = 省钱               → 塞不下要裁剪（06）             → 自回归特性（04）
```

- **① 计费**：主流 API 按 **输入 Token + 输出 Token** 之和计价，且**输出 Token 单价通常明显高于输入**（生成比读取更耗算力）。省钱的本质就是省 Token。
- **② 上下文窗口（Context Window）**：模型一次能"看见"的 Token 总量有硬上限（如 8K、32K、**128K**、乃至百万级）。**输入 + 输出必须一起塞进这个窗口**；超了就会被截断或直接报错，历史对话、检索到的文档、系统提示全都在抢这份预算。怎么在有限窗口里放最该放的内容，是**上下文工程**要解决的（详见 [06-context-engineering](06-context-engineering.md)）。
- **③ 延迟（Latency）**：模型是**自回归逐 Token 生成**的——一次前向只吐一个 Token，再把它接回去预测下一个，循环往复。所以**输出 Token 越多，响应越慢**（首 Token 延迟 + 每 Token 的生成时间叠加）；输入长也会拖慢首 Token。这一逐 Token 的生成机制详见 [04-sampling-decoding](04-sampling-decoding.md)。

**工程影响：省钱省延迟 = 省 Token。** 三个常用手段：
- **RAG 只塞相关内容**：别把整篇文档灌进去，检索出真正相关的片段再喂（详见 [06-context-engineering](06-context-engineering.md)）。
- **精简 Prompt**：去掉冗余的客套、重复的说明；同样的意思用更少的 Token 表达。
- **限制 `max_tokens`**：给输出设上限，既控成本又控延迟，避免模型啰嗦或跑飞。

## 🔑 要点速记

- **Token 是模型的最小处理单位**，是"子词片段"，**不是字、不是词**；模型只认 **Token ID（整数）**，不认文字。
- 用**子词**是在**词表大小 vs 覆盖能力**间折中：高频词整体成 1 个 Token，生僻/未登录词拆成小片段，从而**永不 OOV**、还能跨语言。
- **BPE** 直觉：从字符起步，**反复把最高频相邻组合合并成新 Token**，直到词表达标——高频组合自然变长、变省。
- 换算：**英文 1 词 ≈ 1~1.5 Token，中文 1 字 ≈ 1~2 Token**；代码、标点、空格、emoji 都占 Token。
- **Token 决定三件事**：① 计费（输入+输出，输出更贵）② 上下文窗口上限（塞不下就截断）③ 延迟（输出越多越慢，因自回归逐 Token 生成）。
- **上下文窗口（Context Window）**：一次能看见的 Token 总量上限（如 128K），输入+输出共用这份预算。
- **省钱 = 省 Token**：RAG 只塞相关、精简 Prompt、限 `max_tokens`。
- **不同模型分词器不同，同一段文本 Token 数可能不同**——估算务必用目标模型自己的分词器。

## ❓ 高频面试 / 理解题

**Q：Token 到底是什么？和字、词有什么区别？**
A：Token 是模型处理文本的**最小单位**，是介于字符和单词之间的**子词片段**（subword）。分词器按一张固定词表把文本切成这些片段，再映射成整数 **ID**——模型内部从头到尾只处理这串整数，根本"看不见"文字。所以一个英文长词可能是多个 Token，一个中文字也可能占 1~2 个 Token，不能简单按字数或词数来数。

**Q：为什么用子词分词（BPE），而不是按整词或按字符切？**
A：整词切会导致词表爆炸，且遇到没见过的词（OOV）就废了；单字符切词表虽小但序列太长、语义破碎、又慢。子词是折中：高频完整词保留成 1 个 Token，低频/生僻/新词拆成已知小片段，从而**任意输入都能表示、永不 OOV、还能跨语言**，词表规模又可控。BPE 的做法是从字符起步不断合并最高频的相邻组合，让常见组合自然长成一个 Token。

**Q：为什么说"省钱、控延迟、防截断"本质都是在管 Token？**
A：因为这三件事全按 Token 计量：① 计费按输入+输出 Token 数（输出通常更贵）；② 上下文窗口是 Token 总量的硬上限，输入+输出共用，超了就截断；③ 模型自回归逐 Token 生成，输出 Token 越多越慢。所以优化手段殊途同归——RAG 只塞相关内容、精简 Prompt、限制 `max_tokens`，都是在少花 Token。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别用字数/词数估成本或窗口占用**——要用**目标模型自己的分词器**去数 Token；同一段文本在不同模型上 Token 数可能不同，跨模型迁移时要重新核算。
- ⚠️ **别忽略输出 Token**：上下文窗口是"输入+输出"共用的预算，且输出单价通常更贵。留足输出空间，别把窗口用输入塞满导致回答被截断。
- ⚠️ **中文和代码比想象中"贵"**：中文常和字数同量级甚至更多 Token，代码里的缩进、符号、驼峰命名都在吃 Token，估算时别按英文经验打折。
- ✅ **默认设 `max_tokens`**：既是省钱和控延迟的开关，也能防止模型跑飞输出一大段。配合精简 Prompt、RAG 只塞相关片段，是最直接的降本三板斧。
- ✅ **加分认知**：能说清"计费/窗口/延迟三件事都归结到 Token 数"，并把延迟归因到"自回归逐 Token 生成"（[04-sampling-decoding](04-sampling-decoding.md)），比只知道"Token 是分词结果"更显理解本质。
