# 09 · 结构化输出与约束（Structured Output）

> 让 LLM 稳定吐出**机器可解析的结构**（JSON / 枚举 / schema），而非自由文本，是"把模型接进代码"的必经工程；手段从"Prompt 求它"到"约束解码逼它"层层加强。重要度 ⭐⭐。

## 🎯 一句话核心

应用要把模型输出灌进代码、数据库或下游函数，就必须要**稳定、可反序列化、符合预定 schema 的结构**——而 LLM 本质是"续写自由文本"（详见 [01-llm-overview](01-llm-overview.md)），二者天然冲突；结构化输出就是用**从弱（Prompt 求它守约）到强（约束解码逼它合法）** 的一系列手段，把概率续写"钳"成合法结构。

## 📖 核心原理

**为什么需要结构化输出？** LLM 的默认产物是**自由文本**，对人友好、对代码灾难。一旦你要把结果 `json.loads()` 进程序、写入数据库字段、或当作下游函数的参数，就需要它**每次都返回同一种结构**：字段名固定、类型正确、枚举值合法、能被反序列化。自由文本里夹带 `"当然！这是您要的结果："`、Markdown 代码块围栏、多余解释、字段漏填、把 `true` 写成 `"是"`——任何一处都会让解析崩掉。**结构化输出的目标，就是把"不确定的续写"约束成"确定可解析的数据契约"。**

**实现分层：从"求它"到"逼它"（弱 → 强）。** 关键差别在于**约束发生在哪一层**——是靠 Prompt 里的自然语言"请求"，还是靠解码算法在采样时"物理封死"非法路径：

| 层级 | 手段 | 约束在哪 | 保证强度 |
|---|---|---|---|
| ① | **Prompt 要求返回 JSON + 附 schema/示例** | 自然语言请求 | 最弱，可能不守约（多话、缺字段、非法格式） |
| ② | **few-shot 示例** | 用例子暗示格式 | 稍强，靠模仿，仍无硬保证 |
| ③ | **JSON mode / 强制 JSON** | 解码期保证语法合法 | 保证是合法 JSON，但**不保证符合你的 schema** |
| ④ | **Structured Outputs / 约束解码（constrained decoding）** | 采样每一步按 schema 屏蔽非法 Token | 最强，**保证符合结构**（字段、类型、枚举都对） |
| ⑤ | **Function / Tool Calling 的参数 schema** | 借工具调用的参数定义拿结构 | 强（底层多为约束解码），详见 [20-function-calling](20-function-calling.md) |

> 关键区分：**JSON mode ≠ Structured Outputs**。前者只保证"是一段能解析的 JSON"（语法层），后者保证"是符合你给定 schema 的 JSON"（结构层）——字段名、必填、类型、`enum` 取值都被强制。生产里要接代码，你要的通常是后者。

**约束解码（constrained decoding）原理——为什么能"保证"。** 回忆 LLM 每步在整个词表上算一个概率分布，然后采样一个 Token。约束解码在这一步插入一个**语法/schema 状态机**：根据"已经生成到 JSON 的哪个位置"，计算出**当前唯一合法的 Token 集合**，把所有非法 Token 的概率**置零（mask 掉）**，只在合法集合里采样。例如刚输出 `{"age":` 之后，schema 说 `age` 是整数，那么下一步只允许数字 Token，字母、引号全被屏蔽——模型**在物理上无法**生成非法结构。这也叫 grammar-constrained decoding（用形式文法 / 正则 / JSON Schema 编译成状态机）。代价是要把 schema 编译成状态机、每步做 mask，有一定开销，且过强的约束可能轻微扭曲模型原本的语言分布。

**工程闭环：约束再强，也要"解析 + 校验 + 重试"兜底。** 现实中你可能用的是只有 ①②③ 的弱手段（很多自托管/老模型不支持约束解码），即便用了 ④，也可能遇到**截断（超 `max_tokens`）、空字段、业务级非法值**（格式合法但语义越界，如日期 `2026-13-40`）。所以工程上必须闭环：**输出 → 反序列化 → 用 Pydantic / JSON Schema 校验 → 失败则把错误信息塞回 Prompt 让模型重试（self-repair）**。绝不能盲信"模型这次一定合法"。

## 🔧 关键方法 / 流程 / 架构

**自由文本 → schema 约束 JSON（一个信息抽取示例）：**

```
输入自由文本：
  "帮我记一下，张伟，34 岁，高级工程师，邮箱 zhangwei@corp.com，在职。"

期望 schema（用 JSON Schema / Pydantic 描述数据契约）：
  {
    "name":   string,
    "age":    integer,
    "title":  string,
    "email":  string,
    "status": enum["active","inactive"]   ← 枚举，只能取这两个值
  }

──① 弱：Prompt 求它 ────────────────────────────────
  "抽取为 JSON，字段 name/age/title/email/status，
   status 只能是 active 或 inactive，不要多余解释。"
  → 可能翻车："当然！\n```json\n{...}\n```" （多话+围栏，解析失败）

──④ 强：约束解码 / Structured Outputs ───────────────
  把上面的 schema 作为 response_format 传给模型，
  解码时逐 Token 按 schema 屏蔽非法项：
  → 稳定得到：
  {"name":"张伟","age":34,"title":"高级工程师",
   "email":"zhangwei@corp.com","status":"active"}
  age 位置只允许数字、status 位置只允许两个枚举串。
```

**生产闭环流程（无论用哪一层都要套上）：**

```
Prompt(+schema) ──► LLM ──► 原始输出
                              │
                              ▼
                    反序列化 json.loads
                              │  失败？
              ┌───────────────┴───────────────┐
              ▼ 成功                            ▼ 失败
       Pydantic / JSON Schema 校验        把错误信息回填 Prompt
       （类型/必填/枚举/业务规则）         "上次输出非法：<err>，请修正"
              │  不通过？───────────────────────►│  重试(限次数,如 3)
              ▼ 通过                             │
        交给下游代码/DB/函数            超次数 → 兜底(报错/降级/人工)
```

**四类典型应用：**

| 应用 | 结构化点 | 例子 |
|---|---|---|
| 信息抽取 | 非结构文本 → 固定字段对象 | 简历/合同/工单抽字段 |
| 分类打标 | 返回**枚举**而非一句话 | 情感 `positive/negative/neutral` |
| 表单填充 | 对话内容 → 表单 JSON | 客服对话自动填工单 |
| Agent 参数 | 模型决策 → 工具入参 | Function Calling 的 arguments（[20-function-calling](20-function-calling.md)） |

## 🔑 要点速记

- 结构化输出目的：把"自由文本续写"钳成**可反序列化、符合 schema 的数据契约**，才能接代码/DB/函数。
- 手段五层由弱到强：**Prompt 求它 → few-shot → JSON mode → 约束解码 / Structured Outputs → Function Calling 参数 schema**。
- **JSON mode ≠ Structured Outputs**：前者保证"合法 JSON"（语法），后者保证"符合你的 schema"（结构、枚举、类型）。
- **约束解码原理**：解码每步按 schema 状态机**屏蔽非法 Token**，只在合法集合里采样，物理上无法生成非法结构。
- **工程闭环必做**：反序列化 + Pydantic / JSON Schema 校验 + 失败回填错误重试（self-repair），不盲信一次合法。
- 分类任务用**枚举**约束返回值，抽取任务用**对象 schema**——比让它"说一句话"稳得多。
- 复杂/深嵌套 schema 成功率与稳定性下降；**温度调低**减少格式抖动（[04-sampling-decoding](04-sampling-decoding.md)）。

## ❓ 高频面试 / 理解题

**Q：让模型返回 JSON，为什么"在 Prompt 里要求 + 给 schema"还不够，要上约束解码？**
A：Prompt 是**自然语言请求**，模型本质仍在概率续写，随时可能不守约——加寒暄、包 Markdown 围栏、漏字段、把枚举值写成同义词、类型写错。约束解码把约束下沉到**解码算法层**：每步用 schema 状态机算出合法 Token 集合、把非法项概率置零，模型**物理上无法**吐出非法结构，从而把"大概率对"变成"保证符合结构"。生产接代码时二者可靠性差一个量级。

**Q：JSON mode 和 Structured Outputs 有什么区别？**
A：JSON mode 只保证输出是**能被 `json.loads` 解析的合法 JSON**（语法层面），但字段名、是否必填、类型、枚举值它都不管——可能给你一个结构完全不对的合法 JSON。Structured Outputs（约束解码到具体 schema）保证输出**符合你给定的 JSON Schema**：字段齐、类型对、`enum` 只在允许值里取。要把结果直接灌进强类型代码，你需要的是后者。

**Q：既然有了约束解码保证合法，为什么还要做校验和重试？**
A：约束解码保证的是"符合 schema 结构"，但挡不住：①输出被 `max_tokens` **截断**成半个 JSON；②很多模型/自托管环境根本不支持约束解码，你只能用弱手段；③**业务级非法**（格式合法但语义越界，如金额为负、日期非真实存在）。所以必须闭环：反序列化 → Pydantic/JSON Schema 校验（含业务规则）→ 失败把错误信息回填让模型自修复重试。工程上"永远假设这次可能不合法"。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别盲信"要求了就一定给合法结构"**——弱手段（①②）没有硬保证，必须有解析失败的兜底与重试路径。
- ⚠️ **schema 别过度复杂/深嵌套**——层级越深、字段越多、约束越花，成功率和稳定性越低；能拍平就拍平，大对象拆成多次抽取。
- ✅ **结构化任务把温度调低**（趋近 0）：减少格式抖动和字段漂移，让输出更确定（[04-sampling-decoding](04-sampling-decoding.md)）；结构本身该由约束保证，创造性不该花在格式上。
- ✅ **分类就用枚举、别让它造句**：`status ∈ {active,inactive}` 比"请判断是否在职"稳得多，下游也免去二次解析。
- ✅ **schema 即文档 + 即校验**：用 Pydantic / JSON Schema 同时描述给模型看的契约和代码里的校验规则，一处定义两处复用。
- ✅ **加分认知**：能说清"约束解码是在采样层 mask 非法 Token，所以是'保证'而非'请求'"，以及"JSON mode 只管语法、Structured Outputs 才管 schema"，比只会说"让它返回 JSON"更显理解本质。
- 🔗 结构化的更强形态是把它当工具参数来生成 → [20-function-calling](20-function-calling.md)。
