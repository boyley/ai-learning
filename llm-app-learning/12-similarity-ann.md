# 12 · 相似度与向量检索（Similarity & ANN）

> Embedding 把文本变成向量后，"找语义最像的内容"就变成"在向量空间里找最近邻"；海量向量下精确比对太慢，于是用 **ANN（近似最近邻）** 索引（HNSW/IVF/PQ）在**精度、速度、内存**之间做权衡。重要度 ⭐⭐⭐。

## 🎯 一句话核心

向量检索的本质是**最近邻搜索**：把查询向量和库里向量算"相似度"，取最像的 Top-K。相似度最常用 **余弦（cosine）**，海量数据下不做暴力两两比对，而用 **ANN 索引**——**牺牲一丁点召回率，换几十上百倍的提速**。

## 📖 核心原理

**第一步：怎么衡量"两个向量像不像"？** Embedding（详见 [11-embedding](11-embedding.md)）把语义编码成高维向量，"语义相近"对应"空间中方向相近"。三种主流度量：

| 度量 | 直觉 | 关注 | 取值 | 说明 |
|---|---|---|---|---|
| **余弦相似度 Cosine** | 两向量**夹角**的余弦 | **方向**（不看长度） | −1~1，越大越像 | **语义检索最常用**：文本向量长度受词多少影响，只看方向更稳 |
| **点积 Dot product** | 对应维相乘再求和 | 方向 + 长度 | 无固定范围，越大越像 | 受向量模长影响；某些模型/推荐场景故意用长度编码"重要度" |
| **欧氏距离 L2** | 两点间**直线距离** | 绝对位置 | ≥0，越小越像 | 直觉最自然；对长度敏感，高维下区分度下降 |

**关键结论：向量归一化（L2 normalize，模长化为 1）后，cosine 与 dot product 排序完全一致，且 `L2距离² = 2 − 2·cosine` 单调对应**——三者在归一化后给出**相同的 Top-K 排序**。所以实践中：**大多数 embedding 模型输出已归一化或建议归一化，此时用 cosine 或 dot 都行**（dot 更省一步开方，很多库内部就这么优化）；只有当你刻意保留模长信息时，cosine 和 dot 才会给出不同结果。

**第二步：向量检索 = 最近邻搜索（Nearest Neighbor Search）。** 给定查询向量 `q`，在 N 条库向量里找与它相似度最高的 K 条。这就是 RAG 检索、语义搜索、推荐召回的共同底层操作。

**第三步：为什么不能暴力精确检索（Brute-force KNN）？** 最朴素的做法是把 `q` 和全库 N 个向量逐一算相似度再排序，复杂度 **O(N·d)**（d 是维度，常 768~3072）。库里几万条还行，一旦到百万、千万、上亿级，每次查询都要扫全库、算上亿次浮点乘加——**延迟和算力都扛不住**，尤其在线服务要求毫秒级响应。

**第四步：ANN——用一点精度换巨大提速。** **近似最近邻（Approximate Nearest Neighbor）** 放弃"保证找到绝对最近的 K 个"，改为"大概率找到最近的 K 个"。核心权衡是三角关系：

- **召回率 recall**（找回的 Top-K 里有多少是真正的最近邻，衡量精度）
- **速度**（查询延迟 / QPS）
- **内存**（索引占用）

调参本质就是在这三者间挪动：想更快/更省内存，recall 就降；想 recall 更高，就得多花时间或内存。**ANN 能把 O(N) 的暴力扫描降到近似 O(log N) 或"只扫一小部分候选"**，这是向量检索能规模化的根本原因。

## 🔧 关键方法 / 流程 / 架构

**暴力 KNN vs ANN 索引 对比示意：**

```
① 暴力精确 KNN（Flat / Brute-force）
   查询 q ──┬─ 算相似度 ─ 向量1
            ├─ 算相似度 ─ 向量2
            ├─ 算相似度 ─ 向量3
            │      ⋮   （全库 N 个都算一遍）
            └─ 算相似度 ─ 向量N
        → 全排序取 Top-K   ✅100%准  ❌O(N·d) 慢，百万级就跪

② ANN 索引（先"缩小范围"再精算，只碰一小撮候选）
   查询 q ── 索引导航 ──▶ [候选子集 ~几百个] ── 精算 ─▶ Top-K
                │
        HNSW：图上贪心跳转，从入口逐层逼近
        IVF ：先定位最近的几个聚类桶，只搜桶内
        → ✅快几十~上百倍  ⚠️ recall 98%左右（可调），非100%
```

**主流索引（概念级原理直觉，不推公式）：**

| 索引 | 一句话原理 | 优点 | 代价 | 适用 |
|---|---|---|---|---|
| **Flat（暴力）** | 全库逐一精算 | 100% 精确、无需建索引 | 慢、不可规模化 | 小库（万级）、要绝对精确 |
| **HNSW** | **分层可导航小世界图**：向量连成多层近邻图，查询从顶层稀疏图入口贪心跳向更近的点，逐层下沉逼近 | **快、召回高**，主流首选 | **内存大**（存图边），构建较慢 | 中大规模、追求低延迟高精度 |
| **IVF** | **倒排 + 聚类分桶**：先把全库聚成若干簇（类似"分区"），查询只在最近的几个簇里搜 | 省内存、构建快 | 桶边界处可能漏（需调 `nprobe`） | 大规模、内存敏感 |
| **PQ（乘积量化）** | 把高维向量**切段 + 量化压缩**成短编码，用查表近似算距离 | **极省内存**（压几倍~几十倍） | 有量化误差、精度略降 | 超大规模、内存瓶颈 |
| **IVF-PQ（组合）** | IVF 粗定位桶 + PQ 压缩桶内向量 | 又快又省内存 | 精度需仔细调 | 亿级、内存受限的工业场景 |

> 直觉总结：**HNSW = 用内存换速度和精度**（图导航）；**IVF = 用"先分区再局部搜"减少比对量**；**PQ = 用压缩换内存**；三者可组合。**没有免费午餐——所有 ANN 都是在 recall/速度/内存三角里选位置。**

**关键参数直觉（以主流的 HNSW 为例）：**

```
M        每个节点连多少条边（图的"稠密度"）
         ↑大 → 图更密、召回更高、内存更大、构建更慢
ef_construction  建索引时每步考察的候选数
         ↑大 → 图质量更好、构建更慢
ef_search（查询期 ef）  查询时维护的候选队列大小
         ↑大 → 搜得更宽、召回更高、但更慢  ← 最常用的"精度/速度"在线旋钮
```

一句话：**M 和 ef_construction 建索引时定"图的底子"，ef_search 在线调"这次搜多仔细"**。想临时提召回，加大 ef_search 即可（换来延迟上升）。IVF 对应的在线旋钮是 `nprobe`（搜几个桶，越多越准越慢）。

**在检索链路中的位置：**

```
文本 ──[Embedding 模型]──▶ 向量 ──[向量库 + ANN 索引]──▶ Top-K 最近邻
        (11-embedding)                (13-vector-database)
                                              │
                                              ▼
                            RAG 用 Top-K 作上下文喂给 LLM（14-rag-overview）
```

ANN 只是"快速找候选"。工程上常搭 **两阶段检索**：ANN 粗召回一批（如 Top-100），再用更精的 **Rerank**（cross-encoder）精排出 Top-K（详见 [17-rerank](17-rerank.md)）——用 ANN 的快 + rerank 的准互补。

## 🔑 要点速记

- 向量检索 = **最近邻搜索**：给查询向量找库里相似度最高的 Top-K。
- 相似度三选：**cosine（看方向，语义检索最常用）/ dot（方向+长度）/ L2（直线距离）**。
- **归一化后 cosine ≈ dot，且与 L2 排序一致**——三者给相同 Top-K；不归一化才有别。
- 暴力精确 KNN 是 **O(N·d)**，百万级以上扛不住 → 必须上 ANN。
- **ANN = 牺牲一点 recall 换大幅提速**；核心是 **召回率 / 速度 / 内存** 三角权衡。
- **HNSW**（分层图，快+精度高+内存大，主流）、**IVF**（聚类分桶粗定位，省内存）、**PQ**（量化压缩省内存）、**IVF-PQ**（组合，亿级工业级）。
- HNSW 调参：**M / ef_construction**（建索引定图质量）、**ef_search**（在线调精度/速度）；IVF 调 **nprobe**。
- ANN 负责"快而粗"，常配 **Rerank** 做"慢而精"的两阶段检索。

## ❓ 高频面试 / 理解题

**Q：cosine、dot、L2 怎么选？它们有什么关系？**
A：cosine 看**夹角/方向**、不受向量长度影响，是语义检索最常用的；dot 是**方向+长度**都算；L2 是**直线距离**。关键点：**向量归一化后，cosine 和 dot 的排序完全等价，且 `L2² = 2−2·cosine` 与 cosine 单调对应**——三者会给出相同的 Top-K。所以多数 embedding 模型建议归一化后，用 cosine 或 dot 都行（dot 少一步开方更省）。只有刻意保留模长信息（用长度编码重要度）时，选择才会影响结果。

**Q：为什么向量检索要用 ANN，而不是精确 KNN？**
A：精确 KNN 要把查询向量和全库 N 条逐一比对，复杂度 O(N·d)，库到百万/千万级时每次查询都扫全库、算上亿次浮点运算，延迟和算力都撑不住在线服务。ANN（近似最近邻）放弃"保证绝对最近"，换成"大概率最近"，通过图导航（HNSW）或聚类分桶（IVF）**只比对一小撮候选**，把 O(N) 降到近似 O(log N)，提速几十上百倍，recall 仍能到 98%+。代价是牺牲一点精度——这在 RAG 等场景通常可接受。

**Q：HNSW 和 IVF-PQ 各适合什么场景？怎么权衡？**
A：所有 ANN 都在 **recall / 速度 / 内存** 三角里选位置。**HNSW** 用内存换速度和精度（存分层图的边），召回高、延迟低，是中大规模、追求低延迟高精度的主流首选，缺点是内存占用大、构建慢。**IVF-PQ** 用"聚类粗定位 + 乘积量化压缩"把内存压到很低，适合亿级、内存受限的工业场景，代价是量化误差导致精度略降、需要仔细调 nprobe。一句话：**内存充足要快要准选 HNSW，超大规模省内存选 IVF-PQ**。

**Q：ANN 召回率不够高怎么办？**
A：先调在线旋钮——HNSW 加大 `ef_search`、IVF 加大 `nprobe`（搜更宽的候选，换延迟上升）；不够再调建索引参数（HNSW 的 `M`/`ef_construction` 提升图质量，代价是内存和构建时间）。更根本的是加 **两阶段检索**：ANN 粗召回一批候选（如 Top-100），再用 cross-encoder **Rerank** 精排（[17-rerank](17-rerank.md)），用快+准互补，比单纯堆 ANN 参数更划算。

## ⚠️ 易错点 / 实践建议

- ⚠️ **度量要和索引/模型对齐**：建索引时选的距离度量（cosine/dot/L2）必须和 embedding 模型训练时用的一致，否则相似度失真、召回崩。**用了 dot 就要先归一化，别混用**。
- ⚠️ **别拿 recall 当准确率**：ANN 的 recall 是"找回的 Top-K 里有多少是真最近邻"，不等于 RAG 最终答对率。检索质量还看 embedding 好不好、分块合不合理，recall 高≠答案对。
- ⚠️ **HNSW 内存别低估**：图的边随 M 线性增长，亿级向量下内存可能是纯向量的数倍——上线前按 `向量数 × 维度 × 4字节 + 图开销` 估算，内存不够就上 IVF-PQ 或量化。
- ✅ **默认从 HNSW 起步**：多数中小规模应用（百万级以内）HNSW + 归一化 cosine 就够快够准，参数用库的默认值再按需调 `ef_search`；别一上来就上 IVF-PQ 徒增调参复杂度。
- ✅ **ANN + Rerank 是标配**：单靠 ANN 提召回性价比低，粗召回（ANN 拉宽 Top-N）+ 精排（rerank）是 RAG 检索的主流范式（[16-retrieval-optimization](16-retrieval-optimization.md)、[17-rerank](17-rerank.md)）。
- ✅ **加分认知**：能说清"归一化后 cosine=dot=L2 同序"和"ANN 是 recall/速度/内存三角权衡"，比只会背 HNSW 名字更显理解本质。
