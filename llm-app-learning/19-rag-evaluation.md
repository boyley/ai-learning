# 19 · RAG 评估（RAG Evaluation）

> RAG 是一条多环节流水线（分块→检索→rerank→生成），效果差必须能**定位是哪一环坏了**；评估的核心方法是**拆成"检索层 + 生成层"两段分别量化**，尤其抓住生成层的 **Faithfulness（忠实度）**。重要度 ⭐⭐⭐。

## 🎯 一句话核心

RAG 评估不是"给答案打个总分"，而是**把流水线拆开分层量化**——先量"检索层：该找的片段找回来了吗、切不切题"，再量"生成层：答案是否严格基于检索内容（Faithfulness）、切不切题、对不对"。只有分层，才能把"效果差"从玄学变成"第 X 环坏了"的可定位问题。

## 📖 核心原理

**为什么 RAG 必须评估、而且必须分层评估？** RAG 的最终效果是一条链路上多个环节的乘积：分块合不合理 → 向量检索召回准不准 → rerank 排序对不对 → 生成模型用没用好检索内容。任何一环坏了，最终答案都会差。如果只看"最终答案好不好"这一个总分，你根本不知道该去调分块、调检索、换 rerank 还是改 Prompt——调优就变成了**碰运气式的玄学**。评估的第一价值就是**归因（attribution）**：把总误差拆到每一环，让优化有的放矢。

**RAG 的误差在结构上天然分成两段，所以评估也拆两段。** 一条 RAG 请求可以清晰切成"检索（retrieval）"和"生成（generation）"两个阶段，两段的失败模式完全不同：

- **检索层失败**：该召回的文档没召回（Recall 低）、召回一堆不相关的片段（Precision 低）、片段虽相关但切得七零八落不成句（Context Relevance 差）、正确片段排在很后面（MRR/NDCG 低）。**检索层坏了，生成层再强也是"巧妇难为无米之炊"**。
- **生成层失败**：检索内容其实是对的，但模型**没用上、用错了、或凭自己记忆编造**（Faithfulness 低）；或者答非所问（Answer Relevance 低）；或者事实就是错的（Correctness 低）。

**Faithfulness（忠实度）是 RAG 最关键、也是最独有的指标。** RAG 的整个存在意义就是"让答案有据可依、可溯源、不瞎编"。忠实度衡量的正是：**答案里的每一个论断，是否都能在检索到的上下文里找到支撑**。一个答案可能"看起来很对"（Correctness 高），但如果它是模型凭参数记忆编的、检索内容根本没提，那这个 RAG 就是失败的——因为它退化回了会幻觉的裸 LLM（幻觉本质见 [05-hallucination](05-hallucination.md)）。忠实度低 = RAG 没起到"约束模型基于事实作答"的作用，这是比"答错"更隐蔽、更危险的问题。

**为什么现在多用 LLM 来打这些分？** 检索层指标（Recall/Precision）只要有"应召回文档"标注就能用规则算；但生成层的 Faithfulness、Answer Relevance 是**语义层面**的判断——"这句话有没有被上下文支撑""答案切不切题"无法用字符串匹配衡量。于是主流做法是 **LLM-as-a-Judge**：用一个强模型当裁判，读上下文、问题、答案，按定义逐条打分。RAGAS 等框架就是把这套"用 LLM 自动算 RAG 指标"的流程工程化。

## 🔧 关键方法 / 流程 / 架构

**检索层 vs 生成层：指标对照（本篇重点）**

| 层 | 指标 | 衡量什么 | 怎么算 | 坏了说明 |
|---|---|---|---|---|
| **检索层** | **Recall（召回率）** | 应召回的文档，找回了几个 | 命中 golden 文档数 / 应召回总数 | 知识没进上下文，答案必错 |
| 检索层 | **Precision / 命中率** | 召回的片段里有多少是相关的 | 相关片段数 / 召回片段数 | 噪声多，干扰生成、浪费上下文 |
| 检索层 | **Context Relevance** | 召回片段切不切题、成不成句 | LLM 判断片段与问题相关度 | 分块粒度/策略有问题 |
| 检索层 | **MRR / NDCG** | 正确片段排得靠不靠前 | 排序位置加权 | 该上 rerank 或 rerank 没调好 |
| **生成层** | **Faithfulness（忠实度）⭐** | 答案是否**严格基于**检索内容、有无编造 | LLM 逐句核对答案论断能否被上下文支撑 | 模型在幻觉/没用检索内容 |
| 生成层 | **Answer Relevance** | 答案切不切题、答没答到点 | LLM 判断答案与问题的贴合度 | Prompt 或模型没抓住意图 |
| 生成层 | **Correctness（正确性）** | 答案与标准答案对不对 | 对比 golden answer（LLM 或人工） | 事实性错误 |

> 记忆锚点：**检索层 = "米淘对了吗"，生成层 = "饭做对了吗"**；忠实度专门抓"是不是拿着好米却自己瞎编做了别的饭"。

**RAG 评估管道（离线）**

```
              ┌─────────── 评估集 Golden Set ───────────┐
              │  { 问题 Q, 标准答案 A*, 应召回文档 D* }   │
              └──────────────────┬──────────────────────┘
                                 │ 灌入被测 RAG 系统
                                 ▼
        ┌────────────────────────────────────────────────┐
        │  Q ─► [检索/rerank] ─► 上下文 C ─► [生成] ─► 答案 Â │
        └───────┬───────────────────────────────┬─────────┘
                │ 拿 C 和 D* 比                    │ 拿 Â、C、A* 比
                ▼                                 ▼
        ┌──────────────┐                 ┌──────────────────┐
        │  检索层指标    │                 │   生成层指标        │
        │  Recall       │                 │  Faithfulness ⭐  │
        │  Precision    │                 │  Answer Relevance │
        │  MRR / NDCG   │                 │  Correctness      │
        └──────┬───────┘                 └────────┬─────────┘
               └───────────► 分层归因 ◄───────────┘
                     "先看检索对不对，再看用没用上"
```

**分层排查流程（如何定位问题）**

```
答案很差
   │
   ├─① 先看检索层：Recall / Context Relevance 高吗？
   │      │
   │      ├─ 低 ──► 问题在"米"：调分块粒度、换 embedding、
   │      │          加混合检索 / 查询改写 / rerank（详见 18-advanced-rag.md）
   │      │
   │      └─ 高（对的片段确实召回了）
   │                │
   │                ▼
   └─② 再看生成层：Faithfulness 高吗？
          │
          ├─ 低 ──► 问题在"做饭"：模型没用上下文 / 在编造
          │          → 改 Prompt（强约束"只依据上下文"）、
          │            换更强模型、缩短噪声上下文
          │
          └─ 高但 Correctness 低 ──► 上下文本身有误 / 标准答案存疑
```

> 关键顺序：**永远先排检索、再排生成**。检索没召回对的片段时，生成层的忠实度/正确性都无从谈起——先保证"米是对的"，再谈"饭做得好"。这一分层排查思路与高级检索优化互为呼应（详见 18-advanced-rag.md）。

**RAGAS 框架的思路（框架无关地理解）**：RAGAS 把上面几个语义指标做成"用 LLM 自动打分"的标准流程——例如算 Faithfulness 时，先让 LLM 把答案拆成一条条**原子论断（claims）**，再逐条判断"这条能否由检索上下文推出"，支撑率即忠实度；算 Answer Relevance 时，让 LLM 由答案**反推可能的问题**，再算反推问题与原问题的相似度。核心是把"人来判断语义"换成"LLM 按固定 rubric 判断"，从而能规模化、自动化跑分。其它评估工具（TruLens、DeepEval、Phoenix/Arize 等）思路类似，此处不展开。

**评估集（Golden Set）构建**：一条评估样本 = `{ 问题, 标准答案, 应召回文档 }`。构建方法：
- **LLM 合成 + 人工校验**：给定文档库，让 LLM 针对每篇/每段自动生成"问题 + 参考答案 + 该问题应命中哪些片段"，再由人抽检修正。这是低成本冷启动的主流做法，但**必须人工过一遍**——LLM 合成的问题常常过于表面或答案有偏。
- 覆盖**多样性**：简单事实题、需要多片段综合的题、答案不在库里应"拒答"的题（考 RAG 会不会硬编）。评估集质量直接决定评估结论可信度，宁可小而精。

**LLM-as-a-Judge（用强模型当裁判）**：Faithfulness、Answer Relevance、Correctness 这类语义打分，本质都是"让一个强模型读材料按标准打分"。要点是给裁判**清晰的评分 rubric + few-shot 示例 + 让它先给理由再给分**（降低随意性）。裁判模型的选择、偏差（位置偏好、啰嗦偏好、自我偏好）与缓解手段是一个独立话题，展开详见 26-llm-evaluation.md。

**在线评估（生产环境）**：离线 golden set 覆盖不到真实分布，上线后还要收集在线信号：
- **用户显式反馈**：点赞/点踩、"这条有帮助吗"。
- **隐式信号**：是否复制答案、是否追问、是否重问同一问题（重问 = 大概率没答好）。
- **A/B 测试**：新分块策略 / 新 rerank / 新 Prompt 上线，用真实流量对比核心指标与满意度。
- 把点踩样本回流成新的 golden 样本，形成"评估→优化→再评估"闭环。

## 🔑 要点速记

- RAG 是多环节流水线，评估的第一价值是**归因**——把"效果差"定位到坏在哪一环，摆脱玄学调优。
- 核心方法：**拆成检索层 + 生成层两段分别量化**。
- **检索层**：Recall（该召回的召回没）、Precision/命中率（召回的准不准）、Context Relevance（切不切题）、MRR/NDCG（排得靠不靠前）。
- **生成层**：**Faithfulness 忠实度（答案是否严格基于检索内容、有无编造——RAG 最关键指标）**、Answer Relevance（切不切题）、Correctness（对不对）。
- **Faithfulness 是 RAG 独有的命门**：答案"看着对"但凭记忆编的（上下文没提），RAG 就退化回了会幻觉的裸模型。
- 语义指标（忠实度、切题度）用 **LLM-as-a-Judge** 自动打分；**RAGAS** 把这套流程工程化（拆原子论断逐条核对）。
- **评估集 = 问题 + 标准答案 + 应召回文档**，用 LLM 合成 + 人工校验，要覆盖多样性（含"应拒答"题）。
- **排查顺序永远是：先检索、后生成**——先看"检索对不对"，再看"用没用上"。
- 离线跑 golden set + 在线收反馈/点踩/A-B，闭环回流。

## ❓ 高频面试 / 理解题

**Q：为什么 RAG 评估要拆成检索层和生成层，直接看最终答案好坏不行吗？**
A：因为 RAG 效果是"分块→检索→rerank→生成"多环节的乘积，只看最终总分无法归因——你不知道该调检索还是改 Prompt，调优就成了碰运气。拆成两段后：检索层指标（Recall/Precision/Context Relevance/MRR）告诉你"该找的片段找回来、排好了吗"，生成层指标（Faithfulness/Answer Relevance/Correctness）告诉你"模型用没用好这些片段"。排查时**先检索、后生成**，能精准定位坏在哪一环。

**Q：Faithfulness（忠实度）和 Correctness（正确性）有什么区别？为什么说忠实度是 RAG 最关键指标？**
A：Correctness 衡量"答案和标准答案对不对"，Faithfulness 衡量"答案是否严格由检索上下文支撑、有没有编造"。二者会分离：一个答案可能恰好正确（Correctness 高）却是模型凭参数记忆瞎编的、检索内容根本没提（Faithfulness 低）——这时 RAG 已经退化回会幻觉的裸 LLM，只是这次蒙对了。RAG 的存在意义就是"让答案有据可依、可溯源、不瞎编"，所以忠实度直接衡量 RAG 有没有起作用，是它独有的命门。

**Q：Faithfulness 这种语义指标怎么自动打分？RAGAS 是怎么做的？**
A：用 LLM-as-a-Judge。以 RAGAS 算 Faithfulness 为例：先让 LLM 把生成的答案拆成一条条**原子论断（claim）**，再逐条判断"这条能否由检索到的上下文推出"，被支撑的比例就是忠实度；算 Answer Relevance 则让 LLM 由答案反推问题、再与原问题算相似度。核心是把"人判断语义"换成"LLM 按固定 rubric 判断"，从而能规模化自动跑分。裁判模型的偏差与缓解详见 26-llm-evaluation.md。

**Q：评估集（golden set）怎么构建？全靠人工标注成本太高怎么办？**
A：一条样本 = {问题, 标准答案, 应召回文档}。低成本做法是 **LLM 合成 + 人工校验**：让 LLM 针对文档库自动生成"问题+参考答案+应命中片段"，再由人抽检修正——但人工这一步不能省，LLM 合成的题常过于表面。要点是覆盖多样性：简单事实题、需多片段综合的题、以及答案不在库里应"拒答"的题（考 RAG 会不会硬编）。评估集宁可小而精。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别只看最终答案好坏**：不分层就无法归因，最典型的坑是"检索层其实没召回对片段，却在拼命调 Prompt"——方向全错。永远先确认检索层是否健康。
- ⚠️ **别把 Correctness 高当成 RAG 成功**：忠实度低的"蒙对"是定时炸弹，换个问题就露馅。生产上把 Faithfulness 作为核心守门指标，甚至可用它做在线拦截（低忠实度答案触发兜底/拒答）。
- ⚠️ **LLM-as-a-Judge 不是绝对真理**：裁判模型自身有偏差（偏好啰嗦、位置偏好、自我偏好），且换裁判模型分数会漂移。要固定裁判版本、给清晰 rubric、让它先说理由再打分，关键结论用人工抽检校准（详见 26-llm-evaluation.md）。
- ✅ **别让评估集"泄题"**：合成评估集若用的正是被测系统同款模型/同款分块，评分会虚高。评估集应独立构建、人工把关，并覆盖"应拒答"负样本。
- ✅ **离线 + 在线两条腿**：离线 golden set 保证可复现、可回归；在线点踩/A-B 捕捉真实分布，并把 badcase 回流成新 golden 样本，形成评估—优化闭环。
