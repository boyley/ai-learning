# 17 · 重排 Rerank（Reranking）

> 在"快而粗"的向量/BM25 召回之后，再用一个"慢而准"的 **cross-encoder** 对少量候选重新精排，把真正最相关的几条送进 Prompt——这就是**两阶段检索**里决定上下文质量的关键一环。重要度 ⭐⭐⭐。

## 🎯 一句话核心

Rerank 的本质是**"先广撒网、再精挑细选"**：召回阶段用便宜的向量距离粗筛出 Top-N（保召回率），Rerank 阶段用一个能做 **query-doc 深度交互**的强模型对这 N 条重新打分，只留 Top-K（保精确率）——**用一次可控的延迟/成本，换进入 Prompt 的上下文质量的显著提升**。

## 📖 核心原理

**为什么向量检索"不够准"？根子在 bi-encoder（双塔编码器）。** 向量检索的做法是：把 query 和每篇 doc **各自独立**编码成一个定长向量，然后算余弦相似度或点积（相似度原理详见 [12-similarity-ann](12-similarity-ann.md)）。这套设计的**优点是可离线预计算**——所有 doc 的向量提前算好存进向量库，查询时只算一次 query 向量再做 ANN 近邻搜索，快到毫秒级、可扩展到亿级文档。但它的**代价是牺牲了 query 与 doc 之间的细粒度交互**：doc 在被编码时**根本不知道 query 是什么**，query 里哪个词该重点匹配、哪个是关键约束，向量都无从体现。它把一段几百字的文档压成一个向量，语义被"平均化"，于是常出现**"大体相关但不是真正想要"**的候选——比如 query 问"退货运费谁承担"，召回一堆讲"退货流程"的段落，却把那句真正讲运费归属的排在后面。

**Rerank 换用 cross-encoder（交叉编码器）来补这一刀。** cross-encoder 不再各编各的，而是把 **query 和 doc 拼成一个序列**（`[CLS] query [SEP] doc [SEP]`）一起送进 Transformer，让 query 的每个 token 与 doc 的每个 token 在**注意力层充分交互**，最后输出一个 0~1 的相关性分数。因为模型能"带着 query 去读 doc"，它能捕捉否定、条件、指代、精确匹配这些 bi-encoder 丢掉的信号，**打分精度显著更高**。但代价也很直接：它**不能离线预计算**——分数依赖具体的 query+doc 组合，每来一个 query 都得把候选逐条重新前向推理一遍，复杂度是 O(N) 次模型调用。若对全库百万文档都跑 cross-encoder，延迟不可接受。

**于是两者的分工顺理成章：召回用 bi-encoder（快、负责"别漏"），精排用 cross-encoder（准、负责"选对"）。** cross-encoder 只作用在召回出的那 **N 条**（如 50~100）上——N 足够小，它的高成本被摊薄到可接受；N 又足够大，能把召回阶段"排在二三十名但其实最相关"的那条捞回来重新扶正。这正是 Rerank 的核心价值：**它允许你在召回阶段放心地把 Top-N 放大以保住召回率，再由精排把精确率赢回来**——鱼和熊掌通过"两阶段"分别拿到。

**Rerank 带来的下游收益是复合的。** 送进 Prompt 的上下文更相关、噪音更少，直接意味着：① LLM 更容易基于正确材料作答，**减少被无关段落带偏导致的幻觉**（幻觉成因详见 [05-hallucination](05-hallucination.md)）；② 同样的 Top-K 预算装进更高含金量的内容，**token 花得更值**，也缓解长上下文里的"Lost in the Middle"（详见 [06-context-engineering](06-context-engineering.md)）；③ 因为有精排兜底，召回阶段可以更激进地扩大 N、甚至多路召回，**整体召回率与精确率同时抬高**。

## 🔧 关键方法 / 流程 / 架构

**两阶段检索：粗召回 → Rerank 精排**

```
                        用户 Query
                            │
        ┌───────────────────┴────────────────────┐
        │  ① 粗召回 Retrieval（快 · 重召回率 Recall）│
        │   bi-encoder 向量检索 / BM25 / 混合检索    │
        │   目标：别漏 → 放大 Top-N（如 50~100）     │
        └───────────────────┬────────────────────┘
                            │  N 条候选（大体相关、含噪）
                            ▼
        ┌────────────────────────────────────────┐
        │  ② 精排 Rerank（慢 · 重精确率 Precision） │
        │   cross-encoder 对每条 (query, doc) 打分  │
        │   目标：选对 → 按分数排序，取 Top-K（3~5） │
        └───────────────────┬────────────────────┘
                            │  K 条真正最相关
                            ▼
                  拼进 Prompt → 交给 LLM 生成
```

**Bi-encoder vs Cross-encoder 对比**

| 维度 | Bi-encoder（双塔，用于召回） | Cross-encoder（交叉，用于精排） |
|---|---|---|
| 编码方式 | query、doc **各自独立**编码成向量 | query+doc **拼一起**送进模型 |
| query-doc 交互 | ❌ 无（编码 doc 时不知 query） | ✅ 注意力层深度交互 |
| 可否离线预计算 | ✅ doc 向量提前算好入库 | ❌ 依赖具体 query，须实时逐条算 |
| 速度 | 极快（一次编码 + ANN，毫秒级） | 慢（N 次模型前向，O(N)） |
| 精度 | 较粗（语义平均化，含噪） | 高（能抓否定/条件/精确匹配） |
| 可扩展规模 | 亿级全库检索 | 仅几十~几百候选 |
| 输出 | 向量 → 算距离 | 直接输出相关性分数 0~1 |
| 定位 | 第一阶段"别漏"（Recall） | 第二阶段"选对"（Precision） |

**实现方式（框架无关，概念级）**

- **专用 Rerank API**：如 **Cohere Rerank**、Jina Reranker、阿里/百度等厂商的重排服务——传入 `query` + 候选文档列表，返回带相关性分数的重排结果，托管、免运维。
- **开源 Rerank 模型自托管**：如 **`bge-reranker`（BAAI）**、`mxbai-rerank` 等 cross-encoder 模型，可本地部署、数据不出域、可微调适配领域。
- 极简调用直觉（伪代码）：

```text
candidates = retrieve(query, top_n=100)          # ① bi-encoder 粗召回
scored     = reranker.score(query, candidates)   # ② cross-encoder 逐条打分
context    = top_k(scored, k=5)                  # 取精排 Top-K 进 Prompt
```

> 具体框架落地（Spring AI / LangChain4j 的 Reranker 组件接线）见对应框架库，本篇只讲原理与方法。

**N 与 K 怎么定（核心权衡）**

- **N（召回候选数）**：太小 → 真正相关的可能压根没进候选，精排再强也回天乏术（**召回率是精排的天花板**）；太大 → cross-encoder 调用变多，延迟/成本线性上涨。常见 50~100，是"召回兜底"与"精排成本"的平衡点。
- **K（最终保留数）**：太小 → 可能漏掉有用上下文；太大 → 噪音回流、token 浪费、重新触发 Lost in the Middle。常见 3~5，视 Prompt 预算与任务而定。
- 经验路径：**先把 N 放大保住召回率，再用 Rerank 把 K 收窄提精确率**——这正是两阶段的意义。

## 🔑 要点速记

- **两阶段检索**：① 粗召回（向量/BM25，快，重 Recall，Top-N 50~100）→ ② Rerank 精排（cross-encoder，准，重 Precision，Top-K 3~5）。
- **bi-encoder**：query/doc 各自独编码算距离，可离线预算、快但粗，**牺牲 query-doc 交互**。
- **cross-encoder**：query+doc 拼一起深度交互打分，**精度高但不能预算、须实时逐条跑**，故只用于少量候选。
- Rerank 收益：**上下文更相关、噪音更少、降幻觉、token 更值**，且允许召回放大 N 保召回率。
- **召回率是精排的天花板**：真相关文档没进 Top-N，Rerank 也救不回来。
- 实现：专用 API（Cohere Rerank 等）或自托管模型（bge-reranker 等）。
- 权衡：N 越大召回越稳但越贵，K 越小越干净但可能漏；Rerank 多一次延迟/成本，**但通常值得**。

## ❓ 高频面试 / 理解题

**Q：已经有向量检索了，为什么还要 Rerank？它到底解决了向量检索的什么短板？**
A：向量检索用 bi-encoder，query 和 doc **各自独立编码**再算距离，好处是 doc 向量能离线预算、检索极快可扩展，但**编码 doc 时根本不知道 query**，丢失了 query 与 doc 的细粒度交互，导致召回"大体相关但不精准"。Rerank 换用 cross-encoder，把 query+doc **拼在一起**送进模型做注意力交互再打分，能抓住否定、条件、精确匹配等信号，精度高得多；代价是不能预算、要实时逐条推理，所以只对粗召回的少量候选（N 条）用它——用一次可控成本换上下文质量。

**Q：为什么不直接用 cross-encoder 检索全库，省掉两阶段？**
A：因为 cross-encoder 的分数依赖具体的 (query, doc) 组合，**无法离线预计算**，每个 query 都要对候选逐条前向推理，复杂度 O(N)。对百万级全库跑就是百万次模型调用，延迟和成本都不可接受。而 bi-encoder 可预算向量 + ANN 近邻搜索能在毫秒内从亿级文档里粗筛。所以让 bi-encoder 负责"从海量里快速别漏"，cross-encoder 负责"从少量里精准选对"，各取所长。

**Q：Rerank 里的 N 和 K 怎么权衡？为什么说召回率是精排的天花板？**
A：N 是召回候选数，K 是最终进 Prompt 数。N 太小则真正相关的可能没进候选，**精排只能在给它的 N 条里排序，选不出没被召回的东西**——这就是"召回率是精排天花板"；N 太大则 cross-encoder 调用线性变多、变慢变贵。K 太大则噪音回流、浪费 token、触发 Lost in the Middle；太小则可能漏上下文。实践上先放大 N 保召回，再用 Rerank 收窄 K 提精确，典型 N=50~100、K=3~5。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别指望 Rerank 补救召回的漏**：Rerank 只能在候选 N 条里重排，召回阶段没捞到的文档它永远选不出来。相关文档命中率低时，先去优化召回（混合检索/query 改写，详见 [16-retrieval-optimization](16-retrieval-optimization.md)），而不是加 Rerank。
- ⚠️ **N 别盲目开大**：cross-encoder 成本随 N 线性涨，N 从 20 提到 200 延迟可能翻十倍而召回增益递减。先用评估找到召回率饱和的 N，别拍脑袋。
- ⚠️ **Rerank 是一次额外的网络/推理延迟**：串在检索与生成之间，对低延迟场景要评估是否可接受；可考虑候选并行打分、缓存热门 query、或用更小的 reranker。
- ✅ **N 与 K 要靠评估调，不是玄学**：用检索指标（Recall@N、MRR、nDCG）量化召回与重排效果，端到端再看答案质量（详见 [19-rag-evaluation](19-rag-evaluation.md)）——先量化再调参。
- ✅ **领域差距大时可微调 reranker**：通用 cross-encoder 在专业领域（法律/医疗/代码）可能水土不服，用领域内 query-doc 相关性标注微调开源 reranker，收益往往比换更大 LLM 更划算。
- ✅ **加分认知**：能说清"bi-encoder 牺牲交互换可预算的速度、cross-encoder 用不可预算的交互换精度，两阶段让 Recall 与 Precision 分别到位"，比只会背"Rerank 提升相关性"更显对检索本质的理解。
