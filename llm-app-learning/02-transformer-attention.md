# 02 · Transformer 与注意力（Transformer & Attention）

> Transformer 是现代 LLM 的底层网络架构，其核心是**自注意力（Self-Attention）**——让每个 Token 动态"看"序列里所有其它 Token 并按相关性加权聚合信息；正是它带来了**并行训练**和**长距离依赖建模**，才催生了大模型。重要度 ⭐⭐。

## 🎯 一句话核心

Transformer 用**注意力（Attention）取代了 RNN 的逐词串行处理**：每个 Token 一步就能"扫视全序列、按相关性抓取需要的信息"，因此**能并行训练（快）、能建模长距离依赖（准）**——这是 LLM 得以规模化的架构前提。作为应用开发者，理解它到"直觉"层面即可：不必推公式，但要懂**为什么长上下文又贵又慢**。

## 📖 核心原理

**为什么 Transformer 取代了 RNN？** 在 Transformer（2017《Attention Is All You Need》）之前，处理序列靠 RNN/LSTM——它**逐个 Token 顺序处理**，第 t 个词必须等第 t-1 个算完。这带来两个致命问题：① **无法并行**，训练慢，喂不下海量语料（正是规模效应的敌人，规模效应见 [01-llm-overview](01-llm-overview.md)）；② **长距离依赖衰减**，信息要一格一格传递，隔得远的词之间关系容易在传递中丢失（"梯度消失"）。Transformer 用注意力**一次性让所有 Token 两两直接相连**：整句话同时进入网络并行计算，任意两个词无论隔多远都是"一步可达"。**能并行 + 能记远** 这两点，正是大模型能在万亿 Token 上训练出来的架构基础。

**自注意力 Self-Attention 的直觉："这个词该重点看哪些词"。** 理解一个词要看上下文——"苹果"在"吃苹果"里是水果，在"苹果发布会"里是公司。自注意力就是让每个 Token 主动**环视序列里所有其它 Token，判断谁跟我相关，然后按相关性高低加权，把它们的信息聚合到自己身上**，形成融入了上下文的新表示。例如句子"那只**猫**没过马路因为**它**太累了"，处理"它"时，注意力会给"猫"很高的权重——模型借此"知道"它指的是猫。这种"按需抓取相关信息"的能力，就是语言理解的核心机制。

**Q/K/V 的直觉（不推公式）：** 注意力用三个角色实现"按相关性加权":
- **Query（查询）**：当前 Token 发出的"我在找什么"的提问。
- **Key（键）**：每个 Token 挂出的"我是关于什么的"标签，用来被匹配。
- **Value（值）**：每个 Token 实际携带、准备被取走的信息内容。
机制像**带权检索**：拿我的 Query 去和所有 Token 的 Key 逐一比对相似度，算出"我该关注每个词多少"的权重，再用这些权重去加权汇总所有词的 Value。相似度高的词，其 Value 就更多地流进当前 Token 的新表示里。一句话：**Query 问、Key 应、Value 给**。

**多头注意力 Multi-Head：多个角度同时看关系。** 一组 Q/K/V 只能捕捉一种关系模式。多头注意力把注意力**并行复制成多个"头"**，每个头用各自的 Q/K/V 学习**不同角度的关系**——有的头盯语法主谓、有的头盯指代（它→猫）、有的头盯长距离呼应，最后把各头结果拼接融合。就像多个专家从不同视角审同一句话，表达力远强于单头。

**位置编码 Positional Encoding：为什么必须补"顺序"。** 注意力有个"缺陷"：它把输入当成一**袋无序的 Token**（谁和谁的相关性只看内容，不看位置）——但"猫追狗"和"狗追猫"含义完全相反，语言是有序的。所以 Transformer 必须**额外给每个 Token 注入位置信息**（早期用正弦编码，现代 LLM 多用 RoPE 旋转位置编码等），让模型分得清词序。**记住这条因果：注意力本身无序 → 才需要位置编码**，这也是"长上下文外推""上下文窗口"等话题的根子。

## 🔧 关键方法 / 流程 / 架构

**自注意力概念示意（处理"它"时环视全句、按相关性加权）：**

```
输入序列：  [那只]  [猫]  [过了]  [马路]  [因为]  [它]  [累了]
                                                     │
                          当前处理 "它"，发出 Query ─┘（我指代谁？）
                                                     │
        拿 Query 与每个 Token 的 Key 比相似度，得到注意力权重：
                                                     ▼
        那只:0.02  猫:0.71  过了:0.03  马路:0.05  因为:0.04  它:0.10  累了:0.05
                     ▲高权重
                     │  按权重加权汇总各 Token 的 Value
                     ▼
        "它" 的新表示 ≈ 大量吸收了 "猫" 的信息 → 模型"知道"它=猫

  （多头 = 上面这套并行跑多组，各头关注不同关系：指代/语法/呼应…最后拼接）
```

**三种架构类型（按用到 Transformer 的哪半边划分）：**

| 架构 | 代表 | 注意力可见范围 | 擅长 | 典型任务 |
|---|---|---|---|---|
| **Encoder-only** | BERT | 双向（看得到左右全文） | **理解**（把整段读懂再判断） | 分类、抽取、检索/Embedding |
| **Decoder-only** | GPT、Claude、Llama | **单向**（只能看左边，看不到未来词） | **生成**（自回归续写） | 对话、写作、代码——**当今 LLM 主流** |
| **Encoder-Decoder** | T5、原始 Transformer | 编码器双向 + 解码器单向 | **转换**（读入 A 生成 B） | 翻译、摘要 |

**为什么现在生成式 LLM 几乎都是 Decoder-only？**
- **任务天然契合**：LLM 的本质是"预测下一个 Token"的自回归续写（见 [01-llm-overview](01-llm-overview.md)），Decoder 的**单向掩码注意力（只能看左边）**恰好就是这个目标——训练即生成，架构与任务完全一致。
- **规模化与通用性更好**：结构简单统一，一个模型靠续写就能零样本做几乎所有任务（对话、翻译、抽取都可转化为"续写"），无需 Encoder-Decoder 那样区分输入/输出两套网络；工程上更易堆参数、更易做 KV Cache 加速。
- 于是"理解型"的 Encoder-only（BERT 路线）如今主要用于 Embedding/检索这类判别任务，生成式大模型则清一色走 Decoder-only。

**计算复杂度 O(n²)——长上下文为什么又贵又慢：** 自注意力要让**每个 Token 和每个 Token 都两两算相关性**，n 个 Token 就是 n×n 次比对。所以**计算量和显存随序列长度呈平方级增长**：上下文翻 10 倍，注意力开销约翻 100 倍。这直接解释了三件应用者天天遇到的事：① 长 Prompt/长文档**推理更慢**；② 长上下文**更烧钱**（呼应按 Token 计费，见 [03-token-tokenization](03-token-tokenization.md)）；③ 模型有**上下文窗口上限**、且塞满未必更好（呼应上下文工程，见 [06-context-engineering](06-context-engineering.md)）。这也是长上下文优化（稀疏注意力、FlashAttention 等）持续演进的原因。

**KV Cache 一句话：** 自回归生成是一个 Token 一个 Token 吐的，每步都要用到前文所有 Token 的 Key/Value。把它们**缓存下来**避免每步重算，就是 KV Cache，能大幅加速推理（也正因它占显存，长上下文更吃内存）——详见 [29-inference-optimization](29-inference-optimization.md)。

## 🔑 要点速记

- Transformer 取代 RNN 的两大杀手锏：**并行训练**（RNN 串行慢）+ **长距离依赖**（任意两词一步可达，不衰减）。
- **自注意力 = 每个 Token 环视全序列、按相关性加权聚合信息**（"这个词该重点看哪些词"）。
- **Q/K/V 直觉**：Query 问"我找什么"、Key 应"我是关于什么"、Value 给"实际信息"；带权检索式聚合。
- **多头**：多组注意力并行，从不同角度（指代/语法/呼应）看关系再拼接。
- **位置编码**：注意力本身**无序**（词袋），必须额外注入位置，模型才分得清"猫追狗 vs 狗追猫"。
- 三架构：**Encoder-only(BERT/理解) · Decoder-only(GPT/生成/主流) · Encoder-Decoder(T5/翻译)**。
- 生成式 LLM 都用 **Decoder-only**：单向续写与"预测下一个 Token"目标天然一致、易规模化。
- **注意力复杂度 O(n²)**：长上下文平方级变贵变慢 → 呼应 Token 计费与上下文窗口。
- **KV Cache** 缓存前文 K/V 加速自回归推理（详见 [29-inference-optimization](29-inference-optimization.md)）。

## ❓ 高频面试 / 理解题

**Q：Transformer 为什么能取代 RNN？自注意力解决了什么？**
A：RNN 逐词串行处理，① 无法并行导致训练慢、喂不下海量数据；② 长距离依赖靠逐格传递会衰减。自注意力让整句 Token **同时进入网络并行计算**，且任意两个词**两两直接相连、一步可达**，既能并行（训练快、可规模化）又能稳稳建模长距离依赖。这两点正是大模型能在万亿 Token 上训出来的架构前提。

**Q：用大白话讲讲自注意力和 Q/K/V。**
A：自注意力就是每个词处理时**环视句子里所有其它词，判断谁跟我相关，按相关性加权把它们的信息吸收进来**——比如处理"它"时给"猫"很高权重，模型就"知道"它指猫。实现上靠三个角色：**Query 是当前词发出的"我在找什么"、Key 是每个词挂出的"我是关于什么"标签、Value 是词携带的实际信息**；拿 Query 和所有 Key 比相似度得到权重，再加权汇总 Value。一句话：Query 问、Key 应、Value 给。

**Q：为什么需要位置编码？为什么现在的生成式大模型都是 Decoder-only？**
A：注意力只按内容算相关性、**本身不含顺序信息**（把输入当无序词袋），但"猫追狗≠狗追猫"，所以必须额外注入位置编码让模型分清词序。Decoder-only 盛行是因为它的**单向掩码注意力（只看左边）与 LLM"预测下一个 Token"的自回归目标完全一致**，训练即生成、结构简单统一、易堆参数、易做 KV Cache 加速；而双向的 Encoder-only（BERT）更适合理解/Embedding 类判别任务。

**Q：为什么长上下文又贵又慢？和架构有什么关系？**
A：因为自注意力要让每个 Token 和每个 Token 两两算相关性，复杂度是 **O(n²)**——序列长度翻 10 倍，注意力计算和显存约翻 100 倍。所以长 Prompt 推理更慢、按 Token 计费下更烧钱、且有上下文窗口上限。这也是为什么要做上下文工程（少而精地喂）和长上下文优化（FlashAttention、稀疏注意力、KV Cache 等）。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别以为"上下文越长越好"**：O(n²) 决定了长上下文平方级变贵变慢，且模型对超长上下文里的信息利用会打折（"中间遗忘"）——该做的是**上下文工程**精选内容（[06-context-engineering](06-context-engineering.md)），而非无脑塞满。
- ⚠️ **别混淆架构与任务**：Encoder-only(BERT) 不能用来"生成对话"，它是理解/Embedding 的；做生成就认准 Decoder-only。选 Embedding 模型和选对话模型是两条技术线。
- ✅ **把"注意力无序 → 需要位置编码"讲成因果链**，比只背"有位置编码"更显理解本质；这也是长上下文外推、RoPE 等话题的根。
- ✅ **理解 O(n²) 能反哺工程直觉**：能解释为什么要 KV Cache、为什么长文档要先检索再喂（RAG）而不是全塞进去、为什么 Prompt 要精简——都是在跟平方级开销较劲。
- ✅ **加分认知**：能说清"Decoder-only 的单向注意力恰好等价于'预测下一个 Token'的训练目标"，把架构选择和 LLM 本质（[01-llm-overview](01-llm-overview.md)）打通，比只会列三种架构更显功底。
