# 22 · Agent 原理与 ReAct（Agents & ReAct）

> Agent 是以 LLM 为"大脑"、能**自主规划 + 调工具 + 观察结果 + 多步迭代**直到完成目标的系统；**ReAct（Reasoning + Acting）** 是让它"边想边做"的经典范式。理解 Agent 循环与它"为什么不稳"，是 Agent 落地的核心。重要度 ⭐⭐⭐。

## 🎯 一句话核心

普通调用是"一问一答"，Agent 是给 LLM 装上**一个循环**：**思考下一步该做什么 → 选工具并给参数 → 执行 → 观察结果 → 没完成就回到思考**，如此反复直到达成目标。LLM 不再只是回答者，而是**在循环里自主决策"下一步做什么"的决策者**——强大也正因如此不稳。

## 📖 核心原理

**Agent = LLM（大脑）+ 工具（手脚）+ 记忆（状态）+ 规划循环（灵魂）。** 单次 LLM 调用是无状态的一问一答：给 Prompt、出答案、结束。Agent 的本质区别在于**加了一个反馈循环**——LLM 的输出不是最终答案，而是"下一步动作"（调哪个工具、传什么参数）；动作执行后的结果（Observation）又回喂给 LLM，让它据此决定再下一步。这样单个模型就能把一个大目标**拆成多步、逐步逼近**，而不是一口气蒙一个答案。四块缺一不可：工具让它能感知和改变外部世界（[20-function-calling](20-function-calling.md)），记忆让它跨步骤记住已知信息和中间结果（[25-agent-memory-planning](25-agent-memory-planning.md)），规划循环让它把这些串成"自主完成任务"的过程。

**ReAct 范式：把"推理"和"行动"交替编织在一起。** ReAct（Reason + Act）的关键洞见是——纯推理（只在脑子里想，像 CoT，[08-cot-reasoning](08-cot-reasoning.md)）会因为**缺乏与真实世界的交互而想偏、想错、编造事实**；纯行动（只调工具不推理）又会**盲目乱调、不知道为什么调、拿到结果也不会用**。ReAct 让两者**交替循环**：先 **Thought**（推理"要达成目标，我下一步该做什么、为什么"），再 **Action**（据推理调一个工具），再 **Observation**（读工具返回的真实结果），然后基于这个新事实**再 Thought**……直到推理出"信息够了，可以给最终答案"。推理为行动提供方向和依据，行动为推理注入真实世界的反馈来**纠偏和补充事实**——这正是它比纯 CoT 更能对付"需要查外部信息的多步任务"的原因：CoT 是"闭卷硬想"，ReAct 是"开卷边想边查"。

**为什么"推理+行动结合"是质变？** 因为它把 LLM 从"一次性生成器"变成"可以基于观察不断修正的决策者"。每一步的 Observation 都是真实世界给的反馈：查到的数据、API 的返回、报错信息——LLM 用它来判断上一步对不对、下一步往哪走。这让 Agent 具备了**处理不确定、路径不预知任务**的能力（"先查了才知道下一步查什么"）。但也正是这个"每步自主决定下一步"的自由度，带来了后面要讲的**不稳定与难落地**。

**Agent 的自主性是一条光谱，不是开关。** 从"固定流程、LLM 只填空"（Workflow）到"LLM 完全自主决定每一步和何时停止"（纯 Agent），中间有连续的自主度。自主度越高越灵活、越能处理开放任务，但也越不可预测、越难调试、成本越高。工程上的核心判断是：**这个任务到底需要多少自主性**——能用固定路径解决的，就别给它自由裁量权。

## 🔧 关键方法 / 流程 / 架构

**Agent 循环（ReAct 循环）——Agent 的心脏：**

```
          ┌─────────────────── 目标 Goal（用户任务）
          ▼
   ┌────────────┐
   │ ① 思考 Thought │  LLM 推理：为达成目标，下一步该做什么？为什么？
   └──────┬─────┘
          ▼
   ┌────────────────┐
   │ ② 选工具+参数 Action │  决定调用哪个工具、传什么参数（Function Calling）
   └──────┬─────────┘
          ▼
   ┌────────────┐
   │ ③ 执行 Execute │  应用层真正去调 API / 查库 / 算 / 搜
   └──────┬─────┘
          ▼
   ┌────────────────┐
   │ ④ 观察 Observation │  把工具返回结果喂回 LLM 作为新事实
   └──────┬─────────┘
          ▼
      完成了吗？──否──┐（且未超最大步数 / 预算）
          │           └──► 回到 ① 再思考（带上已有的 Thought/Action/Observation 历史）
          否→超上限：兜底退出（报错/降级/交人工）
          │
          是
          ▼
   ┌────────────┐
   │ ⑤ 输出 Final │  LLM 判定信息已足够，生成最终答案
   └────────────┘
```

关键点：**每一轮的 Thought/Action/Observation 都累加进上下文**（这就是记忆），LLM 每次思考都能看到之前所有步骤；循环**必须带最大步数/迭代上限**，否则可能永远不判定"完成"。

**一段极简伪代码（框架无关，看清循环本质）：**

```
history = [system_prompt(目标, 可用工具清单)]
for step in range(MAX_STEPS):          # ← 硬上限，防死循环
    thought, action = LLM(history)      # LLM 推理并决定下一步
    if action == FINISH:                # LLM 判定可以给答案
        return action.final_answer
    observation = execute_tool(action)  # 真正调工具，拿真实结果
    history += [thought, action, observation]   # 累加进记忆
return fallback()                       # 超上限 → 兜底（不能无限跑）
```

**Workflow vs Agent（工程取舍的核心）：**

| 维度 | Workflow（路径预定义） | Agent（自主决定路径） |
|---|---|---|
| 谁决定执行路径 | **开发者写死**（固定 DAG/流程） | **LLM 运行时自己决定** |
| 步骤/工具顺序 | 预先编排、可预测 | 每步动态选，路径不定 |
| 可预测性/可测试 | 高，易测、易复现 | 低，同输入可能走不同路径 |
| 成本/延迟 | 可控（步数固定） | 不可控（步数由 LLM 定，每步一次 LLM 调用） |
| 适合场景 | 流程明确、可拆成固定步骤 | 路径不预知、需临场判断的开放任务 |

> **工程铁律：能用 Workflow 就别用 Agent。** 大多数"看起来要 Agent"的需求，其实是可以拆成固定步骤的 Workflow（如"检索→总结→翻译"这种链）。只有当**路径真的无法预先确定**（"得先查了才知道下一步查什么"）时，才值得为自主性付出不稳定和成本的代价。编排模式与如何从 Workflow 渐进到 Agent，详见 [23-agent-patterns](23-agent-patterns.md)。

## 🔑 要点速记

- Agent = **LLM（大脑）+ 工具（手脚）+ 记忆（状态）+ 规划循环（灵魂）**；核心区别于一问一答的是**那个反馈循环**。
- **ReAct = Thought（想下一步）→ Action（调工具）→ Observation（看结果）交替循环**，直到推理出可给最终答案。
- ReAct 比纯 CoT 强在：**用真实世界反馈纠偏和补事实**（开卷边想边查 vs 闭卷硬想）。
- Agent 循环**必须带最大步数上限**，否则可能永不判定"完成"→ 死循环 / 成本爆炸。
- 每轮 Thought/Action/Observation **累加进上下文**，这就是 Agent 的短期记忆。
- 自主性是**光谱**（Workflow ↔ 纯 Agent），越自主越灵活也越不稳；**能用 Workflow 就别用 Agent**。
- Agent 的强大（自主多步）和不稳（错误累积/不可预测）**同源于"每步自主决定下一步"**。

## ❓ 高频面试 / 理解题

**Q：Agent 和普通的 LLM 一问一答、以及 Function Calling，本质区别是什么？**
A：一问一答是无状态单次调用，出了答案就结束。Function Calling（[20-function-calling](20-function-calling.md)）让 LLM 能"输出一次工具调用请求"，但它本身是**单步**能力。Agent 是在 Function Calling 之上**套了一个循环 + 记忆**：把"调工具→拿结果→再思考"反复迭代，让 LLM **自主地把大目标拆成多步、逐步完成**。一句话：Function Calling 是"能调一次工具"，Agent 是"能自己决定调几次、按什么顺序调、什么时候停"。

**Q：ReAct 为什么要把"推理"和"行动"结合？只推理（CoT）或只行动不行吗？**
A：纯推理（CoT）是"闭卷硬想"——没有外部反馈，容易想偏、编造事实，对需要查真实信息的任务无能为力；纯行动是盲目调工具，不知道为什么调、拿到结果也不会用。ReAct 让两者交替：**推理为行动指方向和依据，行动的 Observation 又用真实世界事实来纠正推理**。这样 Agent 能处理"先查了才知道下一步查什么"的多步不确定任务，比 CoT 更可靠、更能对付外部信息。

**Q：什么时候该用 Agent，什么时候该用 Workflow？**
A：判断标准是**执行路径能否预先确定**。路径明确、能拆成固定步骤的（检索→总结→翻译），用 Workflow——可预测、可测试、成本可控。只有当路径**无法预知、需要临场根据中间结果决定下一步**时，才用 Agent。原则是"能用 Workflow 就别用 Agent"，因为 Agent 的自主性带来不稳定、不可预测、成本和延迟失控的代价，不该为不需要的灵活性买单（详见 [23-agent-patterns](23-agent-patterns.md)）。

**Q：Agent 为什么难落地、不稳定？怎么兜底？**
A：根因是**多步自主决策**：每步都可能出错，且错误会沿链**累积和放大**（第 2 步查错，后面全跑偏）；LLM 可能永远不判定"完成"→ 无限循环；每步都调一次 LLM → 成本和延迟不可控；路径不定 → 不可预测、难复现、难调试。兜底手段：**最大步数/迭代上限 + 超时 + 成本预算上限**（硬止损）、**每步可观测 trace**（能回放定位）、**关键动作 Human-in-the-loop 人工确认**、**工具权限最小化**（[10-prompt-security](10-prompt-security.md)）、**失败回退/降级**。

## ⚠️ 易错点 / 实践建议

- ⚠️ **不给上限的 Agent 是定时炸弹**——一定要设**最大步数 + 超时 + 成本预算上限**三重硬止损，否则一次跑飞就可能烧掉大量 Token 或卡死。
- ⚠️ **别高估 Agent 的稳定性**：多步自主决策会让**单步的小错误沿链累积放大**，10 步里每步 95% 正确，整体成功率也只剩约 60%。步数越多越脆——**能少一步就少一步**。
- ✅ **可观测性是 Agent 的命根子**：每步的 Thought/Action/Observation 都要落 trace，否则出问题根本无法定位（Agent 天然难调试）。上生产前先把"能回放每一步"做好。
- ✅ **危险/不可逆动作必须 Human-in-the-loop**：删数据、发邮件、下单、转账等关键动作，让 Agent **停下来等人工确认**再执行，别让它全自动。
- ✅ **工具权限最小化**：只给 Agent 完成任务**必需**的工具和最小权限，工具描述里别暴露危险能力——这既降风险也降它"乱调工具"的概率（[10-prompt-security](10-prompt-security.md)）。
- ✅ **典型适用场景**：复杂任务自动化、需多步查询/推理的问答、多工具串联的流程（查天气→查日历→订会议室）。**加分认知**：说清"Agent 的强大和不稳同源于'每步自主决定下一步'"，比只会背 ReAct 三件套更显理解本质。
