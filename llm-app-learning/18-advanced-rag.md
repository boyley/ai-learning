# 18 · 高级 RAG 架构（Advanced RAG）

> Naive RAG（分块→向量检索→拼接→生成）在真实场景常"检索不准、上下文不全、多跳答不出"；高级 RAG 是一组**针对具体瓶颈的架构升级**——父子分块、HyDE、GraphRAG、Agentic RAG、多模态、查询路由、Self-RAG/CRAG。核心是**对症下药，不是堆技术**。重要度 ⭐⭐。

## 🎯 一句话核心

高级 RAG 不是"更高级的 RAG"，而是**围绕检索质量做的一系列针对性增强**：让"用来检索的东西"和"喂给 LLM 的东西"解耦（父子分块）、让 Agent 自己决定检不检索（Agentic）、让知识结构化成图以支持多跳（GraphRAG）、让系统能反思和纠错（Self-RAG/CRAG）——**每一招都对应 Naive RAG 的一个具体失败模式**。

## 📖 核心原理

**Naive RAG 的三大失败模式，是理解一切高级 RAG 的起点。** 标准 RAG 流程是"分块 → Embedding → 向量检索 Top-K → 拼进 Prompt → 生成"（全流程见 [14-rag-overview](14-rag-overview.md)）。它在三处最容易崩：

1. **检索不准**：用户问法和文档措辞不匹配（语义 gap），向量召回的块牛头不对马嘴；或块切得太大混入噪声、太小丢了上下文。
2. **上下文不全**：命中的块是精准了，但答案需要的周边信息（前后文、父章节）没带上，LLM"看得见片段却拼不出全貌"。
3. **多跳/全局问答弱**：像"A 和 B 有什么关系""总结整个文档集的核心主题"这类问题，答案分散在多个文档、需要跨块推理或全局归纳——Top-K 相似检索**天然只会捞回局部相似片段**，凑不出全局视图。

**高级 RAG 的演进动机，就是逐个拆掉这三堵墙。** 关键的思想转变有三个：

- **"检索用的表示"和"生成用的内容"应当解耦**——用最利于命中的形式去检索（小块、假设答案、摘要），用最利于回答的形式喂给 LLM（大块、父段落、原文）。这是父子分块 / Small-to-Big / HyDE 的共同内核。
- **知识不一定是"一堆扁平的块"**——可以是**图**（实体+关系），从而支持多跳推理和全局归纳，这是 GraphRAG。
- **检索不一定是"一次性、固定"的动作**——可以由 Agent **动态、多轮、带反思**地驱动，这是 Agentic RAG 与 Self-RAG/CRAG。

**但方向性原则要先立住：别过度设计。** 上面每一招都增加了工程复杂度、延迟和成本。绝大多数场景，**把 Naive RAG 的基本功（合理分块 + 混合检索 + Rerank）做扎实，效果就够用**；只有当你**用评估（[19-rag-evaluation](19-rag-evaluation.md)）定位到明确瓶颈**——比如召回率低、多跳题全错——再针对性上对应的高级架构。高级 RAG 是"哪疼治哪"，不是"全都用上"。

## 🔧 关键方法 / 流程 / 架构

**一、父子分块 / Small-to-Big / Sentence-Window——解耦"检索粒度"与"上下文粒度"**

核心思想一句话：**用小块检索（命中准），返回大块给 LLM（上下文全）**。这直接呼应分块篇（[15-chunking](15-chunking.md)）里"块大小的两难"——小块检索精准但上下文碎，大块上下文全但检索易混噪声。父子分块把两者的优点都拿走：

- **父子分块（Parent-Child / Small-to-Big）**：文档切成大"父块"，每个父块再切成小"子块"；**索引子块做检索**，命中后**用子块所属的父块**（或多个子块指向同一父块时去重合并）喂给 LLM。
- **Sentence-Window（句子窗口）**：以单句为检索粒度，命中后**向前后各扩 N 句**作为上下文返回。适合答案是"某一句"但需要邻句支撑的场景。

```
Naive：       [————大块————]  ← 既拿它检索又拿它生成（两头不讨好）

Small-to-Big：
  索引层  子块① 子块② 子块③   ← 小块，语义聚焦，检索命中准
             │（命中子块②）
  返回层  [—— 父块（含①②③）——] ← 大块，上下文完整，喂给 LLM
```

**二、HyDE（假设文档嵌入，Hypothetical Document Embeddings）**——先让 LLM 根据问题**生成一段"假设答案"**，再用这段假设答案（而非原始问题）去做向量检索，缩小"问句↔文档"的语义 gap。一句话带过，详见 [16-retrieval-optimization](16-retrieval-optimization.md)。

**三、GraphRAG——把知识建成图，支持多跳推理与全局问答**

针对"多跳/全局问答弱"这一失败模式。思路（以微软 GraphRAG 为代表）：

1. **索引期**：用 LLM 从文档中抽取**实体（entities）和关系（relations）**，构建**知识图谱**；再对图做**社区聚类（community detection，如 Leiden 算法）**，并让 LLM 为每个社区**预生成摘要**。
2. **查询期**分两种模式：
   - **Local search（局部）**：围绕问题相关的实体，沿图的边**多跳游走**，聚合邻域信息回答"A 与 B 如何关联"这类关系型/多跳问题。
   - **Global search（全局）**：面对"总结整个文档集的主题"这类**全局归纳**问题，直接**基于社区摘要做 map-reduce 式汇总**——这是 Top-K 向量检索做不到的，因为它从不"纵览全局"。

```
文档集 ──LLM抽取──> 实体-关系图 ──社区聚类+摘要──> 分层知识结构
                        │                            │
              Local：实体邻域多跳         Global：社区摘要 map-reduce
              （多跳关系问答）            （"整个文集讲了啥"全局归纳）
```

代价：索引期要跑大量 LLM 抽取，**建图贵、更新麻烦**；适合知识密集、需要关系推理/全局洞察的语料，不适合频繁变动或只需事实问答的场景。

**四、Agentic RAG——让 Agent 动态决定"检不检、检什么、检几次、够没够"**

Naive RAG 是"无脑检索一次"。Agentic RAG 把检索变成 Agent 手里的一个**工具**，由 Agent 用 ReAct 式循环（详见 [22-agent-react](22-agent-react.md)）自主编排：

- **是否检索**：简单问题（闲聊、常识）直接答，不浪费一次检索。
- **检索什么**：把复杂问题**拆成子问题**分别检索；或选择检索**哪个数据源**。
- **检索几次 / 够了没**：看回来的证据够不够，**不够就改写查询再检一轮**（多轮迭代检索），够了才生成——这是多跳问答的另一条路径（用迭代检索代替建图）。

```
问题 → Agent 判断 → 需要检索？──否──> 直接答
                        │是
                   选数据源/改写查询 → 检索 → 证据够吗？──否──┐
                        ▲                                      │(改写再检)
                        └──────────────────────────────────────┘
                                     │够
                                     ▼ 生成
```

**五、多模态 RAG（Multimodal RAG）**——语料含图片、图表、PDF 版面时，用**多模态 Embedding**（如 CLIP 类，把图文映射到同一向量空间，详见 [11-embedding](11-embedding.md)）实现"文字查图、图文混检"。两条常见路线：① 直接对图文做统一向量检索；② 先用多模态 LLM 把图**转成文字描述**再走文本 RAG。

**六、其它常用增强**

| 技术 | 解决什么 | 一句话机制 |
|---|---|---|
| **查询路由（Query Routing）** | 多数据源/多工具时"该查哪" | 用 LLM/分类器把问题路由到对应索引、数据库或工具 |
| **Self-RAG** | 检索质量与生成忠实度 | 生成时插入"反思 token"，自评"要不要检索/这条证据相关吗/回答有据吗" |
| **CRAG（Corrective RAG）** | 检索结果不靠谱时纠错 | 用轻量评估器给检索结果打分，差就触发**查询改写 / 转外部搜索**兜底 |
| **上下文压缩（Contextual Compression）** | 命中块太长、含噪声 | 检索后用 LLM/小模型**抽取或压缩**出真正相关的句子再喂给生成 |

## 🔑 要点速记

- Naive RAG 三大痛：**检索不准、上下文不全、多跳/全局问答弱**——高级 RAG 逐一对治。
- 核心思想：**"检索用的表示"与"生成用的内容"解耦**（父子分块、HyDE 都是这个内核）。
- **父子分块 / Small-to-Big / Sentence-Window**：小块检索命中准，返回父块/邻句给 LLM 保上下文全。
- **HyDE**：先生成假设答案再拿它检索，缩语义 gap（详见 [16-retrieval-optimization](16-retrieval-optimization.md)）。
- **GraphRAG**：抽实体关系建图 + 社区摘要；Local 多跳、Global 全局归纳，解 Top-K 做不到的全局问答。
- **Agentic RAG**：Agent 动态决定检不检、检什么、检几次、够没够，多轮迭代检索（[22-agent-react](22-agent-react)）。
- **多模态 RAG**：多模态 Embedding 实现图文混检（[11-embedding](11-embedding.md)）。
- 其它：**查询路由**（选数据源）、**Self-RAG/CRAG**（自评+纠错）、**上下文压缩**（去噪）。
- ⚠️ 铁律：先把 Naive RAG（分块+混合检索+Rerank）做好，**评估定位到瓶颈**再上对应高级架构。

## ❓ 高频面试 / 理解题

**Q：父子分块（Small-to-Big）为什么比"直接用大块"或"直接用小块"都好？**
A：因为它把**检索粒度和上下文粒度解耦**了。小块检索命中准（语义聚焦、噪声少），但直接把小块喂 LLM 会缺上下文；大块上下文全，但直接拿大块检索会因为混入多个主题而召回不准、命中率下降。父子分块**用小子块去命中、用其所属大父块去回答**，两头的优点都拿到——这是"用最利于检索的形式检索、用最利于回答的形式生成"这一通用思想的典型落地。

**Q：什么时候该上 GraphRAG，而普通向量 RAG 不行？**
A：当问题需要**多跳关系推理**（"A 通过谁和 C 产生关联"）或**全局归纳**（"总结整个文档集的核心主题/趋势"）时。Top-K 向量检索本质只捞"与问题局部相似的片段"，既不会跨多个实体串联推理，也从不纵览全局。GraphRAG 把知识抽成实体-关系图并做社区摘要，Local search 沿边多跳、Global search 基于社区摘要 map-reduce 汇总，正好补上这两块。代价是建图的 LLM 抽取成本高、更新麻烦，所以只在这类需求明确时才值得。

**Q：Agentic RAG 和 Naive RAG 最本质的区别是什么？**
A：检索从"**固定的一次性步骤**"变成"**Agent 可自主编排的动态工具**"。Naive RAG 不管问题难易都检索一次就生成；Agentic RAG 让 Agent 用 ReAct 循环自己判断：简单题不检索、复杂题拆子问题分别检、证据不够就改写查询再检一轮、够了才回答。它用**多轮迭代检索**换来了多跳问答能力和更少的无效检索，代价是更多 LLM 调用带来的延迟和成本。

**Q：这么多高级 RAG 技术，实际项目怎么选？**
A：**对症下药，别堆技术**。先把 Naive RAG 基本功（合理分块 + 混合检索 + Rerank）做扎实并**用评估量化**（[19-rag-evaluation](19-rag-evaluation.md)）；然后看瓶颈在哪：召回不准→HyDE/查询改写/父子分块；上下文碎→父子分块/Sentence-Window；多跳全局答不出→GraphRAG 或 Agentic 迭代检索；证据质量差→Self-RAG/CRAG；块太长有噪声→上下文压缩。**每一招都对应一个具体失败模式**，没瓶颈就别上，否则徒增延迟、成本和维护负担。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别一上来就堆高级架构**。GraphRAG、Agentic RAG 都显著增加延迟、成本和工程复杂度；90% 的项目把 Naive RAG（分块+混合检索+Rerank）做好就够，**先有明确瓶颈再针对性升级**。
- ⚠️ **没有评估就没有"高级"**。判断该上哪个技术、上了有没有变好，全靠离线评估（召回率、Faithfulness 等，详见 [19-rag-evaluation](19-rag-evaluation.md)）。凭感觉加技术等于盲人摸象。
- ✅ **父子分块几乎是"免费午餐"**：实现简单、几乎无副作用、普遍提升上下文完整度，是最该优先尝试的高级手段之一。
- ✅ **GraphRAG 不是万能药**：它建图贵、增量更新难，且对"简单事实问答"并不比向量 RAG 强；只在需要多跳推理/全局归纳的知识密集语料上才划算。可与向量 RAG **混合使用**（简单题走向量、复杂题走图）。
- ✅ **Agentic RAG 要控住循环成本**：动态多轮检索容易失控（反复检索不收敛），务必设**最大迭代轮数**和明确的"证据充分"停止条件，否则延迟和 Token 花费爆炸。
