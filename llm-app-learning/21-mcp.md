# 21 · MCP 模型上下文协议（Model Context Protocol）

> MCP 是 Anthropic 于 2024 年提出的**开放标准协议**，规范"AI 应用/Agent 如何统一接入外部工具、数据源与资源"；它之于 AI 集成，就像 **USB-C 之于外设、JDBC 之于数据库、LSP 之于编辑器**——定义一次标准接口，工具可插拔、跨模型跨框架复用。重要度 ⭐⭐⭐。

## 🎯 一句话核心

MCP 不是"让模型调工具的能力"（那是 Function Calling 的事），而是**"工具/数据如何被标准化地暴露和接入"的协议层**——它把"每个应用 × 每个工具都要单独写一遍集成"的 **M×N 爆炸，拉平成 M+N**：工具方写一个 MCP Server，任何支持 MCP 的客户端（Claude Desktop、IDE、各框架 Agent）都能直接用。

## 📖 核心原理

**MCP 要解决的是"集成碎片化"，不是"模型能力"。** 在没有统一标准前，你想让一个 AI 应用连上 GitHub、数据库、文件系统、内部 API，就得为**每个应用和每个工具的组合**单独写一份粘合代码；换个模型、换个框架，又要重写。假设有 M 个 AI 应用、N 个工具/数据源，集成工作量是 **M×N**——这就是**集成爆炸**。MCP 的做法和历史上所有成功的"标准接口"一样：让双方都对接同一套协议，工作量降为 **M+N**（每个应用实现一次 MCP Client，每个工具实现一次 MCP Server，任意组合即插即用）。

**类比能帮你秒懂它的定位：**
- **USB-C**：不管什么设备，插上同一个口就能用——工具对 AI 应用即插即用。
- **JDBC / ODBC**：Java 用一套 API 连任意数据库，换数据库不改业务代码——换模型/换框架不改工具集成。
- **LSP（Language Server Protocol）**：一个语言服务器写好，VS Code / JetBrains / Neovim 都能用——这正是 MCP 的直接精神来源（同为"N 个前端 × M 个后端 → N+M"）。

**MCP 是"协议"而非"库"，这一点很关键。** 它规定的是**通信契约**（消息格式、能力协商、传输方式），底层用 **JSON-RPC 2.0** 做消息编码，传输层支持 **stdio**（本地进程，如桌面应用拉起本地 Server）、**SSE / Streamable HTTP**（远程 Server）。正因为它只约定"怎么对话"，所以 Server 用什么语言写、跑在哪、内部怎么实现，客户端一概不关心——这才是"跨模型跨框架复用"的根基。

**MCP 与模型本身解耦。** 模型看到的仍然只是"一组工具的描述"，具体怎么发现这些工具、怎么把调用请求路由到真实的工具执行方、怎么拿回结果，都由 MCP 这一层标准化承接。换句话说，**Function Calling 负责"模型决定调哪个工具"，MCP 负责"这个工具从哪来、怎么被接进来"**（详见下文澄清）。

## 🔧 关键方法 / 流程 / 架构

**MCP 的三方角色与通信：**

```
┌──────────────────────────────┐         ┌────────────────────────────┐
│  MCP Host / Client（宿主侧）  │         │   MCP Server（工具方）      │
│  Claude Desktop / IDE / Agent │         │  暴露 Tools/Resources/Prompt│
│                               │         │                            │
│  ┌────────┐   ┌───────────┐   │  JSON-  │  ┌──────────────────────┐  │
│  │  LLM   │   │ MCP Client│◀──┼──RPC────┼─▶│  GitHub / DB / 文件   │  │
│  │(决定调) │──▶│ (一对一连)│   │ stdio / │  │  内部API / 检索 ...   │  │
│  └────────┘   └───────────┘   │ SSE/HTTP│  └──────────────────────┘  │
└──────────────────────────────┘         └────────────────────────────┘
   Host 内可挂多个 Client，每个 Client ↔ 一个 Server（1:1）
```

- **Host**：用户直接使用的宿主应用（Claude Desktop、IDE、某个 Agent 应用），负责管理若干 Client、承载 LLM、做权限与编排。
- **Client**：Host 内的连接器，与**一个** Server 保持 1:1 会话，负责能力协商与消息收发。
- **Server**：把某个系统的能力按 MCP 规范暴露出来的独立进程/服务。

**从 M×N 到 M+N（这张图是 MCP 存在的全部理由）：**

```
❌ 没有 MCP：M×N 条私有集成         ✅ 有 MCP：M+N 条标准对接
应用A ─┬─ GitHub                    应用A ─┐
应用A ─┼─ 数据库                    应用B ─┼─▶【 MCP 标准 】◀─┬─ GitHub-Server
应用A ─┴─ 文件系统                  应用C ─┘                └─ 数据库-Server
应用B ─┬─ GitHub  (又写一遍)                                └─ 文件-Server
应用B ─┼─ 数据库  (又写一遍)         每个应用只实现 1 次 Client，
应用B ─┴─ 文件系统 (又写一遍)        每个工具只实现 1 次 Server，任意组合复用
   连线数 = M × N                       连线数 = M + N
```

**MCP Server 暴露的三类能力（务必分清）：**

| 能力 | 是什么 | 谁来触发 | 类比 |
|---|---|---|---|
| **Tools** | 可被调用的函数/动作（查 API、写文件、执行查询） | **模型**决定调用（经 Function Calling） | 可执行的 API |
| **Resources** | 可读取的数据/上下文（文件、记录、文档片段） | **应用/用户**选择加载 | 只读的 GET 资源 |
| **Prompts** | 可复用的提示模板/工作流（预置指令） | **用户**主动选用 | 预设的命令/模板 |

> 一句话记忆：**Tools 是"模型能做的动作"，Resources 是"能读的数据"，Prompts 是"能套的模板"**——三者共同构成 Server 对外的"能力清单"。

**一次典型交互流程：**

```
① Host 启动 → Client 连上 Server → 能力协商（Server 报出有哪些 Tools/Resources/Prompts）
② 用户提问 → Host 把可用 Tools 的描述随请求给到 LLM
③ LLM 通过 Function Calling 决定"调用某工具 + 参数"
④ Client 按 MCP 协议把调用转发给 Server → Server 执行 → 回传结果
⑤ 结果作为上下文喂回 LLM → LLM 生成最终回答
```

## 🔑 要点速记

- MCP = **开放标准协议**（Anthropic 2024），统一"AI 应用如何接入外部工具/数据/资源"。
- 核心价值：把集成从 **M×N 爆炸拉平成 M+N**——写一次 Server，所有 MCP 客户端通用。
- 类比：**USB-C（外设即插即用）/ JDBC（换库不改码）/ LSP（一服务多编辑器）**。
- 架构三角色：**Host（宿主）→ Client（1:1 连接器）→ Server（暴露能力方）**。
- 传输与编码：**JSON-RPC 2.0** 消息 + **stdio / SSE / Streamable HTTP** 传输。
- Server 三类能力：**Tools（可调函数）、Resources（可读数据）、Prompts（可复用模板）**。
- 与 Function Calling **互补不冲突**：FC 是模型级"决定调用"，MCP 是集成级"标准暴露/接入"；Server 的工具最终仍由 FC 触发（详见 [20-function-calling](20-function-calling.md)）。
- 生态意义：**一次写 Server，Claude Desktop / IDE / 各框架 Agent 都能用**，跨模型跨框架复用。

## ❓ 高频面试 / 理解题

**Q：MCP 和 Function Calling 是一回事吗？有了 Function Calling 为什么还要 MCP？**
A：**不是一回事，二者在不同层次、互补。** Function Calling 是**模型级能力**——模型根据工具描述"决定要调哪个工具、传什么参数"（详见 [20-function-calling](20-function-calling.md)）；MCP 是**集成级协议**——规范"工具/数据源如何被标准化地暴露出来、如何被应用发现和接入"。没有 MCP，你每接一个工具都要为特定应用手写一遍集成（M×N）；有了 MCP，工具方写一个 Server 就能被所有 MCP 客户端复用（M+N）。而且 **MCP Server 暴露的 Tools，最终仍然是通过 Function Calling 被模型调用的**——MCP 解决"工具从哪来、怎么接进来"，FC 解决"模型决定调哪个"，两者配合完成一次工具调用。

**Q：MCP 到底解决了什么痛点？为什么说它像 USB-C / LSP？**
A：解决**集成碎片化（M×N 爆炸）**。过去 M 个 AI 应用要各自对接 N 个工具，组合是 M×N，换模型换框架还得重写。MCP 让双方都对接同一套标准协议，工作量降为 M+N。这和 USB-C（任何设备一个口）、JDBC（一套 API 连任意数据库）、LSP（一个语言服务器服务所有编辑器）是同一个思想：**用统一接口消除 N×M 的私有适配**，实现工具可插拔、跨端复用。

**Q：MCP Server 能暴露哪几类能力，分别谁触发？**
A：三类。**Tools**——可调用的函数/动作，由**模型**经 Function Calling 决定调用；**Resources**——可读取的只读数据/上下文（文件、记录），由**应用/用户**选择加载进上下文；**Prompts**——可复用的提示模板/工作流，由**用户**主动选用。分清"谁触发"是理解 MCP 的关键：只有 Tools 是模型自主调用的。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别把 MCP 当成"让模型会调工具的技术"**——那是 Function Calling。MCP 是**协议/标准**，管的是"工具怎么被标准化暴露和接入"，不替代也不包含模型的调用决策能力。
- ⚠️ **别混淆 Tools 与 Resources**：Tools 是"模型可执行的动作"（有副作用、模型自主调），Resources 是"可读的数据"（只读、由应用/用户加载）——设计 Server 时把只读数据错误地做成 Tool，会让模型无谓地"决定要不要读"，增加不确定性。
- ⚠️ **安全是重中之重**：MCP Server 往往能访问文件、数据库、内部 API，一旦接入不可信 Server 或其返回内容里藏有恶意指令，就可能触发**间接提示注入（indirect prompt injection）**——被读取的"数据/工具结果"里夹带指令，诱导模型执行越权操作。务必**只接可信 Server、对工具做权限最小化、对返回内容做隔离与校验、敏感动作加人工确认**（详见 [10-prompt-security](10-prompt-security.md)）。
- ✅ **传输选型**：本地工具（文件、本机命令）用 **stdio**（Host 直接拉起进程，简单低延迟）；远程/多用户共享服务用 **SSE / Streamable HTTP**（可跨网络、可鉴权）。
- ✅ **加分认知**：能一句话说清"**MCP 把 M×N 集成拉平成 M+N，是集成层协议；Function Calling 是模型层能力，Server 的工具最终仍由 FC 触发**"，就抓住了它和工具调用生态的关系本质——这也是它能"一次编写、处处复用"的根本原因。
