# 29 · 推理优化与部署（Inference Optimization）

> 大模型推理慢且贵，根源是**自回归逐 Token 生成 + 显存受限**；优化分**引擎层**（KV Cache / 量化 / Continuous Batching / 投机解码）和**应用层**（缓存 / 限长 / 精简 Prompt / 分级路由），**应用者最该先做后者**。重要度 ⭐⭐。

## 🎯 一句话核心

推理慢不是因为"模型在思考"，而是因为它必须**一个 Token 一个 Token 地串行往外吐**，每吐一个都要把整个模型的权重从显存搬一遍——所以推理是**显存带宽受限（memory-bound）** 的活，优化的本质就是**少算、少搬、多并行、少调用**。

## 📖 核心原理

**为什么推理慢/贵？根子在自回归。** LLM 生成是"预测下一个 Token"的循环（详见 [04-sampling-decoding](04-sampling-decoding.md)）：生成第 N 个 Token 必须先有前 N-1 个，天生**串行、无法并行**。生成 500 个 Token 就要跑 500 次前向传播，每次都要把千亿级权重从显存读进计算单元。因此推理瓶颈通常不在算力（compute）而在**显存带宽（memory bandwidth）**——GPU 算得快，但"搬权重"搬不过来，算力大量空转。这也是为什么衡量推理有两个关键指标：**TTFT（首 Token 延迟）** 和 **TPOT/ITL（每个后续 Token 的间隔）**。

**推理分两阶段，性格截然相反（理解优化的前提）：**

- **Prefill（预填充）**：把用户输入的整段 Prompt 一次性喂进去，**所有输入 Token 可以并行计算**（像做阅读理解，一眼扫完全文），算得快、是 **compute-bound**。它决定 **TTFT**。
- **Decode（解码）**：从第一个输出 Token 开始，**逐个串行生成**，每步只处理 1 个新 Token 却要重读全部权重，是 **memory-bound**、慢。它决定后续吐字速度。

一句话：**Prefill 快而并行，Decode 慢而串行**——大部分推理优化都在啃 Decode 这块硬骨头。

**显存（VRAM）是硬约束。** 显存要同时装下三样东西：①**模型权重**（如 13B 模型 FP16 约 26GB）；②**KV Cache**（随上下文长度和并发数线性膨胀）；③激活值。显存不够就跑不起来、或并发上不去。所以推理优化很多时候是在"**省显存**"和"**省时间**"之间做文章——量化省的是权重显存，Continuous Batching 提的是显存利用率下的吞吐。

## 🔧 关键方法 / 流程 / 架构

**Prefill / Decode 两阶段 + 各层优化手段示意：**

```
用户输入 "帮我总结这篇文章：……（长文）"
        │
        ▼
┌───────────────────────────────┐
│ ① Prefill 预填充                │  整段输入并行算 → 快
│   把 Prompt 所有 Token 一次过    │  compute-bound，决定 TTFT
│   算出并缓存它们的 K/V ──────────┼──▶ 存入 KV Cache
└───────────────────────────────┘
        │  产出第 1 个输出 Token
        ▼
┌───────────────────────────────┐   ← 循环，逐 Token 串行
│ ② Decode 解码                   │  每步只算 1 个新 Token → 慢
│   读 KV Cache（不重算历史）      │  memory-bound，决定 TPOT
│   算新 Token 的 K/V，追加进缓存   │
└───────────────────────────────┘
        │  重复直到 EOS 或 max_tokens
        ▼
      完整回答（流式逐字返回）

优化落点：
  引擎层 ── KV Cache（免重算） · 量化（省显存/提速）
           · Continuous Batching（提吞吐） · 投机解码（提速）
  应用层 ── 语义/结果缓存 · 限 max_tokens · 精简 Prompt · 分级路由 · 流式输出
```

**引擎层优化（自托管时引擎已内置，了解原理即可）：**

| 手段 | 解决什么 | 一句话原理 |
|---|---|---|
| **KV Cache** | Decode 重复计算 | 缓存历史 Token 的 K/V，每步只算新 Token，**推理加速的核心** |
| **量化 Quantization** | 权重占显存大 | 权重从 FP16 降到 INT8/INT4，省显存、提速，精度小损 |
| **Continuous Batching** | GPU 空转、吞吐低 | 请求动态拼批、谁先完谁先走，提高显存/算力利用率 |
| **投机解码 Speculative Decoding** | Decode 串行慢 | 小模型草稿 + 大模型并行验证，一步吐多个 Token |

**① KV Cache（推理加速核心，呼应注意力机制）。** 注意力里每个 Token 都要算 Key/Value 向量（详见 [02-transformer-attention](02-transformer-attention.md)）。Decode 时如果每步都把历史所有 Token 的 K/V 重算一遍，复杂度是 O(N²) 的浪费。**KV Cache 就是把已生成 Token 的 K/V 存起来**，每步只算当前新 Token 的 K/V 并追加，历史直接读缓存——把每步计算从"重算全序列"降到"只算一个"。代价是**吃显存**：KV Cache 大小 ∝ 上下文长度 × 层数 × 并发数，**上下文越长、并发越高，显存越紧张**（这也是长上下文贵、易 OOM 的直接原因）。

**② 量化 Quantization（让大模型跑在小显卡）。** 权重默认 FP16（16 位）。量化把它压到 INT8（8 位）甚至 INT4（4 位），显存直接砍半/砍到 1/4，搬权重也更快（memory-bound 场景直接提速），而精度损失通常很小（INT8 几乎无感，INT4 略有损）。这让 70B 大模型能塞进单张消费级显卡。量化也和微调结合——**QLoRA 就是在 4-bit 量化的基座上做 LoRA 微调**，大幅降低微调显存门槛（详见 [28-fine-tuning](28-fine-tuning.md)）。

**③ Continuous Batching + PagedAttention（vLLM 思路）。** 传统静态批处理要等一批请求凑齐、且必须等最慢的那条生成完才整批释放，GPU 大量空转。**Continuous Batching（连续批处理）** 改成 Token 级动态调度：某条请求生成完就立刻退出、腾出的槽位马上塞新请求进来，吞吐大幅提升。配套的 **PagedAttention** 借鉴操作系统虚拟内存分页，把 KV Cache 切成小块非连续存储，消除显存碎片、支持更高并发——这是 vLLM 高吞吐的核心。

**④ 投机解码 Speculative Decoding。** 用一个**小而快的草稿模型**一口气猜出后面几个 Token，再让**大模型一次并行验证**这几个 Token（验证是 Prefill 式的并行，快）：猜对的直接采纳，猜错的从错处回退重来。因为"验证一批"比"逐个生成一批"便宜，平均下来大模型少跑好几次前向，实测常有 2~3 倍加速，**且输出分布与原模型一致**（无损加速）。

**应用层降本提速（重点——应用者不碰引擎也能立刻见效）：**

- **语义缓存 / 结果缓存**：把"问题→回答"存起来，重复或高度相似的问题**直接返回缓存**，不再调模型。精确缓存按输入哈希命中；**语义缓存**用 Embedding 相似度命中"意思相同但措辞不同"的问题（如客服 FAQ），命中即零 Token 零延迟。是 ROI 最高的一招。
- **限 `max_tokens`**：输出越长、Decode 步数越多、越慢越贵。按场景压死输出上限（分类任务给几十、摘要给几百），别放任模型长篇大论。
- **精简上下文 / Prompt**：输入 Token 直接决定 Prefill 成本和 KV Cache 占用。删冗余 few-shot、压缩历史、只塞相关检索片段（上下文工程详见 [06-context-engineering](06-context-engineering.md)）——省钱又降延迟，还能提质量。
- **分级路由（model routing）**：不是所有请求都需要最强模型。**简单请求走小/便宜/快模型，复杂请求才升级到大模型**（可用规则或一个轻量分类器判断难度）。是成本与质量平衡的关键杠杆。
- **流式输出（streaming）**：不改总耗时，但**首字更快到达**，用户感知延迟大幅下降——体验优化的标配。
- **Prompt Caching**：多请求共享的固定前缀（长 system prompt、大段文档）可复用其 Prefill 结果，主流 API 已支持，省钱又降 TTFT。

**部署选择：API vs 自托管。**

| 维度 | 调 API（GPT/Claude/通义） | 自托管（vLLM / TGI / Ollama） |
|---|---|---|
| **上手** | 开箱即用、无需运维 | 要 GPU、要运维调优 |
| **成本** | 按 Token 付费，量大后偏贵 | 前期硬件投入，高并发下单位成本更低 |
| **隐私** | 数据出域（需评估合规） | **数据不出域**，私有化，合规友好 |
| **能力** | 最强闭源模型、随平台升级 | 只能用开源模型，可自由微调/量化 |
| **延迟/可控** | 受网络与限流影响 | 可控、可就近部署，但要自己保稳定 |

> 经验：**先用 API 快速验证需求**；当调用量大到成本敏感、或数据合规要求私有化、或需要深度定制微调时，再评估自托管。中间态可用 Ollama 本地起小模型做开发/离线场景。落地代码见框架库 `../spring-ai-learning`。

## 🔑 要点速记

- 推理慢的根：**自回归逐 Token 串行**，且 Decode 阶段**显存带宽受限**（搬权重比算还慢）。
- 两阶段：**Prefill 并行快（定 TTFT，compute-bound）/ Decode 串行慢（定 TPOT，memory-bound）**。
- **KV Cache = 推理加速核心**：缓存历史 K/V 免重算；代价是吃显存，上下文/并发越大越吃。
- **量化**：FP16→INT8/INT4，省显存提速、精度小损，让大模型上小显卡；QLoRA 结合微调。
- **Continuous Batching + PagedAttention**（vLLM）：Token 级动态拼批 + 分页显存，提吞吐。
- **投机解码**：小模型草稿 + 大模型并行验证，无损 2~3 倍加速。
- 应用层最该做：**语义/结果缓存、限 max_tokens、精简 Prompt、分级路由、流式输出**。
- 部署：**API 省心贵、自托管私有可控**；先 API 验证，量大/合规/定制再自托管。

## ❓ 高频面试 / 理解题

**Q：大模型推理为什么慢？瓶颈到底在哪？**
A：根在**自回归**——生成第 N 个 Token 必须等前 N-1 个都出来，天生串行，生成 N 个 Token 就要跑 N 次前向。而单次前向在 **Decode 阶段是显存带宽受限**：每步只处理一个新 Token，却要把整个模型权重从显存搬一遍，GPU 算力大量空转，瓶颈是"搬权重"而非"算"。所以优化围绕**少搬（量化）、少算（KV Cache）、多并行（批处理/投机解码）** 展开。

**Q：Prefill 和 Decode 有什么区别？为什么要分开看？**
A：Prefill 是把整段输入 Prompt 一次喂入，**所有输入 Token 并行计算**，快、compute-bound，决定首 Token 延迟 TTFT；Decode 是从第一个输出开始**逐 Token 串行生成**，每步只算一个新 Token 却要重读全部权重，慢、memory-bound，决定后续吐字速度 TPOT。分开看是因为二者瓶颈不同、优化手段不同——大多数推理优化（KV Cache、投机解码、Continuous Batching）都在啃 Decode。

**Q：KV Cache 是什么？为什么它是推理加速核心，又为什么吃显存？**
A：注意力里每个 Token 要算 Key/Value 向量，Decode 若每步重算历史所有 Token 的 K/V 就是 O(N²) 浪费。KV Cache 把已生成 Token 的 K/V 缓存起来，每步只算当前新 Token 的、历史直接读缓存，把每步从"重算全序列"降到"只算一个"，所以是加速核心。代价是它占显存且大小正比于 **上下文长度 × 层数 × 并发数**——长上下文和高并发会让显存吃紧甚至 OOM，这正是长上下文贵的直接原因。

**Q：作为应用开发者（不碰 GPU），怎么给大模型应用降本提速？**
A：优先做应用层：①**语义/结果缓存**——重复或相似问答直接返回，零 Token 零延迟，ROI 最高；②**限 max_tokens**——输出越长越慢越贵；③**精简 Prompt/上下文**——直接砍 Prefill 成本和 KV Cache；④**分级路由**——简单请求走便宜小模型，复杂的才上大模型；⑤**流式输出**——不减总耗时但让首字快到，改善体验。引擎层（量化、批处理）交给 vLLM 等自托管方案或 API 平台。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别一上来就自托管折腾 GPU**：先用 API 验证产品需求，等调用量大到成本敏感、或有合规/定制刚需再自托管，否则运维成本吞掉一切收益。
- ⚠️ **别忽视 max_tokens 和 Prompt 长度**：很多"太贵/太慢"其实是放任了超长输出和臃肿上下文——这俩是应用层最容易漏的省钱开关。
- ⚠️ **语义缓存要控相似度阈值**：阈值太松会把"意思不同但措辞像"的问题错误命中、返回错答案；对结果准确性敏感的场景要收紧阈值或加校验。
- ✅ **量化按场景选精度**：追求几乎无损用 INT8；显存极度紧张、可接受轻微质量下降再上 INT4；关键任务先小样本评估量化后的质量再上线。
- ✅ **长上下文要盯显存**：KV Cache 随上下文和并发线性涨，长文档/高并发场景优先评估显存和成本，必要时靠精简上下文而非无脑塞满窗口。
- ✅ **加分认知**：能说清"推理是 memory-bound、瓶颈在搬权重不在算"，比只会背"KV Cache 加速"更显理解本质——这也解释了量化（少搬）和批处理（一次搬多用）为何有效。
