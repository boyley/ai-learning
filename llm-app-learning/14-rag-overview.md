# 14 · RAG 概览与动机（RAG Overview）

> RAG（Retrieval-Augmented Generation，检索增强生成）= **先从外部知识库检索相关内容，拼进 Prompt，让 LLM 基于这些内容作答**。它把"闭卷靠记忆"的 LLM 变成"开卷查资料再答"，是治幻觉、补私域知识、可溯源的主流工程手段。本篇是整个 RAG 阶段的总纲。重要度 ⭐⭐⭐。

## 🎯 一句话核心

LLM 本质是"闭卷考试"——只能凭训练时压进参数的记忆答题，记不清就**一本正经地编**。RAG 的做法是把考试改成**"开卷"**：答题前先去**知识库里翻出相关的几页资料**，连同问题一起递给模型，让它**照着资料写答案并标出处**。一句话：**RAG 不改变模型本身，而是在"提问的那一刻"临时给它喂进正确依据**——所以能补最新/私域知识、能溯源、能压幻觉，且比微调便宜灵活得多。

## 📖 核心原理

**RAG 要解决的根本矛盾是：LLM 的知识是"烧进参数、静态、封闭"的，而真实应用要回答的问题却是"最新的、私域的、要有出处的"。** 大模型的知识来自预训练（详见 [01-llm-overview](01-llm-overview.md)），有三个硬边界：①**时效**——知识停在训练截止日，之后的事一概不知；②**私域**——你公司的文档、产品手册、内部规章，模型从没见过；③**幻觉**——模型是概率续写器，记不清时会编造看似合理实则错误的内容（详见 [05-hallucination](05-hallucination.md)）。这三点无法靠"把模型做得更大"根治，因为它们是"参数化记忆"这种存储方式的固有缺陷。

**RAG 的核心洞见：把"知识"从"参数（记忆）"里搬到"外部知识库（可查的资料）"里，让 LLM 只负责它真正擅长的事——"基于给定材料的语言理解与生成"，而不是"当数据库背事实"。** 这正是 LLM 的能力甜区：它不擅长精确记忆海量事实，但极擅长**读懂一段材料并据此组织答案**。RAG 顺应了这个特性——检索系统负责"找对资料"（这是信息检索的强项），LLM 负责"读懂资料、组织成人话"（这是它的强项），二者各司其职。

**从信息流角度看，RAG 本质是一种"运行时的上下文注入"**：不修改模型权重，而是在**推理时**动态地把相关知识塞进 Prompt 的上下文窗口（这属于上下文工程的一种，详见 [06-context-engineering](06-context-engineering.md)）。所以 RAG 是"外挂知识"，微调是"内化能力"——一个改输入、一个改模型。也正因为知识在库里而不在参数里，**更新知识只需更新知识库（增删文档、重建索引），无需重新训练模型**，这是 RAG 相对微调最大的工程优势。

**RAG 的上限 = 检索质量，而非生成质量。** 这是全篇最该记住的一句话：RAG 是"检索"和"生成"两段的串联，**只要第一段没把正确依据检索出来，第二段的 LLM 再强也无米下炊**——它要么基于错误/无关的检索结果继续编，要么答"资料里没有"。生产中 80% 的 RAG 效果问题出在检索侧（分块烂、召回不全、排序不准），而非 LLM 侧。这也是为什么后续几篇（分块、检索优化、Rerank）全在打磨"检索"——把正确依据可靠地送到 LLM 面前，才是 RAG 工程的主战场。

## 🔧 关键方法 / 流程 / 架构

**RAG 全流程分两条线：离线索引（Indexing，把知识库预处理成可检索的向量）+ 在线检索生成（Retrieval & Generation，实时回答提问）。** 二者的桥梁是**同一个 Embedding 模型**——离线把文档编码成向量存起来，在线把问题编码成向量去比对，语义相近的才能匹配上（Embedding 原理详见 [11-embedding](11-embedding.md)）。

```
════════ 离线：索引阶段（Indexing，建库，提前做一次）════════

  原始文档                                          向量数据库
 (PDF/Word/                                        ┌──────────┐
  网页/DB)   ①加载   ②分块      ③Embedding         │ vec + 原文│
    │ ─────▶ Load ─▶ Chunk ───▶ 每块→向量 ────────▶│ + 元数据  │
    │       解析文本  切成小片    (同一编码模型)      │(HNSW索引) │
    │                  ▲                            └──────────┘
    │              [15-chunking]                         ▲
    │           切多大/重叠/按语义                         │
    └─────────────────────────────────────────────────────┘

════════ 在线：检索 + 生成阶段（每次提问实时跑）════════

  用户提问
    │ ④ 问题→Embedding（同一模型）
    ▼
  查询向量 ──⑤ 向量检索 Top-K──▶ [向量库] ──▶ 召回 K 个候选片段
    │                              ▲
    │                       [16-retrieval-optimization]
    │                    混合检索(向量+BM25)/query改写/多路召回
    ▼
  ⑥ Rerank 精排  ◀── [17-rerank] cross-encoder 从粗召回里挑最相关的 top-n
    │
    ▼
  ⑦ 拼 Prompt：  ┌─────────────────────────────────┐
                 │ 系统指令：只依据下列资料作答，   │
                 │          不知道就说不知道         │
                 │ 【资料】<检索到的 top-n 片段>     │
                 │ 【问题】<用户提问>                │
                 └─────────────────────────────────┘
    │
    ▼
  ⑧ LLM 生成 ──▶ ⑨ 带出处的答案（citation，标明来自哪篇/哪段）
                              │
                        [19-rag-evaluation]
                   检索指标 + 生成指标(faithfulness) 闭环评估
```

**逐步拆解（每步都有专篇深入，本篇只讲它在全局的作用）：**

| 步骤 | 做什么 | 为什么关键 | 深入篇 |
|---|---|---|---|
| ② 分块 Chunk | 把长文档切成小片段 | 太大→检索不精准且塞不下；太小→语义割裂丢上下文 | [15-chunking](15-chunking.md) |
| ③④ Embedding | 文档块/问题都编码成向量 | 让"语义相近"变成"向量距离近"，才能按含义检索 | [11-embedding](11-embedding.md) |
| ⑤ 向量检索 Top-K | 算问题向量与库中向量的相似度，取最近 K 个 | 召回的"广度"，宁多勿漏（后面还能精排） | [16-retrieval-optimization](16-retrieval-optimization.md) |
| ⑥ Rerank 重排 | 用更强的模型对 K 个候选精排，取 top-n | 召回的"精度"，把最相关的挤到最前面 | [17-rerank](17-rerank.md) |
| ⑦ 拼 Prompt | 检索片段 + 问题 + 指令组装成上下文 | 指令必须强约束"只依据资料作答"才能压幻觉 | [06-context-engineering](06-context-engineering.md) |
| ⑧⑨ 生成 + 溯源 | LLM 基于资料作答并标注出处 | 答案可核查，是 RAG 相对纯 LLM 的核心增值 | — |
| 🔁 评估 | 分别量化"检索准不准"和"答得忠不忠于资料" | 出问题时能定位是检索坏还是生成坏 | [19-rag-evaluation](19-rag-evaluation.md) |

**一段极简伪代码（框架无关，只为看清数据流；具体框架实现链 `../spring-ai-learning`）：**

```
# ── 离线：建库 ──
for doc in docs:
    for chunk in split(doc):                 # ② 分块
        vec = embed(chunk)                    # ③ 编码
        vector_db.add(vec, text=chunk, meta=doc.source)   # 存向量+原文+出处

# ── 在线：回答 ──
def answer(question):
    q_vec      = embed(question)                       # ④ 问题编码
    candidates = vector_db.search(q_vec, k=20)         # ⑤ 粗召回 Top-K
    passages   = rerank(question, candidates)[:5]      # ⑥ 精排取 top-5
    prompt = f"""只依据下列资料回答，无法回答就说"资料中未提及"。
    【资料】{passages}
    【问题】{question}"""
    return llm(prompt)                                 # ⑧ 基于资料生成
```

**RAG vs 微调 vs 长上下文——三条"给模型补知识/改行为"的路，怎么选：**

| 维度 | RAG（检索增强） | 微调 Fine-tuning | 长上下文直塞 |
|---|---|---|---|
| **改的是什么** | 改**输入**（外挂知识） | 改**模型权重**（内化能力/风格） | 改**输入**（把资料全塞进上下文） |
| **最适合** | 补**动态/私域/海量事实**知识 | 教**新能力、固定风格、专有格式**、领域语感 | 资料**少且每次都要全量**看（如单篇长文问答） |
| **知识更新** | ✅ 改库即可，实时 | ❌ 要重新训练，慢且贵 | ✅ 换输入即可 |
| **可溯源** | ✅ 能标出处 | ❌ 说不清依据 | ⚠️ 能，但常"Lost in Middle" |
| **成本** | 中（建库+每次检索） | 高（训练+数据标注） | 高（长 Prompt 每次都烧 Token，且贵） |
| **容量** | ✅ 海量（知识库无上限） | 参数容量有限 | ❌ 受上下文窗口硬限制，放不下大知识库 |
| **典型短板** | 检索不准就全盘皆输 | 学不进大量事实性知识，易过拟合 | 贵；**Lost in Middle**（塞太多，中间的被忽略）；放不下 |

> **为什么通常"先 RAG"？** 成本从低到高是 **Prompt < RAG < 微调**（详见 [28-fine-tuning](28-fine-tuning.md) 的选型决策）。补**知识**类需求（最新资讯、私域文档、事实问答）几乎都该先上 RAG——便宜、可溯源、改库即更新；只有当需求是"改模型的**能力/风格/输出格式**"（如学会一种专有 DSL、固定客服话术、领域语气），RAG 无能为力时才考虑微调。长上下文直塞则适合"资料就一两篇、每次都要通读"的场景，一旦知识量大就会**贵 + Lost in Middle + 放不下**，此时反而要靠 RAG 先"筛出相关的几段"再塞。三者也常**组合**用：微调过的模型 + RAG 检索 + 精心设计的 Prompt。

## 🔑 要点速记

- **RAG = 检索（找依据）+ 增强（拼进 Prompt）+ 生成（据此作答）**；类比"开卷考试"，不改模型只改输入。
- **五大动机**：①治幻觉（给依据）②补知识时效（越过训练截止日）③接私域/企业知识（模型没学过）④可溯源（标出处、可核查）⑤比微调便宜灵活（改库即更新）。
- **两条线一座桥**：离线索引（加载→分块→Embedding→存向量库）+ 在线检索生成（问题 Embedding→检索 Top-K→Rerank→拼 Prompt→生成→溯源）；桥 = 同一个 Embedding 模型。
- **RAG 的上限 = 检索质量**：正确依据没检索到，LLM 再强也白搭；生产 80% 问题在检索侧。
- **召回广度 vs 排序精度**：先向量检索粗召回（宁多勿漏），再 Rerank 精排（挤出最相关）——两阶段。
- **RAG vs 微调**：RAG 改输入补**知识**（动态/可溯源/便宜），微调改权重改**能力/风格**（静态/贵/内化）。
- **RAG vs 长上下文**：知识量大时长上下文会**贵 + Lost in Middle + 放不下**，RAG 先筛后塞更划算。
- 选型口诀：**能 Prompt 就别 RAG，能 RAG 就别微调**（成本从低到高）；补知识→RAG，改能力→微调。

## ❓ 高频面试 / 理解题

**Q：什么是 RAG？用一句话讲清它的机制。**
A：RAG（检索增强生成）是在 LLM **回答前**，先根据用户问题**从外部知识库检索出相关内容，拼进 Prompt**，让模型**基于这些检索到的内容作答**的技术。机制上分两段：离线把知识库文档分块、Embedding、存进向量库；在线把问题也 Embedding，去向量库检索最相关的 Top-K 片段，（可选 Rerank 精排后）连同问题组装成 Prompt 交给 LLM 生成答案并标注出处。本质是**运行时的上下文注入**——不改模型权重，只在推理时临时喂进正确依据。类比就是把"闭卷考试"变成"开卷查资料"。

**Q：为什么要用 RAG，它解决了 LLM 的什么问题？**
A：LLM 的知识烧进参数里，有三个硬伤 RAG 恰好补上：①**时效**——知识停在训练截止日，RAG 让它能引用最新信息；②**私域**——公司内部文档模型没学过，RAG 把它检索出来喂进去；③**幻觉**——模型记不清就编，RAG 给它真实依据、还能标出处让答案可核查（治幻觉、可溯源）。此外相比微调，RAG **更新知识只需改库、不用重训**，便宜且灵活。所以补"知识"类需求几乎都先上 RAG。

**Q：RAG 和微调（Fine-tuning）怎么选？能一起用吗？**
A：核心区别是**改什么**：RAG 改**输入**、外挂知识，适合补充**动态、私域、海量的事实性知识**，可溯源、改库即更新、成本低；微调改**模型权重**、内化能力，适合教模型**新能力、固定风格、专有输出格式、领域语感**这类"改行为"的需求，但知识更新要重训、贵、说不清依据。选型上：补知识→RAG，改能力/风格→微调，成本 Prompt < RAG < 微调，所以先 RAG。二者不冲突、常组合：用微调过的领域模型 + RAG 检索最新资料，效果最好（详见 [28-fine-tuning](28-fine-tuning.md)）。

**Q：既然上下文窗口越来越长，把资料全塞进去不就行了，还要 RAG 干嘛？**
A：长上下文直塞只适合"资料少、每次都要通读"的场景，知识量一大就三个问题：①**贵**——长 Prompt 每次请求都按 Token 计费，成本随资料线性涨；②**Lost in Middle**——塞太多时模型会忽略中间部分的信息，准确率反而下降；③**放不下**——企业知识库动辄百万文档，再长的窗口也塞不下。RAG 恰恰是"先检索筛出最相关的几段、只塞这几段"，既省 Token 又避免噪声干扰。所以长上下文不是 RAG 的替代，反而常与 RAG 配合（检索出候选后塞进长窗口）。

**Q：为什么说"RAG 的上限是检索质量"？**
A：因为 RAG 是"检索→生成"的串联，LLM 只能基于被检索出来、塞进 Prompt 的内容作答。**如果检索环节没把正确依据召回**（分块切坏了、语义没匹配上、排序把对的挤下去了），那么无论 LLM 多强，它手里都没有正确资料——要么基于错误/无关片段继续编、要么只能说"资料里没有"。所以生产中大部分 RAG 效果问题出在检索侧，后续的分块、检索优化、Rerank 都是在提升"把正确依据可靠送到 LLM 面前"的能力。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别把 RAG 当"搜索 + 拼接"的花架子**——真正的难点全在检索质量：分块策略、Embedding 选型、混合检索、Rerank 缺一不可。Demo 很好搭，生产可用很难，差距就在这些细节（后续 15–19 篇逐个打磨）。
- ⚠️ **检索没召回到正确依据 = RAG 直接失效**，且比"模型没这知识"更隐蔽——模型会拿着无关片段一本正经地编。所以**必须做评估**：分别量化"检索准不准（召回率/命中率）"和"答得忠不忠于资料（faithfulness）"，出问题才能定位是检索坏还是生成坏（详见 [19-rag-evaluation](19-rag-evaluation.md)）。
- ✅ **Prompt 里务必强约束"只依据资料作答、无依据就说不知道"**，否则模型会混用参数记忆和检索内容，溯源和抗幻觉效果大打折扣。这是把 RAG 的抗幻觉能力真正落地的关键一句指令。
- ✅ **Top-K 不是越大越好**：召回太多会引入噪声、稀释相关内容、还触发 Lost in Middle。正确姿势是"粗召回宁多（K 大点）→ Rerank 精排后只塞少而精的 top-n"（详见 [17-rerank](17-rerank.md)）。
- ✅ **元数据（来源、时间、权限）和原文一起存**：既用于溯源引用，也用于过滤（如按时间/部门/权限筛选），生产 RAG 几乎都要"向量检索 + 元数据过滤"组合。
- ✅ **加分认知**：能说清"RAG 是把知识从参数搬到外部库、让 LLM 只做它擅长的'读材料+组织语言'、其上限取决于检索而非生成"，比只会背"检索+生成"流程更显理解本质。
