# 26 · 大模型应用评估（LLM Evaluation）

> LLM 输出**开放、不确定、无唯一正确答案**，无法像传统软件用精确断言测试；评估要靠**分层方法（规则 → LLM-as-a-Judge → 人工）+ 金标准评估集 + 离线/在线闭环**，把"感觉变好了"变成"可量化、可回归"。重要度 ⭐⭐⭐。

## 🎯 一句话核心

传统软件测试是 `assert output == expected`——**输入确定、输出唯一**；而 LLM 应用是 `assert output 足够好`——**答案开放、每次可能不同、好坏是程度问题**。评估的本质就是：为"足够好"找一把**可扩展、可复现、可量化**的尺子，其中最主力的尺子是**让另一个强模型当裁判打分（LLM-as-a-Judge）**，再用少量人工校准这把尺子。

## 📖 核心原理

**为什么 LLM 应用"没法用老办法测"？** 传统单元测试成立的前提是**确定性**：同样输入→同样输出→可精确断言。LLM 三条全破了：①**输出开放**——"介绍一下杭州"有无数种合格答法，没有唯一 ground truth；②**不确定**——采样随机性（[04-sampling-decoding](04-sampling-decoding.md)）让同一 Prompt 每次结果不同，`==` 直接失效；③**质量是连续谱**——同一问题两个答案可能都对，但一个更准确/更有用/更简洁。所以评估不是"通过/失败"的布尔判定，而是**沿多个维度（正确性、相关性、有用性、安全性、格式）打分**，且这些维度多数**无法用字符串比较得到**。这就逼出了"用模型评模型"的思路。

**评估的核心矛盾：可扩展 vs 可信。** 人工评估最可信（金标准），但**贵、慢、不可规模化**——你不可能每改一句 Prompt 就让人重标 500 条。基于规则的自动评估**快而廉**，但只在有标准答案、可字符串匹配的窄场景成立（如"抽取的身份证号对不对""是否输出合法 JSON"），面对开放生成基本无能为力。**LLM-as-a-Judge 卡在中间**：用强模型模拟人的判断，既能自动化规模跑，又能理解语义、评开放输出——它是现代 LLM 应用评估的**主力**。整个评估体系的设计，就是在这三层之间做权衡与互补：**人工校准裁判、裁判规模化跑、规则兜底硬约束**。

**评估要"闭环"而非"一次性"。** 一次评估只告诉你此刻多好；真正的价值在于**回归防退化**：LLM 应用极其脆弱，改一句 Prompt、换个模型版本、调一个检索参数，都可能在你没注意的角落变差（"改好了 A 场景，悄悄弄坏了 B 场景"）。所以要沉淀一个**固定的评估集（golden set）**，每次变更都回归跑一遍，用分数对比守住底线——这正是把"玄学调 Prompt"变成"工程"的关键。评估还要分两个战场：**离线**（发布前，用评估集回归）和**在线**（生产中，用真实用户信号持续监控），二者互补形成"发布前把关 + 发布后监控"的完整闭环。

## 🔧 关键方法 / 流程 / 架构

**评估方法分层对照（从廉价窄场景到昂贵金标准）：**

| 方法 | 怎么评 | 适用 | 优点 | 局限 |
|---|---|---|---|---|
| **精确匹配 / 断言** | `output == expected`、包含关键点、正则、格式校验 | 分类、抽取、结构化输出（[09-structured-output](09-structured-output.md)） | 快、准、零成本、确定 | 只适合有唯一答案/可机械判定的窄任务 |
| **参考式指标** BLEU/ROUGE | 与参考答案算 n-gram 重叠 | 翻译、摘要（有标准答案时） | 自动、可复现 | 只看字面重叠，**语义近但用词不同会被误判**，与人类判断相关性弱 |
| **LLM-as-a-Judge**（主力） | 用强模型按 rubric 给开放输出打分/成对比较 | 开放生成、对话、RAG 答案、有用性/安全性 | **可扩展、懂语义、能评开放输出** | 有偏差、需校准、有 Token 成本、裁判本身可能出错 |
| **人工评估**（金标准） | 人按标准打分/标注/盲评 | 校准自动评估、高风险场景终审 | 最可信、能抓微妙问题 | 贵、慢、不可规模化、有主观差异 |

**LLM-as-a-Judge 的正确打开方式（重点，直接决定评估可不可信）：**

```
          ┌─────────────────────────────────────────────┐
          │  待评样本 (输入 + 模型输出 [+ 参考答案/上下文]) │
          └───────────────────────┬─────────────────────┘
                                   ▼
   ① 给明确评分标准 rubric ──►  ┌──────────────────┐
      (1-5 分每档什么含义,        │  Judge 模型(强)   │
       评哪些维度: 正确性/         │  按 rubric 逐维打分 │
       相关性/有用性/安全)         │  + 要求给出理由     │
                                  └────────┬─────────┘
                                           ▼
   ② 成对比较 pairwise (A vs B 选更好的, 比绝对打分更稳)
   ③ 控制位置偏差: 交换 A/B 顺序各评一次取一致结果
   ④ 用人工标注抽样校准: Judge 与人打分是否一致?  ◄── 关键
                                           ▼
                            聚合成可量化分数 → 进评估报告
```

要点：**给 rubric（评分细则）而非只说"打个分"**——否则模型标准漂移；**成对比较（pairwise）通常比绝对打分更稳**，因为"A 和 B 谁更好"比"这答案值几分"更容易判准；**控制位置偏差**——裁判有倾向选靠前/靠后选项的偏好，需交换顺序双评；**要求裁判给理由**（先解释后打分），能显著提升一致性；最后**必须用人工抽样校准**——先验证"裁判打分和人类判断一致"，这把尺子才可信。

**离线评估 vs 在线评估（两个战场，缺一不可）：**

| 维度 | 离线评估（Offline） | 在线评估（Online） |
|---|---|---|
| 时机 | **发布前** | **生产运行中** |
| 数据 | 固定 golden set | 真实用户流量 |
| 手段 | 评估集回归跑分（规则 + Judge） | 点赞/点踩、A-B 测试、隐式信号 |
| 目的 | **把关 + 防回归退化** | **监控真实效果 + 发现盲区** |
| 反馈 | 快、可控、可重复 | 真实、有分布偏移、有噪声 |

在线**隐式信号**很值钱：用户是否复制了答案、是否追问/重问（可能不满意）、是否点了引用来源、会话时长、是否走到转化——这些无需用户主动打分就能反映质量。**A-B 测试**是在线评估金手段：新旧 Prompt/模型各分一部分流量，用业务指标（满意度、任务完成率、转化）实测谁更好，胜过任何离线猜测。

**可观测性（Observability）是评估的地基。** 评估要有数据可评，就得先**记录每一次调用**：输入、输出、用到的上下文/检索片段、Token 数、延迟、成本，以及贯穿多步（检索→Prompt→生成→工具调用）的完整 **trace**。没有 trace，线上出问题（答错/超时/花钱）根本无从定位是哪一环坏了；有了 trace，就能把线上真实 case 沉淀回 golden set，形成"生产发现问题 → 补进评估集 → 回归守住"的正循环（应用层如何埋点与串 trace 详见 [30-app-architecture](30-app-architecture.md)）。

**回归防退化的工作流（把评估变成 CI）：**

```
改 Prompt / 换模型 / 调检索参数
        │
        ▼
   跑 golden set  ──►  规则断言 + LLM-as-a-Judge 打分
        │
        ▼
   对比基线分数
    ├─ 总分↑ 且无维度明显↓ → 通过, 可发布
    └─ 任一关键维度↓ (如安全/正确性) → 拦截, 回退定位
        │
        ▼   线上发现的新 badcase 持续补进 golden set
   评估集越跑越强 → 护城河
```

## 🔑 要点速记

- LLM 难评估的三根源：**输出开放、结果不确定、质量是连续谱**——不能用 `assert ==`。
- 评估分三层：**规则/参考**（廉价窄场景）→ **LLM-as-a-Judge**（主力，评开放输出）→ **人工**（金标准，校准用）。
- BLEU/ROUGE 只看**字面 n-gram 重叠**，语义对但用词不同会误判，与人类判断相关性弱——别当唯一标准。
- **LLM-as-a-Judge 三件套**：给 rubric 评分细则、用 pairwise 成对比较、控制位置偏差（交换顺序双评），并**用人工抽样校准**裁判本身。
- **golden set（金标准评估集）**：可 LLM 合成候选 + 人工审核，线上 badcase 持续回补，是回归防退化的核心资产。
- **离线**（发布前跑评估集把关）+ **在线**（生产用点赞点踩/隐式信号/A-B 测试监控）双闭环。
- **可观测性**是评估地基：记录输入输出、Token、延迟、成本、trace，才能定位问题、沉淀数据。
- 每次改 Prompt/模型都跑评估集，把"玄学调参"变成**可量化的工程回归**。

## ❓ 高频面试 / 理解题

**Q：LLM 应用为什么不能像传统软件那样写单元测试？**
A：传统测试靠确定性——同样输入产生唯一输出，可用 `assert output == expected` 精确判定。LLM 三点都不满足：①输出开放，同一问题有无数种合格答案，没有唯一 ground truth；②采样随机性让同一输入每次结果不同，`==` 直接失效；③质量是连续程度（更准/更有用/更简洁），不是布尔的对错。所以评估要沿多个维度打分，而多数维度得靠语义理解判断，这才引出了 LLM-as-a-Judge。

**Q：什么是 LLM-as-a-Judge？怎么让它评得可信？**
A：用一个强模型当裁判，按给定标准给开放输出打分或做成对比较，从而自动、规模化地评估语义质量。要评得可信需四招：①给明确 **rubric**（每档分数什么含义、评哪些维度），避免标准漂移；②优先 **pairwise 成对比较**（判"谁更好"比"值几分"更稳）；③**控制位置偏差**，交换候选顺序各评一次；④**用人工抽样校准**——先证明裁判打分和人类判断一致，这把尺子才算数。它的代价是有偏差、有成本、裁判本身也可能错。

**Q：离线评估和在线评估分别解决什么？为什么都要有？**
A：离线是发布前拿固定 golden set 回归跑分，作用是**把关和防退化**——快、可复现、可控，但数据是人造的、覆盖不全。在线是生产中用真实流量评估——点赞点踩、隐式信号（复制、追问、停留、转化）、A-B 测试，作用是**监控真实效果、发现离线盲区**，但有噪声和分布偏移。二者互补：离线守发布底线，在线抓真实问题并把 badcase 回补进 golden set，形成完整闭环。

**Q：RAG 评估和这里讲的通用评估是什么关系？**
A：本篇是通用应用评估的方法框架（分层方法、Judge、离线/在线、可观测性）；RAG 评估是它在检索增强场景的**专门化**——额外要拆开评"检索质量"（命中率/召回）和"生成质量"（Faithfulness 忠实度、Answer Relevance 答案相关性、是否有出处支撑），大量用 LLM-as-a-Judge 判断答案是否忠于检索到的上下文。方法同源，指标更细，详见 [19-rag-evaluation](19-rag-evaluation.md)。Agent 评估则更难，要评**多步轨迹**（工具选得对不对、路径是否高效、最终任务是否完成），而不只看最后一句输出。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别只信 BLEU/ROUGE**：它们只量字面重叠，语义正确但换了说法会被判低分，对开放生成几乎没用——有标准答案时可做辅助，别当质量唯一标尺。
- ⚠️ **LLM-as-a-Judge 不校准就用 = 自欺**：裁判有位置偏差、冗长偏好（爱选更长答案）、对自家模型输出的偏袒。上线前必须用人工抽样验证裁判与人一致，并交换顺序控偏差。
- ⚠️ **没有 golden set 就等于没评估**：靠"我试了几条感觉不错"发布，改一版就悄悄退化且无从察觉。先花力气建评估集（LLM 合成候选 + 人工审），它是最值钱的资产。
- ✅ **评估集要覆盖 badcase 和边界**：不止 happy path，要专门收集难例、易错例、安全红线例；线上暴露的新问题第一时间回补进去，评估集越用越强。
- ✅ **先立可观测性再谈评估**：输入输出、Token、延迟、成本、trace 都记下来，既能定位线上问题，又能把真实流量沉淀成评估数据（[30-app-architecture](30-app-architecture.md)）。
- ✅ **能用规则就别用 Judge**：格式、是否含关键点、JSON 合法性这类硬约束用断言最快最准最省钱；把昂贵的 Judge 留给必须评语义的开放维度。
