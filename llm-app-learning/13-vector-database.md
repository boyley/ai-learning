# 13 · 向量数据库（Vector Database）

> 向量数据库是**专为高维向量的相似检索而生的存储系统**：它把 Embedding 向量、原始内容、元数据存在一起，用内置 ANN 索引在海量向量中毫秒级找出"语义最近的 Top-K"。它是 RAG 检索层的基础设施。重要度 ⭐⭐。

## 🎯 一句话核心

传统数据库回答"**哪一行精确等于 X**"（`=` + B+树精确匹配），向量数据库回答"**哪些向量语义上最像 X**"（相似度 + ANN 近似检索）；前者查"相等"，后者查"相近"——这是两类互补的存储，做 RAG 时常常混用。

## 📖 核心原理

**向量数据库解决的是一个传统数据库无解的问题：相似性检索。** 文本经 Embedding 变成几百上千维的稠密向量（详见 [11-embedding](11-embedding.md)），语义相近的文本在向量空间中距离相近。检索的目标不再是"字段精确相等"，而是"在千万级向量里找出与查询向量距离最近的 K 个"。若用暴力法逐个算相似度（brute-force / flat），复杂度是 O(N·d)，百万级向量单次查询要算上亿次浮点乘加——生产环境扛不住。**向量数据库的核心价值，就是把这件事做到又快又可扩展。**

**它靠三件事做到这一点：① 内置 ANN 索引**（Approximate Nearest Neighbor，近似最近邻，如 HNSW、IVF、PQ，原理详见 [12-similarity-ann](12-similarity-ann.md)）——用"牺牲一点召回换几个数量级的速度"的近似算法，把 O(N) 降到近似 O(log N)；**② 工程化封装**——把索引构建、分片、副本、持久化、并发写、崩溃恢复这些脏活封装成开箱即用的服务，而不是让你自己拿 Faiss 库手搓；**③ 向量与元数据同库**——每个向量旁边挂着它的原文、来源、标签、时间等 payload，检索时能一并取回、也能据此过滤。

**元数据过滤（metadata filtering）是向量库的关键能力，也是最容易被低估的一环。** 真实检索几乎从不是"在全库里裸搜向量"，而是"**先按结构化条件圈定范围，再在范围内做向量相似检索**"。比如企业知识库检索时先按 `department = '法务' AND time > 2025 AND type = 'contract'` 过滤，把候选从千万缩到几万，再算相似度。这样做**既提精度**（排除掉语义相近但业务上无关的文档，比如别的部门的同类合同），**又提性能**（搜索空间变小）。这正是"向量+元数据同库"的威力：一次查询里同时表达"语义相近"和"业务约束"两种意图。

**混合检索（hybrid search）则是把向量检索和传统全文检索融合。** 纯向量检索擅长语义匹配（"如何退款"能召回"退货流程说明"），但对精确关键词、专有名词、型号编号、罕见术语却常常不如老牌的 BM25 全文检索。于是主流做法是**两路并行检索再融合**（如 RRF 融合排名），兼得"语义覆盖"和"关键词精确"两种能力——这是检索质量优化的重要手段（详见 [16-retrieval-optimization](16-retrieval-optimization.md)）。

## 🔧 关键方法 / 流程 / 架构

**向量数据库在 RAG 中的位置与一次带过滤的检索流程：**

```
① 写入侧（离线，建库）                    ② 检索侧（在线，查询）
  文档 → 分块 → Embedding                     用户问题 → Embedding
                │                                        │
                ▼  向量 + 元数据(payload) 一起写入        ▼  查询向量
        ┌──────────────────────────┐          ┌──────────────────┐
        │      向 量 数 据 库        │          │ 先按元数据过滤     │
        │  ┌────────────────────┐  │          │ dept/time/type... │  ← 缩小范围、提精度
        │  │ vec  + payload +   │  │◀─────────│ 再在候选集内       │
        │  │ ANN索引(HNSW/IVF)  │  │  Top-K   │ 做 ANN 相似检索    │
        │  └────────────────────┘  │  相似块  │ (可选:并行BM25融合)│
        └──────────────────────────┘          └──────────────────┘
                                                         │
                                                         ▼  Top-K 相关块 → 拼进 Prompt 交给 LLM
```

**核心能力清单（一个成熟向量库应具备）：**

| 能力 | 说明 |
|---|---|
| 向量 CRUD | 增/删/改/查向量，支持批量 upsert；删除/更新要能同步维护 ANN 索引 |
| Top-K 相似检索 | 给定查询向量返回最近 K 个，可选相似度阈值 |
| **元数据过滤** | 先按结构化字段（标量/枚举/范围/布尔）过滤，再向量检索——缩范围、提精度 |
| 混合检索 | 向量 + 全文/BM25 双路召回，RRF 等融合排名 |
| 索引选择 | HNSW（高召回低延迟）/ IVF-PQ（省内存、超大规模）等可调 |
| 分片与副本 | 水平扩展存储、高可用、并发读写 |

**选型对比（2024–2026 主流，按典型场景选）：**

| 方案 | 类型 | 定位 / 适用场景 | 混合检索 | 运维成本 |
|---|---|---|---|---|
| **pgvector** | Postgres 扩展 | **中小数据量、已有 Postgres 首选**；向量与业务表同库、事务一致 | 借 PG 全文（tsvector） | 低（复用现有 PG） |
| **Milvus** | 专业向量库 | **海量（十亿级）、高性能、高并发**；分布式、索引丰富 | 支持 | 中高（要部署集群） |
| **Qdrant** | 专业向量库 | 中大规模、Rust 实现、过滤性能强、API 友好 | 支持 | 中 |
| **Weaviate** | 专业向量库 | 自带混合检索、模块化、可内置 Embedding | 强（原生 hybrid） | 中 |
| **Chroma** | 轻量嵌入式 | **原型 / 本地开发 / 小数据**；上手快、可进程内嵌 | 有限 | 极低 |
| **Redis（RediSearch）** | KV + 向量模块 | 已用 Redis、低延迟、向量+缓存一体 | 支持 | 低中 |
| **Elasticsearch / OpenSearch** | 搜索引擎 + 向量 | **已有 ES、混合检索强**；成熟的全文+向量融合 | 强 | 中高 |
| **Pinecone** | 云托管（SaaS） | **免运维、弹性扩缩**；按用量计费、快速上线 | 支持 | 极低（托管） |

**选型四维度：** ① **数据量**（万级→Chroma/pgvector；亿级→Milvus）；② **是否已有存储**（有 PG→pgvector，有 ES→ES，有 Redis→Redis，复用而非新增组件）；③ **是否要混合检索**（要→Weaviate/ES 更省心）；④ **运维成本**（不想运维→Pinecone 等托管）。

**向量库 vs 传统数据库（互补，非替代）：**

| 维度 | 传统数据库（RDB / KV） | 向量数据库 |
|---|---|---|
| 查询语义 | 精确匹配 `=` / 范围 / JOIN | 语义近似"最像的 Top-K" |
| 索引 | B+树 / 哈希（精确定位） | ANN（HNSW/IVF/PQ，近似检索） |
| 数据 | 结构化行列 | 高维稠密向量 + payload |
| 结果 | 确定、可复现 | 近似、有召回率权衡 |
| 典型用途 | 事务、报表、精确查找 | 语义检索、推荐、RAG 召回 |

> 二者常混用：结构化条件（谁、何时、哪个部门）交给关系型/过滤能力，"语义相近"交给向量索引——这也正是"元数据过滤 + 向量检索"能在一个库里完成的原因。

## 🔑 要点速记

- 向量库 = **海量向量存储 + 内置 ANN 索引 + 元数据同库**，专为相似检索而生。
- 核心能力：向量 CRUD、Top-K 检索、**元数据过滤**、混合检索。
- **元数据过滤**：先按 `department/time/type` 等圈范围，再向量检索——**既提精度又提性能**。
- **混合检索** = 向量（语义）+ BM25/全文（关键词精确），RRF 融合，取长补短。
- 传统库查"相等"（B+树精确），向量库查"相近"（ANN 近似）；**互补常混用**。
- 选型看四维：**数据量 / 是否已有存储 / 是否要混合检索 / 运维成本**。
- 已有 PG 用 **pgvector**；海量高性能上 **Milvus**；原型用 **Chroma**；不想运维用 **Pinecone**；混合检索强看 **ES / Weaviate**。
- **换 Embedding 模型必须全量重建索引**——不同模型的向量空间不通用。

## ❓ 高频面试 / 理解题

**Q：向量数据库和传统数据库的本质区别是什么？为什么不能用 MySQL 存向量直接查？**
A：本质区别是**查询语义**：传统库做精确匹配（`WHERE x = ?`，靠 B+树/哈希精确定位），向量库做**语义近似检索**（找距离最近的 Top-K，靠 ANN 索引）。MySQL 能存向量，但没有 ANN 索引，只能逐行暴力算相似度，百万级向量单次查询要上亿次浮点运算，延迟不可接受；向量库用 HNSW/IVF 等近似算法把 O(N) 降到近似 O(log N)，才能毫秒级返回。二者互补：精确条件用传统库能力过滤，"相近"交给向量索引。

**Q：为什么要元数据过滤？它对检索质量有什么影响？**
A：真实检索几乎不做全库裸搜，而是**先按结构化条件（部门、时间、类型等）圈定候选，再在候选内做向量相似检索**。好处有二：**提精度**——排除语义相近但业务无关的文档（比如另一个部门的同类合同、过期版本），避免污染 Top-K；**提性能**——搜索空间从千万缩到几万。这正是"向量+元数据同库"的价值：一次查询同时表达"语义相近"和"业务约束"。

**Q：什么是混合检索，为什么纯向量检索不够？**
A：纯向量检索靠语义相似，擅长"换种说法也能召回"，但对**精确关键词、专有名词、型号编号、罕见术语**往往不如老牌 BM25 全文检索（这些词 Embedding 未必区分得开）。混合检索让**向量与全文两路并行召回，再用 RRF 等融合排名**，兼得"语义覆盖"和"关键词精确"，是检索质量优化的常用手段（详见 [16-retrieval-optimization](16-retrieval-optimization.md)）。

## ⚠️ 易错点 / 实践建议

- ⚠️ **换 Embedding 模型 = 必须全量重建索引**：不同模型输出的向量维度和空间语义完全不通用，新旧向量混在一起相似度毫无意义。升级模型要重新 Embedding 整库并重建 ANN 索引，做好停机/双写迁移方案（呼应 [11-embedding](11-embedding.md)）。
- ⚠️ **别忽视删除/更新的索引维护**：HNSW 等图索引删点后可能留"墓碑"、长期不重建会退化召回与性能；高频更新场景要关注库的 compaction/rebuild 策略。
- ✅ **不要一上来就选 Milvus 这类重型库**：数据量在百万级以内、又已有 Postgres，**pgvector 往往是性价比最高的选择**——少一个组件、少一套运维、还能和业务表做事务与 JOIN。选型先看"是否已有存储可复用"。
- ✅ **一致性要想清楚**：多数向量库是**最终一致**，批量导入后索引构建有延迟，写完立刻查可能查不到新数据；对实时性敏感要确认库的可见性/flush 语义。
- ✅ **批量导入用 batch upsert**：逐条写入既慢又频繁触发索引更新；离线建库应分批、必要时建完数据再统一构建索引。
- ✅ **加分认知**：能说清"过滤先于向量检索既提精度又提性能""向量库查相近、传统库查相等所以互补",比只会背产品名更显对检索原理的理解。
