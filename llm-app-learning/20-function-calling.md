# 20 · Function/Tool Calling（工具调用）

> 工具调用让模型**不再只会说，还能"决定去做"**——但它本身**不执行任何代码**，只输出"该调哪个函数、参数是什么"的结构化 JSON，由你的程序真正执行再把结果喂回。它是 Agent 的行动基石。重要度 ⭐⭐⭐。

## 🎯 一句话核心

Function Calling 的本质：模型看到**工具定义（名称/描述/参数 JSON Schema）+ 用户问题**，输出一段**"调用意图 JSON"**（调哪个工具、传什么参数）；**执行由你的程序完成**，结果回传后模型再继续。模型负责"动脑决策"，你的代码负责"动手执行"——这是一次**多轮**协作，不是模型自己联网干活。

## 📖 核心原理

**最关键的认知：模型不执行代码。** 很多人以为"工具调用 = 模型自己去查了数据库"，错。模型能做的只有它唯一会的事——**按概率生成文本**（详见 [01-llm-overview](01-llm-overview.md)）。所谓工具调用，是模型被训练成：当判断"这个问题我自己答不了、需要某个工具"时，就**生成一段符合工具参数 Schema 的结构化 JSON**（本质就是[结构化输出](09-structured-output.md)的专用形态），表达"我想调用 `get_weather`，参数 `{city: "北京"}`"。这段 JSON 由**你的应用代码**解析、真正调用函数/API、拿到结果，再把结果作为新一轮的输入喂回模型，模型据此生成最终自然语言答复。

**为什么要这么设计？** 因为 LLM 有硬边界：不知道实时信息（今天天气、股价）、不会精确计算（算不准 `234×567`）、拿不到私域数据（你数据库里的订单）。这些恰恰是**确定性程序最擅长**的。工具调用把两者拼起来：**LLM 管"理解意图 + 决策 + 组织语言"，程序管"精确执行 + 真实数据"**，各补各的短板（呼应 [01-llm-overview](01-llm-overview.md) 的能力边界）。所以它天然是**多轮交互**：一问不一定一答，中间可能穿插一次或多次"模型请求调用 → 程序执行 → 结果回传"的循环。

**模型是怎么学会"该不该调、调哪个"的？** 靠对齐阶段的训练：厂商用大量"带工具场景"的数据微调，让模型学会读工具描述、匹配用户意图、生成合法参数。所以**工具的"描述"质量直接决定调用准确率**——描述写得含糊，模型就选错工具或漏调；参数 Schema 约束不清，模型就**编造参数（参数幻觉）**。工具定义写得好不好，很大程度决定这套系统靠不靠谱。

## 🔧 关键方法 / 流程 / 架构

**完整多轮流程（这张图是本篇核心）：**

```
                    ┌─────────────────────────────────────┐
   ①用户提问 ─────▶ │   模型（拿到 工具定义 + 对话历史）   │
 "北京今天多少度?"   └─────────────────────────────────────┘
                                   │
                    ②模型判断：自己答不了，需要工具
                       返回"调用意图 JSON"（不执行！）
                       { name:"get_weather",
                         arguments:{ city:"北京" } }
                                   │
                                   ▼
                    ┌─────────────────────────────────────┐
   ③你的程序 ─────▶ │  解析 JSON → 真正调用 get_weather()  │
                    │  → API 返回 { temp: 32, ... }        │
                    └─────────────────────────────────────┘
                                   │
                    ④把工具结果作为新消息回传模型
                       role: "tool", content: "32℃"
                                   │
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  模型据结果生成最终答复              │
                    │  或判断"还需再调下一个工具"→回到②    │
                    └─────────────────────────────────────┘
                                   │
                    ⑤最终自然语言答复
                       "北京今天 32℃，注意防暑。"
```

> 关键：②到④之间**可以循环多次**（多轮调用）。模型每轮只做一个决策——"继续调工具"还是"我可以答了"，由你的程序驱动整个循环直到模型给出最终答复。

**工具定义（Tool Definition）三要素——描述质量是命门：**

| 要素 | 作用 | 写不好的后果 |
|---|---|---|
| **名称 name** | 工具的唯一标识（如 `get_order_status`） | 命名含糊 → 模型分不清相似工具 |
| **描述 description** | 告诉模型"这工具干什么、何时该用" | **最关键**：写不清模型就选错工具或该调不调 |
| **参数 parameters（JSON Schema）** | 定义参数名、类型、是否必填、枚举值 | 约束松 → 参数幻觉/类型错误/漏参 |

极简工具定义（框架无关示意）：

```json
{
  "name": "get_weather",
  "description": "查询指定城市的实时天气。当用户询问天气、气温、是否下雨时调用。",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string", "description": "城市名，如 北京" },
      "unit": { "type": "string", "enum": ["celsius", "fahrenheit"] }
    },
    "required": ["city"]
  }
}
```

**三种进阶调用模式：**

- **多工具选择**：一次给模型多个工具（天气 + 汇率 + 数据库查询），模型**自己挑**该用哪个。工具越多、描述越接近，选错概率越高——工具集要精简、描述要区分度高。
- **多轮（串行）调用**：一个任务需要连续调多次，且**后一步依赖前一步结果**。如"帮我订最便宜航班"：先 `search_flights` → 拿到结果 → 再 `book_flight(id)`。必须一轮一轮来。
- **并行工具调用（parallel tool calls）**：一轮里模型同时返回**多个互不依赖**的调用（如同时查"北京天气"和"上海天气"），程序并发执行后一并回传，省往返、降延迟。现代主流模型（GPT-4、Claude 等）已原生支持。

**典型用途（补上 LLM 的短板，呼应 [01-llm-overview](01-llm-overview.md)）：**

| 场景 | 补的短板 | 例子 |
|---|---|---|
| 查数据库 | 拿不到私域数据 | 查用户订单、库存 |
| 调外部 API | 不知实时/外部信息 | 天气、汇率、发邮件、下单 |
| 精确计算 | 不会精算 | 大数运算、财务公式、日期差 |
| 查实时信息 | 知识停在训练截止日 | 今天新闻、当前股价 |

**与 Agent 的关系——它是 Agent 的行动基石：** 工具调用赋予模型"行动能力"（能查、能算、能操作外部世界）。Agent 正是在此之上加了**自主循环 + 规划 + 推理**：反复"思考该做什么 → 调工具 → 看结果 → 再思考"，直到完成复杂任务。没有工具调用，Agent 就只能"空想"无法"动手"。（Agent 与 ReAct 见后续 Agent 章节。）

## 🔑 要点速记

- **模型不执行代码**——只输出"调哪个工具 + 什么参数"的结构化 JSON，执行由你的程序做。
- 本质是[结构化输出](09-structured-output.md)的专用形态 + **多轮交互**：模型决策 ↔ 程序执行 ↔ 结果回传，可循环多次。
- 工具定义 = **名称 + 描述 + 参数 JSON Schema**；**描述质量直接决定调用准确率**。
- 三种模式：**多工具选择、多轮（串行、后依赖前）、并行调用（互不依赖、并发省延迟）**。
- 用途：查数据库 / 调 API / 精算 / 查实时信息——**补上 LLM 不知实时、不会精算、拿不到私域数据的短板**。
- **是 Agent 的行动基石**：Agent 靠工具调用"动手"，加自主循环即成 Agent。
- 安全红线：**工具权限最小化**，别给模型能删库/转账的高危工具裸权限。
- 类比：让 AI 发起一次 **RPC**；工具 Schema ≈ **接口定义 / OpenAPI 契约**。

## ❓ 高频面试 / 理解题

**Q：Function Calling 到底是不是"模型自己去调了 API"？**
A：不是。模型**不执行任何代码**，它只做一件它会的事——生成文本，具体是生成一段符合工具参数 Schema 的**结构化 JSON**（"我想调 `get_weather`，参数 `{city:北京}`"）。真正解析这段 JSON、调用函数、拿结果的是**你的应用程序**；结果回传后模型才继续。所以它是"模型出决策、程序去执行"的多轮协作，不是模型自己联网干活。

**Q：为什么工具"描述"写得好坏这么关键？**
A：因为模型选不选、选哪个工具、传什么参数，全靠读工具的名称和描述来匹配用户意图。描述含糊 → 该调不调或选错工具；参数 Schema 约束松（没写类型/枚举/必填）→ 模型编造参数（参数幻觉）。工具定义就是模型的"使用说明书"，写不清等于让人凭猜使用 API，准确率自然崩。

**Q：多轮调用和并行调用有什么区别？**
A：**多轮（串行）** 是后一步依赖前一步结果，必须一轮轮来（先 `search_flights` 拿到航班号，再 `book_flight(号)`）；**并行** 是一轮里同时发多个**互不依赖**的调用（同时查北京和上海天气），程序并发执行后一并回传，省往返、降延迟。判断标准就一条：**调用之间有没有数据依赖**。

**Q：Function Calling 和 Agent 是什么关系？**
A：工具调用给了模型"行动能力"，是 Agent 的**基础能力**。Agent 在它之上加了自主循环 + 规划 + 推理：反复"思考 → 调工具 → 观察结果 → 再思考"直到完成任务。可以说工具调用是"手脚"，Agent 是"用手脚干活的自主大脑"——没有工具调用，Agent 只能空想不能动手。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别以为模型会执行工具**——它只产出调用意图 JSON，执行、错误处理、结果回传全是你的代码职责；漏了回传这一步模型就永远等不到结果。
- ⚠️ **参数幻觉要防**：用严格 JSON Schema（类型、`enum`、`required`）收紧参数空间，执行前再校验一遍；不合法的参数直接拒绝或回传报错让模型重试，别盲目执行。
- ⚠️ **工具执行会失败/超时**——外部 API 会挂、会超时。必须做兜底：捕获异常，把"调用失败：xxx"作为工具结果回传，让模型换策略或告知用户，别让整条链崩掉。
- ⚠️ **工具别贪多**：工具一多、描述一接近，模型就**选择困难**、选错率飙升。精简工具集、拉开描述区分度，必要时按场景分组只暴露相关工具。
- 🔒 **安全是红线（详见 [10-prompt-security](10-prompt-security.md)）**：工具权限**最小化**——只读的别给写权限，别把"删库 / 转账 / 执行任意命令"这类高危操作做成模型可裸调的工具。危险操作要加**人工确认 / 白名单 / 权限校验**，并警惕 Prompt 注入诱导模型误调工具。
- ✅ **加分认知**：能说清"工具调用 = 结构化输出（决策 JSON）+ 多轮循环 + 程序执行"，且点明"模型只决策不执行、描述质量决定准确率、它是 Agent 的行动基石"，就抓住了本质，而非停留在"能调 API"的表层。
