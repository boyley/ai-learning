# 15 · 文档处理与分块（Chunking）

> 分块是把原始文档切成"大小合适、语义完整"的小段，是 RAG 离线 ETL 管道中承上启下、决定检索质量的一步；**块切得好不好，直接封顶了整个 RAG 系统的效果**。重要度 ⭐⭐⭐。

## 🎯 一句话核心

Chunking 就是回答一个工程问题：**该把文档切成多大、怎么切的一段段，喂给 Embedding 去建索引？** 切太大——一块里混了好几个主题，检索命中后噪音多、定位不准；切太小——一句话被腰斩，语义残缺、检索不到。分块的全部艺术，就是在**"块内语义完整"和"块间精准定位"之间找平衡**。

## 📖 核心原理

**分块是 RAG 离线 ETL 管道的核心环节。** 一个知识库上线前，要跑一条离线的 **ETL（Extract-Transform-Load）** 流水线，把原始文档变成可检索的向量索引：

1. **Extract 抽取**：从 PDF、Word、PPT、Markdown、HTML 网页、数据库、API 等**异构数据源**里把内容读出来，并做**清洗去噪**——去页眉页脚、去广告导航、去乱码空白、扫描件走 **OCR**、表格/公式做结构化还原。这一步的产出是"干净的纯文本 + 结构信息"。
2. **Transform 转换（= 分块）**：把长文档切成一段段 chunk。本篇主角。
3. **Load 加载**：每块过 Embedding 模型转成向量，连同原文和元数据写入向量数据库（详见 [13-vector-database](13-vector-database.md)）。

**为什么必须分块，不能整篇直接塞？** 两个硬约束 + 一个质量诉求：

- **Embedding 有长度上限**：向量模型一次能编码的 Token 有限（常见 512、8192 等），超长要么被截断、要么根本吃不下。
- **LLM 上下文有限且有成本**：检索结果最终要塞进 Prompt 上下文，整篇几万字塞不下、塞得下也贵、还稀释注意力（详见 [06-context-engineering](06-context-engineering.md)）。
- **检索要"精准定位到一小段"**：用户问"退货政策几天内有效"，理想是命中那一段退货条款，而不是把整份 50 页手册召回。**一整篇文档的向量是所有主题的"平均语义"，谁都不像**——只有切成聚焦单一主题的小块，向量才有区分度，检索才打得准。

**这就引出分块的核心权衡（trade-off）：**

```
块太大 ┃████████████████┃  语义完整✅  但 一块混多主题 → 检索噪音大、定位糊、上下文浪费❌
块适中 ┃████┃            语义完整✅  且 主题聚焦 → 检索准、上下文省✅  ← 目标
块太小 ┃█┃              定位精准✅  但 句子被腰斩 → 语义残缺、检索召不回❌
```

一句话：**块内要"语义自洽"（别把一句话/一个论点切断），块间要"主题单一"（别把无关内容塞一块）。** 两个方向互相拉扯，没有万能值，要按内容类型和检索效果调。

## 🔧 关键方法 / 流程 / 架构

**RAG 离线 ETL 全流程：**

```
                          离线 ETL 管道（建库阶段，一次性/定期跑）
  ┌──────────────────────────────────────────────────────────────────────┐
  │  多源数据                                                              │
  │  PDF / Word / PPT ─┐                                                   │
  │  网页 HTML ────────┤   ① Extract 抽取+清洗                            │
  │  数据库 / API ─────┼──►  读取内容 · 去页眉页脚广告 · OCR扫描件 ──┐     │
  │  Markdown / 代码 ──┘     表格公式结构化还原                     │      │
  │                                                        干净文本+结构    │
  │                                                                │       │
  │              ② Transform 分块（本篇）                          ▼       │
  │              按策略切成 chunk + 加 overlap ◄───────────────────┘       │
  │                        │  每块带元数据(来源/标题/页码/时间)            │
  │                        ▼                                               │
  │              ③ Load 入库                                               │
  │              每块 → Embedding 向量 → 写入向量数据库(向量+原文+元数据)  │
  └──────────────────────────────────────────────────────────────────────┘
                                   │
       ═══════════════════════════╪═══════════════════════════ 在线检索阶段
                                   ▼
         用户提问 → Query Embedding → 向量库 ANN 检索 Top-K 块 → 拼进 Prompt → LLM 作答
```

**四类分块策略（从粗到精）：**

| 策略 | 怎么切 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| ① 固定长度 | 每 N 个 token/字符硬切 | 最简单、块大小均匀 | 极易切断句子、破坏语义 | 快速原型、结构混乱的纯文本 |
| ② **按结构切**（推荐） | 沿**段落 / 标题 / Markdown 章节 / 句子边界**切 | 保住语义单元、天然主题聚焦 | 依赖文档有清晰结构 | 大多数规整文档，**首选** |
| ③ 递归切分 | 先按大结构（章→节→段），太大再层层往下细分（段→句）直到达标 | 兼顾结构与大小上限 | 实现稍复杂 | 通用主力方案 |
| ④ 语义分块 | 逐句算 Embedding，**语义相似的邻句聚在一起，语义突变处切开** | 切在真正的语义边界上 | 要额外算向量、慢、成本高 | 语义边界模糊、追求极致质量 |

**overlap 重叠——防止关键句被切在边界：**

硬切时，一句关键信息可能正好横跨两块边界，被劈成两半，两块都语义不全、检索都召不回。解法是让**相邻块保留 10~20% 的重叠内容**：

```
原文: ……A句 | B句 | C句 | D句 | E句……
块1: [ A  B  C ]
块2:       [ C  D  E ]      ← C 句在两块都完整出现，无论问题偏向哪边都能命中
            └重叠┘
```

**经验值（起点，不是定论）：**

- 常规文本 **200~500 token/块**，overlap 取块长的 10~20%（约 20~100 token）。
- **不同内容用不同策略**：代码按函数/类切、表格整表不拆或转成"每行一句话"、对话按轮次(turn)切、法律/合同按条款切、问答对(FAQ)一问一答一块。
- **务必按检索效果回调**：召回不全→块调小或加 overlap；召回噪音多→块调小、主题切更细；答案总缺上下文→块调大或用父子分块。

**元数据（metadata）——每块都要"挂标签"：**

分块时给每块附上**来源文件名、章节标题、页码、时间/版本、作者、URL** 等结构化字段，一并写入向量库。作用有二：

- **过滤检索**：先按元数据过滤（如"只查 2026 版手册""只查财务部文档"）再做向量检索，又快又准（元数据过滤见 [13-vector-database](13-vector-database.md)）。
- **溯源引用**：答案能标注"出自 X 文档第 Y 页"，可信、可核查，是生产级 RAG 的刚需。

**父子分块预告：** "块要小才检索准"和"块要大才上下文全"这对矛盾，有个经典解法——**用小块（子块）做检索、命中后返回其所属的大块（父块）给 LLM**，兼得定位精准与上下文完整。这属于高级 RAG 手段，详见 [18-advanced-rag](18-advanced-rag.md)。

## 🔑 要点速记

- 分块是 RAG 离线 **ETL** 管道的 T 环节：**Extract**(读+清洗+OCR) → **Transform**(分块) → **Load**(Embedding 入库)。
- 必须分块的原因：**Embedding/上下文有长度限制** + **检索要精准定位一小段**（整篇的平均语义没区分度）。
- 核心权衡：**块内语义完整**（别断句）↔ **块间精准定位**（别一块混多主题），没有万能值。
- 四策略：固定长度（最简易断句）→ **按结构切（段落/标题/句子，推荐）** → 递归切分（先大后细）→ 语义分块（按相似度）。
- **overlap 重叠 10~20%**：防关键句卡在块边界被腰斩。
- 经验起点：**200~500 token/块**；代码/表格/对话各用不同策略；一切按检索效果回调。
- 每块挂**元数据**（来源/标题/页码/时间）：支持过滤检索 + 答案溯源。
- 父子分块：小块检索、大块喂 LLM，兼顾精准与完整（见 [18-advanced-rag](18-advanced-rag.md)）。

## ❓ 高频面试 / 理解题

**Q：为什么 RAG 一定要分块，直接把整篇文档做成一个向量不行吗？**
A：三个原因。① Embedding 模型有输入长度上限，整篇超长会被截断甚至编码不了；② 检索结果要塞进 LLM 上下文，整篇太长塞不下、贵、还稀释注意力；③ 最关键——**一整篇文档的向量是所有主题语义的"平均"，对任何具体问题都不够像，检索没有区分度**。只有切成聚焦单一主题的小块，向量才有辨识度，才能精准命中用户真正要的那一段。

**Q：块该切多大？切大切小各有什么问题？**
A：没有万能值，是个权衡。**切太大**：一块里混了多个主题，检索命中后噪音多、定位模糊，还浪费上下文；**切太小**：句子被切断、语义残缺，反而检索不到。经验起点是 200~500 token，配 10~20% overlap，然后**按实际检索效果调**：召回不全就调小/加重叠，噪音多就切更细，答案缺上下文就调大或上父子分块。内容类型不同（代码、表格、对话）策略也不同。

**Q：overlap 重叠是干嘛的？为什么需要？**
A：硬切时一句关键信息可能正好横跨两块边界被劈成两半，两块都语义不完整、检索都召不回。让相邻块保留 10~20% 的重叠内容，能保证边界处的关键句在至少一块里完整出现，避免因切割位置不巧而丢信息。代价是轻微的存储和冗余增加，值得。

**Q：分块时为什么要给每块加元数据？**
A：两大用途。① **过滤检索**：先按来源、时间、部门等元数据过滤缩小范围，再做向量检索，更快更准（如"只查最新版手册"）；② **溯源**：答案能标注具体出处（哪个文档、第几页），让 RAG 结果可信、可核查——这是生产级系统的硬性要求。所以来源、标题、页码、时间这些字段要在分块时就挂上，随向量一起入库。

## ⚠️ 易错点 / 实践建议

- ⚠️ **分块质量直接封顶检索质量，却最易被忽视。** 很多人把精力砸在换更强的 Embedding、上 rerank 上，却用最粗暴的固定长度硬切——**块切烂了，后面再优化都是补救**。这是 RAG 里性价比最高、最该先做好的一步。
- ⚠️ **别无脑固定长度硬切**，它最容易在句子中间、代码块中间、表格中间断开。规整文档优先"按结构切/递归切分"，保住语义单元。
- ⚠️ **别忽略 Extract 清洗**：页眉页脚、导航广告、乱码会当噪音混进块里污染向量；扫描件不 OCR 就是一堆图片、根本抽不出文字。垃圾进、垃圾出。
- ✅ **块大小和 overlap 要当超参数来调**，用真实问题集评估召回率/命中率反复迭代，别拍脑袋定死一个值。
- ✅ **按内容类型分而治之**：代码按函数、表格保完整或转文本、对话按轮次、FAQ 一问一答——一刀切的策略必然在某类内容上翻车。
- ✅ **加分认知**：能说清"检索准 vs 上下文全"这对矛盾，并知道**父子分块**（小块检索、大块喂模型）是它的经典解，比只会背分块策略更显理解深度（见 [18-advanced-rag](18-advanced-rag.md)）。
