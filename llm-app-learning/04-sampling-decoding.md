# 04 · 采样与解码参数（Sampling & Decoding）

> LLM 每一步只输出**全词表上的一个概率分布**，真正决定"吐哪个 Token"的是**解码策略**；`temperature` / `top-p` / `top-k` 这些参数不改模型、只调"从分布里怎么挑"，是控制输出**确定性 vs 多样性**的唯一旋钮。重要度 ⭐⭐⭐。

## 🎯 一句话核心

模型本身给不出"答案"，只给出**下一个 Token 的概率分布**；采样与解码就是**从这个分布里选一个 Token 的规则**。同一个模型、同一段输入，配不同的解码参数，可以从"呆板复读机"变成"天马行空的创作者"——**模型负责算概率，解码负责做选择**。

## 📖 核心原理

**自回归生成是"预测分布 → 选一个 Token → 追加 → 再预测"的循环。** LLM 的前向计算，最后一步是对整个词表（几万到十几万个 Token）算出一组 **logits（未归一化打分）**，经 `softmax` 变成一个**概率分布**——每个候选 Token 有一个 0~1 的概率、全体之和为 1。模型到此为止的工作就结束了：它**没有"选出"任何词**，只是给出了"下一个词该是什么"的概率地图。真正决定输出哪个 Token 的，是**解码策略（decoding strategy）**。选定一个 Token 后把它追加到序列末尾，再喂回模型预测下一个，如此循环，直到遇到**结束符 `EOS`** 或触及 **`max_tokens` 上限**。这就是"自回归（autoregressive）"——**逐 Token、串行、每一步都依赖前面所有已生成 Token**（也是为什么生成比理解慢、为什么有 KV cache 优化，详见 [29-inference-optimization](29-inference-optimization.md)）。

**关键认知：解码参数不改变模型、不改变知识，只改变"从同一张概率地图里怎么挑路"。** 这解释了为什么调 `temperature` 能让同一个模型时而严谨时而发散——底层的概率分布没变，变的是"挑选规则"。理解这一点，就理解了为什么 LLM 是[概率生成器而非确定性函数](01-llm-overview.md)：**随机性不是 bug，而是采样策略主动引入的**。

**两大策略族：确定性挑选 vs 概率采样。**

- **贪心解码（Greedy）**：每一步都选**概率最高**的那个 Token。给定输入几乎完全确定、可复现，但极易**呆板、重复、陷入循环**（"最优的下一个词"连起来往往不是"最优的一段话"，局部最优 ≠ 全局最优）。
- **采样（Sampling）**：**按概率随机抽**一个 Token——概率 0.6 的词有 60% 机会被选中，低概率词也有小概率入选。输出**多样、自然、有创造力**，但可能**采到长尾的怪词而"跑偏"**。现代对话 API 默认走采样。
- **Beam Search（束搜索）**：同时保留 top-k 条候选序列、比整句累计概率再择优，常用于翻译/摘要等**追求单一最优解**的任务；开放式对话/创作中已少用（易产生平庸、通用、重复的输出）。

**`temperature`（温度）是采样前对 logits 的缩放。** 在 softmax 前把 logits 除以 `T`：`T→0` 时分布被拉得**极尖锐**（高概率词概率趋近 1，退化为贪心，确定）；`T=1` 是模型原始分布；`T>1` 把分布**压平**（拉高长尾词的机会，更随机发散）。直觉：**温度调的是"敢不敢冒险选非最优词"**。场景对照——抽取/分类/SQL/代码/函数调用用**低温（0~0.3）**求稳求准；头脑风暴/文案/创意用**高温（0.7~1.2）**求多样。

## 🔧 关键方法 / 流程 / 架构

**一步生成的内部流水线（"概率分布 → 采样"直观示意）：**

```
输入上文："今天天气真"
        │
        ▼  ① 模型前向 → 全词表 logits（未归一化打分）
   好:  3.2   不错: 2.9   糟: 1.1   香蕉: -4.0  ... (共 N 万个 Token)
        │
        ▼  ② softmax 归一化成概率分布（∑=1）
   概率地图：
   好    ████████████████  0.46
   不错  ██████████        0.31
   热    ████              0.12
   糟    ██                0.06
   冷    █                 0.03
   香蕉  ·                 0.00002   ← 长尾
        │
        ├─ 贪心 Greedy ──────► 永远选「好」(0.46)         确定但呆板
        │
        ├─ temperature 缩放 ─► T↓ 分布变尖(逼近贪心) / T↑ 变平(更敢选长尾)
        │
        ├─ top-k=3 ─────────► 只保留{好,不错,热}再采样    砍掉长尾
        │
        ├─ top-p=0.9(核采样)─► 累积概率到0.9的最小集合{好,不错,热}再采样
        │                       动态候选数：分布尖→候选少，分布平→候选多
        │
        ▼  ③ 采样选中 → 追加到序列 → 回到 ① 预测下一个 Token
              直到 EOS / max_tokens / stop 命中
```

**`top-p`（核采样 nucleus sampling）与 `top-k`——两种"截断长尾"的方式：**

| 参数 | 规则 | 特点 |
|---|---|---|
| `top-k` | 只从**概率最高的 k 个** Token 里采样 | 候选数**固定 k**；分布很尖时仍保留 k 个可能过宽，很平时又可能砍太狠 |
| `top-p` | 从**累积概率达到 p** 的最小候选集合里采样（如 p=0.9） | 候选数**动态自适应**：分布尖锐时候选少（更稳）、平缓时候选多（更活），通常比 top-k 更鲁棒 |

> **工程默认：`temperature` 与 `top-p` 一般二选一调、别同时激进设**（两个都放开会双重放大随机性、更难预期）。常见做法：固定 `top-p≈0.9~1.0`，主要用 `temperature` 控风格；或反之。`top-k` 与 `top-p` 也可叠加（先 k 截断再 p 截断），但多数 API 场景只用其一即可。

**其它常用解码参数：**

- **`max_tokens`**：本次生成的 Token 上限，防跑飞、控成本/延迟（注意它算的是**输出 Token**，与上下文窗口共同受限，见 [03-token-tokenization](03-token-tokenization.md)）。
- **`frequency_penalty` / `presence_penalty`**：**降重复**。frequency 按某 Token **已出现次数**递增惩罚（越啰嗦越压）；presence 只要**出现过**就惩罚（鼓励引入新话题/新词）。值过大易导致文理不通。
- **`stop`（停止词/停止序列）**：命中即停，用于**框定输出边界**（如生成到 `\n\n` 或 `"###"` 就停，配合结构化输出很有用）。
- **`seed`**：固定随机种子以**尽量复现**——但注意"尽量"二字（见下）。

## 🔑 要点速记

- 每步模型只输出**全词表概率分布**（`logits → softmax`）；**解码策略负责从分布里选一个 Token**，追加后循环到 `EOS`/`max_tokens`。
- **贪心 Greedy**：选最高概率，确定但呆板/易重复；**采样 Sampling**：按概率随机，多样但可能跑偏；**Beam Search** 比整句最优、多用于翻译/摘要。
- **`temperature`**：softmax 前缩放 logits——**低温→尖锐确定**（抽取/分类/代码），**高温→平缓随机**（创意）；`T→0` 退化为贪心。
- **`top-p`（核采样）**：从累积概率前 p 的**动态**候选集采样；**`top-k`**：从最高 **k 个固定**候选采样。**一般 `temperature` 或 `top-p` 二选一调**。
- 降重复用 **`frequency`/`presence penalty`**；框边界用 **`stop`**；控长度/成本用 **`max_tokens`**；求复现用 **`seed`（仅尽量）**。
- **确定性做不到 100%**：`temperature=0` 也会因**浮点运算/GPU 并行归约顺序/批处理/模型版本**产生微小差异——呼应 LLM [不可完全复现](01-llm-overview.md)。
- 工程铁律：**结构化/事实类任务用低温 + 结构化输出 + 校验**（见 [09-structured-output](09-structured-output.md)）；创意类才放开温度。

## ❓ 高频面试 / 理解题

**Q：`temperature`、`top-p`、`top-k` 三者到底在调什么？该怎么选？**
A：三者都**不改模型、只改"从概率分布里怎么挑 Token"**。`temperature` 是 softmax 前对 logits 做缩放——低温把分布拉尖（逼近贪心、更确定），高温压平（更随机敢选长尾）；`top-k` 把候选**硬截断为固定 k 个**再采样；`top-p`（核采样）截断为**累积概率达 p 的动态候选集**，分布尖时候少、平时候多，通常更鲁棒。实践上 `temperature` 与 `top-p` **二选一为主**：抽取/分类/代码用低温（0~0.3）求稳，创意用高温（0.7~1.2）求多样。

**Q：为什么"预测下一个词最优"不等于"生成整句最优"？贪心的问题在哪？**
A：贪心每步只挑当前概率最高的 Token，是**局部贪心**——但一句好文本是整体最优，局部最优连起来常常平庸、重复甚至陷入循环（"the the the"式）。Beam Search 用保留多条候选、比整句累计概率来缓解，适合翻译/摘要这类求单一最优解的任务；而开放式对话反而需要采样引入的随机性来产生自然、多样的表达。所以**没有万能策略，取决于任务要"准"还是要"活"**。

**Q：`temperature=0` 是不是就 100% 可复现了？**
A：**不能保证**。`T=0` 只是让采样退化为"每步选最高概率"（贪心），逻辑上确定，但工程上仍受影响：①浮点运算不满足严格结合律，GPU 上**并行归约的累加顺序**会让 logits 出现极小抖动，偶尔翻转两个概率极接近 Token 的排序；②服务端**批处理/并发调度、KV cache、硬件差异**；③**模型版本/权重更新**。所以 `seed` + `T=0` 只是"尽量复现"。这正是 [01](01-llm-overview.md) 强调的"LLM 不可完全复现"——需要稳定就靠**低温 + 结构化输出 + 下游校验**兜底，而不是指望解码参数给你确定性。

## ⚠️ 易错点 / 实践建议

- ⚠️ **别把 `temperature` 当"聪明程度"旋钮**——它只调随机性/多样性，不提升推理能力；调高不会更"有创意地对"，只会更敢采长尾（可能更容易跑偏、幻觉）。
- ⚠️ **别同时把 `temperature` 和 `top-p` 都开到很大**——双重放大随机性、输出更难预期。固定其一、主要动另一个。
- ⚠️ **`temperature=0` ≠ 绝对确定**——浮点/并行/版本会带来微小不可控差异；关键路径要靠**输出校验/重试**保证可靠，别把复现性押在参数上。
- ✅ **结构化/事实/工具调用任务上低温**（0~0.2）+ 明确 `stop` + JSON schema 约束 + 解析失败重试（[09-structured-output](09-structured-output.md)）；这是把"概率生成器"驯成"可靠功能"的标准工程手段。
- ✅ **重复/啰嗦先调 penalty 再想别的**：轻度 `frequency_penalty`（0.1~0.5）常比盲目降温更对症；值过大会伤语义连贯。
- ✅ **加分认知**：能说清"模型只给分布、解码才做选择，随机性是采样主动引入而非模型本身不确定"，就抓住了本质——这也是"同样输入不同输出"以及所有稳定性工程（低温/结构化/评估）存在的根源。
