# 24 · 多智能体系统（Multi-Agent Systems）

> 把一个"什么都干"的巨型 Agent 拆成多个各有分工、各带专属工具与上下文的小 Agent，让它们协作完成复杂任务——**分而治之，但代价是成本 ×N、协调复杂**。重要度 ⭐⭐。

## 🎯 一句话核心

多智能体不是"更多 Agent = 更强"，而是**用职责拆分换取聚焦度**：当单个 Agent 的上下文、工具、职责多到互相干扰时，拆成"规划者 + 执行者 + 审查者"这类专职团队，每个成员上下文更干净、可并行、可复用——但**只有单 Agent 真扛不住时才值得付这份协调税**。

## 📖 核心原理

**什么是多智能体？** 单 Agent（ReAct 那种：一个模型 + 一堆工具 + 一段大 System Prompt 循环推理）在简单任务上足够，但任务一复杂就暴露问题。多智能体（Multi-Agent System, MAS）把任务拆给**多个各有角色、各带专属工具集与独立上下文的 Agent**，让它们分工协作。典型的三角色团队：**规划者（Planner）** 拆解任务、**执行者（Worker/Executor）** 干具体活、**审查者（Critic/Reviewer）** 检查结果并要求返工。本质是把软件工程里"单体拆微服务、一个人拆一个团队"的思路搬到 Agent 上。

**为什么要拆？根因是单 Agent 的"过载"。** 当一个 Agent 被塞进几十个工具、要同时扮演产品经理又当程序员又当测试时，会出现三类退化：① **上下文过载**——历史、工具描述、各种材料挤爆上下文窗口，关键信息被淹没，模型"注意力"分散（呼应 [06-context-engineering](06-context-engineering.md)）；② **工具选择困难**——工具越多，模型选错、乱调的概率越高；③ **职责混乱**——一段 Prompt 里塞多种互相打架的目标，模型顾此失彼。拆成专职 Agent 后，每个 Agent 的上下文只装它这一职责需要的信息、工具只有它该用的那几个，**聚焦度和可控性都上升**，还带来可并行（多个 Worker 同时干）、模块化（单独替换某个 Agent）、易维护（分而调试）等工程收益。

**但拆分不是免费的——它引入了"协调"这个新的一等公民问题。** 单 Agent 内部的信息流是隐式的（都在一个上下文里），多 Agent 之间必须**显式传递消息、共享状态、约定协议**，这正是多智能体的核心难点，也是各框架真正在解决的问题。协调做不好，收益全被"沟通成本"吃掉，甚至更糟：一个 Agent 的错误会顺着协作链**传播并放大**（garbage in → garbage out ×N）。所以多智能体的设计重心，从"怎么让一个模型想清楚"转移到了"怎么组织一群模型有效协作而不失控"——即**拓扑结构（谁指挥谁）** 与 **通信机制（怎么传信息）** 两件事。

## 🔧 关键方法 / 流程 / 架构

### 一、常见拓扑（Topology）

不同拓扑回答的是"控制流怎么走、谁决定下一步"。选型的核心权衡是**中心化 vs 去中心化**：越中心化越可控可调试但主管是瓶颈，越去中心化越灵活但越容易失控。

| 拓扑 | 结构 | 谁做决策 | 适用 | 代价/风险 |
|---|---|---|---|---|
| **主管/编排型 Supervisor / Orchestrator** | 一个主管 Agent 调度多个下属 | 主管集中决策、分派、汇总 | 任务可清晰拆解、需强控制（最常用） | 主管是单点瓶颈，主管 Prompt 复杂 |
| **网络/对等型 Network / Peer** | Agent 之间平等、可互相直接对话 | 分布式、谁需要谁就找谁 | 松耦合、探索性协作 | 易失控、可能死循环、难调试 |
| **层级型 Hierarchical** | 主管下再设子主管，树状多层 | 逐层分派、逐层汇总 | 超大任务、部门化分工 | 层级越深延迟越长、误差层层累积 |
| **流水线型 Pipeline / Sequential** | A→B→C 顺序传递，各管一段 | 无中心，按固定顺序流转 | 步骤固定的工序（如 抽取→翻译→润色） | 前段错误直接污染后段、无法并行 |
| **辩论/评审型 Debate / Reviewer** | 多 Agent 对同一问题给方案再互评/投票 | 通过辩论或多数表决收敛 | 需高质量/降幻觉的关键决策 | 成本翻数倍、可能各执一词不收敛 |

其中**主管/编排型**最主流，正是 [23-agent-patterns](23-agent-patterns.md) 里 **orchestrator-workers 编排模式**在"多 Agent"层面的落地：orchestrator 动态拆任务、分派给 workers、再综合结果。

```
                    ┌──────────────────────────┐
                    │  主管 / Orchestrator      │  ← 拆解任务、分派、汇总、决定是否返工
                    │  （规划者 Planner）        │
                    └─────┬───────┬───────┬─────┘
             分派任务 ↓    │       │       │    ↑ 汇总结果 / 状态回传（A2A）
                 ┌────────┘       │       └────────┐
                 ▼                ▼                ▼
          ┌───────────┐   ┌───────────┐   ┌───────────┐
          │ Worker A  │   │ Worker B  │   │ 审查者     │
          │ 检索专员   │   │ 编码专员   │   │ Critic     │
          │ 工具:搜索  │   │ 工具:代码  │   │ 工具:测试  │
          └───────────┘   └───────────┘   └─────┬─────┘
              (各自独立上下文，可并行执行)          │ 不合格 → 打回重做
                                                  └──────────┘
   ┌────────────────────────────────────────────────────────────┐
   │ 对比：单 Agent = 一个大脑塞几十个工具 + 一段巨型 Prompt 死循环 │
   └────────────────────────────────────────────────────────────┘
```

### 二、A2A（Agent-to-Agent）通信

拓扑决定"谁连谁"，**通信机制**决定"连上之后怎么说话"。核心是两种方式：

- **消息传递（message passing）**：Agent 之间像发消息一样传任务、传结果、传反馈（"审查者→执行者：第 3 点不对，重做"）。
- **共享状态（shared state / blackboard）**：所有 Agent 读写同一块"黑板"/共享内存（如一个全局 state 对象），谁更新了大家都能看到——LangGraph 的 state、CrewAI 的共享上下文都属此类。

**Google 的 A2A（Agent2Agent）协议**是一套开放规范，让**不同厂商、不同框架构建的 Agent 能互相发现能力、协商并交换消息**（用 Agent Card 声明自己能干什么），目标是给"Agent 之间"立一个类似 HTTP 的通用握手标准。

**A2A 与 MCP 别搞混（高频考点）：**

| | 连接谁 | 一句话 |
|---|---|---|
| **MCP**（[21-mcp](21-mcp.md)） | Agent ↔ **工具/数据源** | 给 Agent 接外部能力的"USB 口" |
| **A2A** | Agent ↔ **Agent** | 让 Agent 之间互相对话协作的"外交协议" |

两者互补而非竞争：一个 Agent 通过 **MCP** 拿到工具能力，多个这样的 Agent 之间再通过 **A2A** 协作。

### 三、代表框架 / 思路（概念级，具体代码见框架库）

| 框架 | 核心思路 | 一句话 |
|---|---|---|
| **LangGraph** | 把多 Agent 建模成**有向图**：节点是 Agent/步骤、边是流转、全局 state 做共享黑板 | 显式图编排，控制流最可控、可回环 |
| **AutoGen**（微软） | **可对话 Agent** 之间自由多轮对话（含 GroupChat + 一个 Manager 调度） | 对话驱动、灵活但需管好收敛 |
| **CrewAI** | 拟人化的 **Crew（团队）+ Role + Task**，角色分工 + 顺序/层级流程 | 角色化、上手直观 |
| **Spring AI Alibaba Graph** | JVM 生态的图编排，对标 LangGraph 的节点/边/state 思路 | Java 侧落地，实现见 [`../spring-ai-alibaba-learning`](../spring-ai-alibaba-learning)（`19-graph-basic` 等） |

> 原理相通：都在解决**拓扑（怎么连）+ 通信（怎么传状态）+ 终止（何时停）** 三件事，只是抽象和 API 不同。本库讲原理，代码落地链框架库。

## 🔑 要点速记

- **多智能体 = 按角色/职责/工具拆分 + 协作**（规划者+执行者+审查者），不是简单堆 Agent 数量。
- 拆分动机：单 Agent **上下文过载、工具选择困难、职责混乱** → 拆后每个 Agent **上下文聚焦、可并行、模块化、易维护**。
- 五种拓扑：**主管/编排型（最常用，即 orchestrator-workers）、网络对等型、层级型、流水线型、辩论评审型**；权衡是**中心化(可控) vs 去中心化(灵活)**。
- 通信两法：**消息传递** 与 **共享状态（黑板/全局 state）**。
- **A2A = Agent↔Agent 协作协议；MCP = Agent↔工具**，二者互补（[21-mcp](21-mcp.md)）。
- 代表框架：**LangGraph（图）/ AutoGen（对话）/ CrewAI（角色）/ Spring AI Alibaba Graph（JVM 图）**，本质都在解决拓扑+通信+终止。
- **铁律：单 Agent 能解决就别上多智能体**——多智能体的成本、延迟、复杂度都是数倍代价。

## ❓ 高频面试 / 理解题

**Q：什么时候该用多智能体，什么时候单 Agent 就够？**
A：默认先用单 Agent（一个 ReAct 循环 + 工具）。只有当单 Agent 出现**明显过载信号**才拆：工具多到模型频繁选错、上下文塞不下多种材料、一段 Prompt 要同时干几件互相打架的事、或任务天然可并行/需独立审查。判据是"拆分带来的聚焦收益 > 引入的协调成本"。**多数场景单 Agent 加好工具和 Prompt 就够了**，过早上多智能体是典型过度设计。

**Q：多智能体里 Agent 之间怎么协作？A2A 和 MCP 有什么区别？**
A：协作靠两种机制——**消息传递**（互相发任务/结果/反馈）和**共享状态**（读写同一块全局 state/黑板）；控制流由**拓扑**决定（谁指挥谁）。区别上：**MCP 解决 Agent 连工具/数据源**（给它外部能力），**A2A（Google Agent2Agent）解决 Agent 连 Agent**（让不同框架的 Agent 能互相发现、协商、通信）。一个是对内接工具，一个是对外找同伴，互补。

**Q：主管调度型（orchestrator）拓扑的优势和瓶颈是什么？**
A：优势是**控制流集中、可控可调试**——主管统一拆任务、分派、汇总、决定返工，最贴近人类团队的项目经理模式，也是 [23-agent-patterns](23-agent-patterns.md) 里 orchestrator-workers 的多 Agent 版。瓶颈是**主管本身是单点**：它的 Prompt 会变复杂，它判断失误会全局带偏，且所有信息都要过它、限制了并行度上限。规模再大就转向**层级型**（设子主管分摊）。

**Q：多智能体最大的坑是什么？**
A：**错误在协作链上传播放大 + 成本延迟叠加**。单点小错经过多轮传递会被后续 Agent 当真并层层放大；每个 Agent 都是一次（或多次）LLM 调用，成本和延迟按 Agent 数与轮数翻倍；再加上跨 Agent 的调试极难（问题出在哪个环节、哪次传递不好定位）。所以要加**审查者/护栏、明确终止条件、把 Agent 数量压到最少**。

## ⚠️ 易错点 / 实践建议

- ⚠️ **过度设计是头号陷阱**：不要一上来就设计五个 Agent 的复杂拓扑。**先用单 Agent 打通，遇到明确瓶颈再拆**，且能拆两个绝不拆五个。多智能体 Demo 好看、生产难维护。
- ⚠️ **成本与延迟按数量翻倍**：N 个 Agent、每个多轮对话 = LLM 调用次数爆炸，账单和响应时间都成倍上涨；辩论/评审型尤其烧钱。上线前务必估算调用量。
- ⚠️ **必须设终止条件**：对等/对话型拓扑极易陷入**死循环或来回踢皮球**（A 让 B 做、B 又推回 A）。一定要有最大轮数、超时、收敛判据兜底。
- ⚠️ **防错误传播**：给关键环节加**审查者 Agent 或护栏校验**，别让上游 Agent 的幻觉被下游当成事实继续放大（幻觉本质见 [05-hallucination](05-hallucination.md)）。
- ✅ **优先中心化拓扑**：不确定选什么就用**主管/编排型**——控制流清晰、最好调试；去中心化的网络型只在确有必要时上。
- ✅ **给每个 Agent 收窄上下文与工具**：多智能体的收益正来自"聚焦"，别又把大而全的工具和历史塞给每个子 Agent，否则等于白拆。
